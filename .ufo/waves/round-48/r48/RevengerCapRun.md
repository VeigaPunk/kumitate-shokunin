# RevengerCapRun — frozen runner-chain reconstruction

## Scope and evidence

This reconstructs `scripts/cap-run.mjs` and `scripts/cap-spawn.mjs` at frozen tip `fe3d45bf929246915c8c0de5f7f8682b5015b22c`. `cap-run.mjs` and `cap-spawn.mjs` have no working-tree diff from that tip. The shared working tree's F48 probe has a post-freeze change: the round-48 plan records pre-data amendment A48 (plan lines 125–133). I distinguish frozen F48 behavior below from that later amendment.

The `lsp` device is unavailable in this environment (`xd://lsp` returned “No such tool”; mounted devices are `ast_edit`, `debug`). Therefore this report is based on direct source reads and line anchors, not semantic-reference output; textual search was used only to locate references. No tests or selftests were run.

## Actual argv, environment, and descriptors

1. **`capSpawnSync` builds and starts the runner.** `CAP_RUN` is the adjacent `cap-run.mjs` path (cap-spawn lines 20–26). Defaults are `env={}`, `bind=[]`, `timeout=60000ms`, `mem=512MiB`, `tasks=64`, `encoding='utf8'` (28–30). Its runner argv is, in order: `[CAP_RUN, '--mem', mem, '--tasks', tasks, '--budget', timeout/1000, '--verdict-file', vf]`, then repeated `--bind <dir>`, then repeated `--env K=V` for object entries whose value is neither `undefined` nor `null`, then `-- <cmd> ...args` (31–37). The wrapper is launched as `process.execPath`.

   `cwd`, `encoding`, `maxBuffer`, and `input` are forwarded to Node's `spawnSync`; the wrapper timeout is `timeout + 10_000ms`. The wrapper environment is only `{PATH: process.env.PATH || '/usr/bin', XDG_RUNTIME_DIR: process.env.XDG_RUNTIME_DIR || '/run/user/<uid>'}`—not the caller's full environment and not the `env` option intended for the final child (38–41). `cwd` is the runner's cwd and becomes the sandbox child cwd.

2. **The runner resolves the command and constructs the exact systemd-run argv.** `LAUNCH_ENV` is only `PATH=/usr/bin` plus `XDG_RUNTIME_DIR` (cap-run lines 96–103). A command containing `/` is resolved against `process.cwd()`; otherwise the runner searches its own `process.env.PATH`, skipping empty path elements. It requires an executable regular file and uses its real path (147–158). It then sets the bwrap child `PATH` to `<real executable directory>:/usr/bin` (or just `/usr/bin` when that is the directory) and appends each parsed explicit env pair as another `--setenv K V` (177–190).

   The emitted `systemd-run` argv is exactly:
   ```text
   --user --scope --quiet --unit=<cap-run-PID-ms-randomhex>
   -p MemoryMax=<mem>M -p MemorySwapMax=0 -p TasksMax=<tasks> --
   env -i PATH=/usr/bin bwrap
   --ro-bind / / --dev /dev --proc /proc --tmpfs /tmp --tmpfs /run
   --bind <cwd> <cwd> [--bind <resolved-source> <destination> ...] --chdir <cwd>
   --unshare-pid --die-with-parent --new-session --clearenv
   --setenv PATH <bin-dir>:/usr/bin [--setenv K V ...]
   --argv0 <original cmd spelling> <resolved real path> [args...]
   ```
   Sources: cap-run lines 181–190; unit construction at 182. The actual properties use **two argv elements per property**, `'-p', 'MemoryMax=…'`, etc. The executable name is `systemd-run` (not absolute in argv), resolved through the runner's `/usr/bin` PATH. `env -i` strips the systemd-run environment before bwrap starts; `--clearenv` clears bwrap's child environment. The requested explicit pairs are then installed. The code supplies `--chdir` but no explicit `--setenv PWD`; the helper's header says the child has PWD (lines 14–22, 33–36), so that part relies on bwrap behavior rather than an explicit PWD argv entry.

   Mount order is intentional: root read-only, `/dev` and `/proc`, fresh `/tmp` and `/run`, then writable cwd and caller binds, then chdir (cap-run lines 187–190; header lines 14–23). The binds can therefore overlay the fresh tmpfs mounts. The user binds are validated as existing absolute directories and reject `/`, `/proc`, `/sys`, `/dev`, `/run` (parseArgs lines 122–132). The command's original spelling is `--argv0`; exec uses the resolved path.

3. **FD and output flow.** `capSpawnSync` does not expose a `stdio` option; `spawnSync` gets its standard pipe descriptors (and optional input), and `cap-run` starts `systemd-run` with `stdio: 'inherit'` (cap-spawn lines 38–41; cap-run line 198). Thus fd 0/1/2 are forwarded through `systemd-run` → `env` → bwrap → child; no extra fd-passing mechanism is configured. With a verdict file, the runner writes its verdict to a new file (`O_EXCL|O_NOFOLLOW`, mode 0600) so successful child stderr stays separate/byte-exact; on file-write failure it appends the verdict plus `verdict_file_error=...` to stderr (cap-run lines 199–214; cap-spawn lines 42–47). The cap-run selftest exercises stdout and byte-exact stderr in separate cases (322–349), but F48 does not inspect fd topology or assert this behavior.

## Error paths and silent behavior

- **Missing `systemd-run`:** Node's `spawn` error listener prints `cap-run: cannot spawn systemd-run: <code>` and finishes with `CAP_RUN: EXIT code=127 …` (cap-run lines 192–214, 243–246; exit map lines 63–66). There is no direct-child fallback. `capSpawnSync` recognizes that EXIT verdict and returns status 127; this is not converted to `ECAPRUN` (cap-spawn lines 48–57). The target never runs.
- **Missing `bwrap` [INFERENCE]:** the code does not preflight bwrap. `systemd-run` has already spawned `env -i PATH=/usr/bin bwrap ...`; if that lookup fails, the ordinary `env`/scope failure path should return nonzero (typically 127), which cap-run reports as `EXIT`, not `USAGE` or `ECAPRUN`. There is no fallback to run the target uncapped. This specific missing-bwrap result is inferred from the constructed argv and process-exit handler (cap-run lines 185–190, 247–259); the code contains no dedicated bwrap-missing branch.
- **Invalid runner args / command not found:** parse/resolve failures print `CAP_RUN: USAGE …` and exit 64 before any launch (cap-run lines 105–108, 110–145, 147–158). `capSpawnSync`'s verdict regex accepts only `EXIT|OOM|BUDGET|SIGNAL`, not `USAGE`, so it returns `status:null` and an `ECAPRUN` error (or the underlying spawn error) while retaining `capVerdict` (cap-spawn lines 48–52). A missing verdict file falls back only to the final stderr line if it begins `CAP_RUN: ` (43–46).
- **Outer timeout / runner crash:** the outer spawn timeout is budget+10s. If there is no recognized verdict, `r.error` wins; otherwise the helper constructs `ECAPRUN` (cap-spawn lines 38–40, 49–52). An inner BUDGET verdict maps to `status:null`, `signal:'SIGTERM'`, and `error.code='ETIMEDOUT'` (54–56), even though the runner's verdict/exit is code 124. A runner that exits without writing a recognized verdict is not treated as a normal child exit.
- **Unclean verdict artifact:** `mkdtempSync` creates `cap-spawn.*` and the verdict file is read, but `rmSync` is never called (cap-spawn lines 21–23, 31–47). This silently leaves the directory/file behind. `rmSync` is imported but unused (line 21).
- **Silent systemd/OOM fallback:** scope kill, `systemctl show`, and `reset-failed` failures are swallowed. OOM classification returns false if systemd/cgroup evidence cannot be read; it retries only after signal/high exit codes (cap-run lines 160–175, 192–194, 247–259). This can downgrade unavailable OOM evidence to ordinary EXIT; it does not cause an uncapped launch.
- **Budget/signal cleanup:** budget is total elapsed runner time; timeout or SIGTERM/SIGINT kills the scope, then after a 3s grace sends SIGKILL to the `systemd-run` PID, kills the scope again, and writes BUDGET/SIGNAL (cap-run lines 98–99, 192–240). Normal completion also kills the scope and attempts `reset-failed` (247–258). These cleanup commands are best-effort, not fail-closed errors.

## What frozen F48 actually validates—and trusts

The frozen predicate and its code are at `probe/caproute48-probe.mjs` lines 5–19, 239–261, 263–310, and 347–378. It observes archived gate runs under strace; it does not introspect the runner implementation as a program.

- **`-p` spelling is not an exact counter requirement.** `cap-run` emits `-p` followed by a separate `K=V` argv (lines 185–186). F48's `scopeProps` accepts `-p <value>`, `--property <value>`, `--property=<value>`, and compact `-pVALUE`, scans only before the first `--`, and stores the last value for each property (probe lines 239–253). `isScope` requires `/usr/bin/systemd-run`, `--scope`, exact `MemorySwapMax=0`, `MemoryMax=<digits>M` at most 1024, and `TasksMax=<digits>` at most 256 (254–260). It does not require `--user`, `--quiet`, or `--unit`; the regexes allow zero for MemoryMax/TasksMax, though cap-run's own CLI accepts only positive mem/tasks (cap-run 138–141). The counter checks argv shape/ancestry, not that systemd actually enforced the limits.
- **Bwrap is checked by path and flag presence, not full argv semantics.** F48 requires exact path `/usr/bin/bwrap` and presence of `--unshare-pid`, `--clearenv`, `--die-with-parent`; it does not check their order, mount list, `--chdir`, env pairs, command argv, or fd behavior (probe lines 254–261). It also does not require an `/usr/bin/env` exec in the chain.
- **The chain is ordered ancestry, not exact adjacency.** The checker finds a matching target exec, searches its ancestry for bwrap, then scope before that bwrap, then the node/cap-run exec before that scope (probe lines 280–310). It excludes machine paths from target candidates (47–49), recognizes node by basename `node` (50), and identifies the runner by `argv[1]` equaling the archived tree's `scripts/cap-run.mjs` path (263–282). It does not require each process to be the immediate parent of the next or hash/inspect the executable contents. The other direct children are constrained separately, with fixture-tool and named allowances (263–277; set allowances at 61–75).
- **Environment check is narrow.** The canary is planted on the gate run; F48 rejects its presence in the matched site's child `execve` envp (probe lines 200–207, 280–310). It does not assert that the child's entire environment is exactly `{PATH,PWD,...explicit pairs}`, or that no canary appears in intermediate runner environments. `capSpawnSync`'s wrapper whitelist and cap-run's two environment-clearing stages are the implementation evidence for the stronger filtering claim (cap-spawn 38–41; cap-run 100–103, 185–190).
- **Bind-view fidelity is outside this counter.** F48 checks routing and gate health, not that caller-requested host directories were actually mounted with the expected contents. The current attempt-2 plan explicitly records the `SP491`/`SP519` dropped-bind mutant that still reads 4/4 and assigns bind-view fidelity to integration source review (plan lines 133). Do not use a ROUTED_HELD score alone as evidence of filesystem-view equivalence.
- **Gate health has a post-freeze amendment.** Frozen F48 checks status, summary numbers, final verdict, FAIL lines, and execveat (probe lines 218–226, 347–378), but not that printed per-case lines corroborate the summary. The attempt-2 plan records a forged-summary control that passed frozen F48 and the pre-data A48 amendment adding per-case/pass-line corroboration for gates that print those lines (plan lines 125–131). The shared working-tree probe now has that later A48 change; a current run should be identified as `F48+A48`, not attributed to the frozen F48 source.
