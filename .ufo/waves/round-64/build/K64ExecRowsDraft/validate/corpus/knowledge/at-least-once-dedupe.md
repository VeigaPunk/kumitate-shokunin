# At-least-once delivery and operation identity

A redelivered message is normal under at-least-once delivery; it is not, by itself, proof that the original operation failed. For this lane, the durable task key, the dispatch attempt, a broker delivery identifier, and an invocation-receipt nonce are different identities. Keep those distinctions explicit when reasoning about claim/repend, retries, and downstream effects.

## Delivery contracts

- **MQTT QoS 1 permits duplicates.** The OASIS abstract says “At least once”, where messages are assured to arrive but duplicates can occur (S106, Abstract, saved HTML lines 1919-1920). A consumer cannot infer “first delivery” from success at this transport level. `receipt:.ufo/waves/round-54/build/ScoutMqtt/abstract-excerpt.txt@sha256:23a792b4e2cd99293e81f9be2fd359cc0bae2b3a5ac6ab5008f62b67501a03a7`
- **QoS 1 carries protocol delivery state.** A PUBLISH packet has a Packet Identifier in its Variable Header and is acknowledged by PUBACK (S106, §4.3.2, saved HTML lines 22302-22305); that names the protocol exchange, not this lane's durable task. `receipt:.ufo/waves/round-54/build/ScoutMqtt/qos1-excerpt.txt@sha256:c17b2a0d905864dab7297c0561c08529c9b4c736088970f8cdb3893297bc7e5a`
- **A Packet Identifier is not an application idempotency key.** MQTT requires an unused Packet Identifier for each new Application Message and starts that QoS 1 PUBLISH with DUP=0 (S106, §4.3.2, saved HTML lines 22317-22324); the field belongs to transport delivery state. Treating it as a cross-retry business key would exceed what the spec says. `receipt:.ufo/waves/round-54/build/ScoutMqtt/packet-identifier-excerpt.txt@sha256:f9fc49f41a58772814a9e6301e7e29983d654e4efa4eba14fe5bf2e6bf34ef42`
- **RabbitMQ can requeue a delivery.** Its consumer `basic.nack` / `basic.reject` behavior is controlled by `requeue`; when true, the broker requeues the delivery (S107, §Negative Acknowledgement and Requeuing of Deliveries, saved HTML lines 157-166). `receipt:.ufo/waves/round-54/build/ScoutRabbitmq/requeue-excerpt.txt@sha256:be8b45893d0fa3da6ba98ea8fd9d809ea7ed0dd3ea20af7b4913635b9ad16930`
- **RabbitMQ delivery tags are channel-scoped.** The official guide says a delivery tag uniquely identifies a delivery on a channel and must be acknowledged on that channel (S107, §Delivery Identifiers: Delivery Tags, saved HTML lines 67-82). It is not a durable identity to carry across channel or task lifetimes. `receipt:.ufo/waves/round-54/build/ScoutRabbitmq/delivery-tag-excerpt.txt@sha256:98003fbf6d385545bab72f1a3af36ff7bcfdd2c20fd7c47b285801497a508e73`
- **A broker acknowledgement is not the task's identity.** RabbitMQ's positive acknowledgement records a message as delivered and allows it to be discarded (S107, §Consumer Acknowledgement Modes, saved HTML lines 91-105); it is a delivery-state transition, not a stable key for the application operation. `receipt:.ufo/waves/round-54/build/ScoutRabbitmq/acknowledgement-excerpt.txt@sha256:a0c0839c5af5b72e010f79a5b2fe0c792559e90c875bc1fea4087cc884312f9c`

## Mapping to kumitate's queue and receipts

- **The queue task key is content-derived.** `queue-and-claim.md` records `task_${sha256(immutable).slice(0,24)}` as the `task_` key and separately defines `runId` / `sessionId`; the content key is the lane's durable operation handle, not a dispatch-attempt number. `receipt:.ufo/waves/round-54/build/ScoutQueue/task-key-and-attempts.txt@sha256:cd4cfb18f4b48545d24e7b75a149c22f0fc4f1d1f96dd4bcc2de27573e208cf9`
- **Attempts describe delivery tries, not identity.** In the queue note, `attempts` is monotone across repends; `resumeAttempts` and `launchMisses` have separate budgets and reset behavior. Do not key dedupe on any of them. `receipt:.ufo/waves/round-54/build/ScoutQueue/attempt-counters.txt@sha256:45e7129e5960e892ffcde7b4d70eb1ac7587cc5586cef25e37a9a12ab7f1ee65`
- **The claim is durable before spawn.** The dispatcher flips a row to `launching` and commits the queue before the spawn; a crash can leave a claim for reconciliation, while the same immutable task key remains the operation handle (`queue-and-claim.md` §Claim → dispatch pipeline). `receipt:.ufo/waves/round-54/build/ScoutQueue/claim-before-spawn.txt@sha256:a86d17287e60fcd3b257f6a1b44edf08a1af2103b545fc12d0d8ecd41e980881`
- **A receipt nonce identifies an invocation record.** The receipt entry says its nonce is freshly generated and the ledger detects reuse only when the same nonce is bound to a different record digest; this proves invocation-record freshness, not that two invocations are different business tasks (`invocation-attestation.md`). `receipt:.ufo/waves/round-54/build/ScoutReceipt/nonce-ledger.txt@sha256:54fe389f60704a2a6c573064e2105a13eb174fecca9dd04fc2142f16b6d7582f`
- **A receipt digest identifies the record, not the operation.** `receipt-identity-canonicalization.md` distinguishes canonical-JSON record identity from whole-file bytes and treats the ledger's evidence set as the directory; neither is the dispatcher's content-derived task key. `receipt:.ufo/waves/round-54/build/ScoutReceipt/record-identity.txt@sha256:72545d279dfb9611b9bf9ad5da6ef560c44f7998f36ee64b40beb73262ff2788`
- **[INFERENCE] Make side effects duplicate-safe at the operation boundary.** Since S106 permits duplicate QoS 1 delivery and S107 permits requeue, if repeated handling must not repeat an effect, the consumer needs a stable application/task identity and duplicate detection at that effect boundary; a timestamp, per-delivery tag, attempt counter, or receipt nonce is a different key. This is a design inference, not an exactly-once guarantee from either source. `receipt:.ufo/waves/round-54/build/ScoutReceipt/duplicate-delivery-inference.txt@sha256:8522e699a207aab28081d136464996485f2d47613379b47f80ab5cb30478ef31`
- **S107's version scope is pinned.** The RabbitMQ source is the official 4.4 documentation served on 2026-10-24; this entry does not generalize its requeue details to other broker versions. `receipt:.ufo/waves/round-54/build/ScoutRabbitmq/source-metadata.txt@sha256:11ad442765aa7389d01ad4da9400349a9ecc1a12085eb07e9d4551e705331bc0`
