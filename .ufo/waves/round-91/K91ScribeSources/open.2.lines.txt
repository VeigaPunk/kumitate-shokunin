67	
68	NAME top
69	open, openat, creat - open and possibly create a file
70	
71	LIBRARY top
72	Standard C library (libc, -lc)
73	
74	SYNOPSIS top
75	#include <fcntl.h>
76	
77	int open(const char *path, int flags, ...
78	/* mode_t mode */ );
79	
80	int creat(const char *path, mode_t mode);
81	
82	int openat(int dirfd, const char *path, int flags, ...
83	/* mode_t mode */ );
84	
85	/* Documented separately, in openat2(2): */
86	int openat2(int dirfd, const char *path,
87	const struct open_how *how, size_t size);
88	
89	Feature Test Macro Requirements for glibc (see
90	feature_test_macros(7)):
91	
92	openat():
93	Since glibc 2.10:
94	_POSIX_C_SOURCE >= 200809L
95	Before glibc 2.10:
96	_ATFILE_SOURCE
97	
98	DESCRIPTION top
99	The open() system call opens the file specified by path. If the
100	specified file does not exist, it may optionally (if O_CREAT is
101	specified in flags) be created by open().
102	
103	The return value of open() is a file descriptor, a small,
104	nonnegative integer that is an index to an entry in the process's
105	table of open file descriptors. The file descriptor is used in
106	subsequent system calls (read(2), write(2), lseek(2), fcntl(2),
107	etc.) to refer to the open file. The file descriptor returned by
108	a successful call will be the lowest-numbered file descriptor not
109	currently open for the process.
110	
111	By default, the new file descriptor is set to remain open across
112	an execve(2) (i.e., the FD_CLOEXEC file descriptor flag described
113	in fcntl(2) is initially disabled); the O_CLOEXEC flag, described
114	below, can be used to change this default. The file offset is set
115	to the beginning of the file (see lseek(2)).
116	
117	A call to open() creates a new open file description, an entry in
118	the system-wide table of open files. The open file description
119	records the file offset and the file status flags (see below). A
120	file descriptor is a reference to an open file description; this
121	reference is unaffected if path is subsequently removed or
122	modified to refer to a different file. For further details on
123	open file descriptions, see NOTES.
124	
125	The argument flags must include one of the following access modes:
126	O_RDONLY, O_WRONLY, or O_RDWR. These request opening the file
127	read-only, write-only, or read/write, respectively.
128	
129	In addition, zero or more file creation flags and file status
130	flags can be bitwise ORed in flags. The file creation flags are
131	O_CLOEXEC, O_CREAT, O_DIRECTORY, O_EXCL, O_NOCTTY, O_NOFOLLOW,
132	O_TMPFILE, and O_TRUNC. The file status flags are all of the
133	remaining flags listed below. The distinction between these two
134	groups of flags is that the file creation flags affect the
135	semantics of the open operation itself, while the file status
136	flags affect the semantics of subsequent I/O operations. The file
137	status flags can be retrieved and (in some cases) modified; see
138	fcntl(2) for details.
139	
140	The full list of file creation flags and file status flags is as
141	follows:
142	
143	O_APPEND
144	The file is opened in append mode. Before each write(2),
145	the file offset is positioned at the end of the file, as if
146	with lseek(2). The modification of the file offset and the
147	write operation are performed as a single atomic step.
148	
149	O_APPEND may lead to corrupted files on NFS filesystems if
150	more than one process appends data to a file at once. This
151	is because NFS does not support appending to a file, so the
152	client kernel has to simulate it, which can't be done
153	without a race condition.
154	
155	O_ASYNC
156	Enable signal-driven I/O: generate a signal (SIGIO by
157	default, but this can be changed via fcntl(2)) when input
158	or output becomes possible on this file descriptor. This
159	feature is available only for terminals, pseudoterminals,
160	sockets, and (since Linux 2.6) pipes and FIFOs. See
161	fcntl(2) for further details. See also BUGS, below.
162	
163	O_CLOEXEC (since Linux 2.6.23)
164	Enable the close-on-exec flag for the new file descriptor.
165	Specifying this flag permits a program to avoid additional
166	fcntl(2) F_SETFD operations to set the FD_CLOEXEC flag.
167	
168	Note that the use of this flag is essential in some
169	multithreaded programs, because using a separate fcntl(2)
170	F_SETFD operation to set the FD_CLOEXEC flag does not
171	suffice to avoid race conditions where one thread opens a
172	file descriptor and attempts to set its close-on-exec flag
173	using fcntl(2) at the same time as another thread does a
174	fork(2) plus execve(2). Depending on the order of
175	execution, the race may lead to the file descriptor
176	returned by open() being unintentionally leaked to the
177	program executed by the child process created by fork(2).
178	(This kind of race is in principle possible for any system
179	call that creates a file descriptor whose close-on-exec
180	flag should be set, and various other Linux system calls
181	provide an equivalent of the O_CLOEXEC flag to deal with
182	this problem.)
183	
184	O_CREAT
185	If path does not exist, create it as a regular file.
186	
187	The owner (user ID) of the new file is set to the effective
188	user ID of the process.
189	
190	The group ownership (group ID) of the new file is set
191	either to the effective group ID of the process (System V
192	semantics) or to the group ID of the parent directory (BSD
193	semantics). On Linux, the behavior depends on whether the
194	set-group-ID mode bit is set on the parent directory: if
195	that bit is set, then BSD semantics apply; otherwise,
196	System V semantics apply. For some filesystems, the
197	behavior also depends on the bsdgroups and sysvgroups mount
198	options described in mount(8).
199	
200	The mode argument specifies the file mode bits to be
201	applied when a new file is created. If neither O_CREAT nor
202	O_TMPFILE is specified in flags, then mode is ignored (and
203	can thus be specified as 0, or simply omitted). The mode
204	argument must be supplied if O_CREAT or O_TMPFILE is
205	specified in flags; if it is not supplied, some arbitrary
206	bytes from the stack will be applied as the file mode.
207	
208	The effective mode is modified by the process's umask in
209	the usual way: in the absence of a default ACL, the mode of
210	the created file is (mode & ~umask).
211	
212	Note that mode applies only to future accesses of the newly
213	created file; the open() call that creates a read-only file
214	may well return a read/write file descriptor.
215	
216	The following symbolic constants are provided for mode:
217	
218	S_IRWXU 00700 user (file owner) has read, write, and
219	execute permission
220	
221	S_IRUSR 00400 user has read permission
222	
223	S_IWUSR 00200 user has write permission
224	
225	S_IXUSR 00100 user has execute permission
226	
227	S_IRWXG 00070 group has read, write, and execute
228	permission
229	
230	S_IRGRP 00040 group has read permission
231	
232	S_IWGRP 00020 group has write permission
233	
234	S_IXGRP 00010 group has execute permission
235	
236	S_IRWXO 00007 others have read, write, and execute
237	permission
238	
239	S_IROTH 00004 others have read permission
240	
241	S_IWOTH 00002 others have write permission
242	
243	S_IXOTH 00001 others have execute permission
244	
245	According to POSIX, the effect when other bits are set in
246	mode is unspecified. On Linux, the following bits are also
247	honored in mode:
248	
249	S_ISUID 0004000 set-user-ID bit
250	
251	S_ISGID 0002000 set-group-ID bit (see inode(7)).
252	
253	S_ISVTX 0001000 sticky bit (see inode(7)).
254	
255	O_DIRECT (since Linux 2.4.10)
256	Try to minimize cache effects of the I/O to and from this
257	file. In general this will degrade performance, but it is
258	useful in special situations, such as when applications do
259	their own caching. File I/O is done directly to/from user-
260	space buffers. The O_DIRECT flag on its own makes an
261	effort to transfer data synchronously, but does not give
262	the guarantees of the O_SYNC flag that data and necessary
263	metadata are transferred. To guarantee synchronous I/O,
264	O_SYNC must be used in addition to O_DIRECT. See NOTES
265	below for further discussion.
266	
267	A semantically similar (but deprecated) interface for block
268	devices is described in raw(8).
269	
270	O_DIRECTORY
271	If path is not a directory, cause open() to fail. This
272	flag was added in Linux 2.1.126, to avoid denial-of-service
273	problems if opendir(3) is called on a FIFO or tape device.
274	
275	O_DSYNC
276	Write operations on the file will complete according to the
277	requirements of synchronized I/O data integrity completion.
278	
279	By the time write(2) (and similar) return, the output data
280	has been transferred to the underlying hardware, along with
281	any file metadata that would be required to retrieve that
282	data (i.e., as though each write(2) was followed by a call
283	to fdatasync(2)). See VERSIONS.
284	
285	O_EXCL Ensure that this call creates the file: if this flag is
286	specified in conjunction with O_CREAT, and path already
287	exists, then open() fails with the error EEXIST.
288	
289	When these two flags are specified, symbolic links are not
290	followed: if path is a symbolic link, then open() fails
291	regardless of where the symbolic link points.
292	
293	In general, the behavior of O_EXCL is undefined if it is
294	used without O_CREAT. There is one exception: on Linux 2.6
295	and later, O_EXCL can be used without O_CREAT if path
296	refers to a block device. If the block device is in use by
297	the system (e.g., mounted), open() fails with the error
298	EBUSY.
299	
300	On NFS, O_EXCL is supported only when using NFSv3 or later
301	on kernel 2.6 or later. In NFS environments where O_EXCL
302	support is not provided, programs that rely on it for
303	performing locking tasks will contain a race condition.
304	Portable programs that want to perform atomic file locking
305	using a lockfile, and need to avoid reliance on NFS support
306	for O_EXCL, can create a unique file on the same filesystem
307	(e.g., incorporating hostname and PID), and use link(2) to
308	make a link to the lockfile. If link(2) returns 0, the
309	lock is successful. Otherwise, use stat(2) on the unique
310	file to check if its link count has increased to 2, in
311	which case the lock is also successful.
312	
313	O_LARGEFILE
314	(LFS) Allow files whose sizes cannot be represented in an
315	off_t (but can be represented in an off64_t) to be opened.
316	The _LARGEFILE64_SOURCE macro must be defined (before
317	including any header files) in order to obtain this
318	definition. Setting the _FILE_OFFSET_BITS feature test
319	macro to 64 (rather than using O_LARGEFILE) is the
320	preferred method of accessing large files on 32-bit systems
321	(see feature_test_macros(7)).
322	
323	O_NOATIME (since Linux 2.6.8)
324	Do not update the file last access time (st_atime in the
325	inode) when the file is read(2).
326	
327	This flag can be employed only if one of the following
328	conditions is true:
329	
330	• The effective UID of the process matches the owner UID
331	of the file.
332	
333	• The calling process has the CAP_FOWNER capability in its
334	user namespace and the owner UID of the file has a
335	mapping in the namespace.
336	
337	This flag is intended for use by indexing or backup
338	programs, where its use can significantly reduce the amount
339	of disk activity. This flag may not be effective on all
340	filesystems. One example is NFS, where the server
341	maintains the access time.
342	
343	O_NOCTTY
344	If path refers to a terminal device—see tty(4)—it will not
345	become the process's controlling terminal even if the
346	process does not have one.
347	
348	O_NOFOLLOW
349	If the trailing component (i.e., basename) of path is a
350	symbolic link, then the open fails, with the error ELOOP.
351	Symbolic links in earlier components of the pathname will
352	still be followed. (Note that the ELOOP error that can
353	occur in this case is indistinguishable from the case where
354	an open fails because there are too many symbolic links
355	found while resolving components in the path prefix of the
356	pathname.)
357	
358	This flag is a FreeBSD extension, which was added in Linux
359	2.1.126, and has subsequently been standardized in
360	POSIX.1-2008.
361	
362	See also O_PATH below.
363	
364	O_NONBLOCK or O_NDELAY
365	When possible, the file is opened in nonblocking mode.
366	Neither the open() nor any subsequent I/O operations on the
367	file descriptor which is returned will cause the calling
368	process to wait.
369	
370	Note that the setting of this flag has no effect on the
371	operation of poll(2), select(2), epoll(7), and similar,
372	since those interfaces merely inform the caller about
373	whether a file descriptor is "ready", meaning that an I/O
374	operation performed on the file descriptor with the
375	O_NONBLOCK flag clear would not block.
376	
377	Note that this flag has no effect for regular files and
378	block devices; that is, I/O operations will (briefly) block
379	when device activity is required, regardless of whether
380	O_NONBLOCK is set. Since O_NONBLOCK semantics might
381	eventually be implemented, applications should not depend
382	upon blocking behavior when specifying this flag for
383	regular files and block devices.
384	
385	For the handling of FIFOs (named pipes), see also fifo(7).
386	For a discussion of the effect of O_NONBLOCK in conjunction
387	with mandatory file locks and with file leases, see
388	fcntl(2).
389	
390	O_PATH (since Linux 2.6.39)
391	Obtain a file descriptor that can be used for two purposes:
392	to indicate a location in the filesystem tree and to
393	perform operations that act purely at the file descriptor
394	level. The file itself is not opened, and other file
395	operations (e.g., read(2), write(2), fchmod(2), fchown(2),
396	fgetxattr(2), ioctl(2), mmap(2)) fail with the error EBADF.
397	
398	The following operations can be performed on the resulting
399	file descriptor:
400	
401	• close(2).
402	
403	• fchdir(2), if the file descriptor refers to a directory
404	(since Linux 3.5).
405	
406	• fstat(2) (since Linux 3.6).
407	
408	• fstatfs(2) (since Linux 3.12).
409	
410	• Duplicating the file descriptor (dup(2), fcntl(2)
411	F_DUPFD, etc.).
412	
413	• Getting and setting file descriptor flags (fcntl(2)
414	F_GETFD and F_SETFD).
415	
416	• Retrieving open file status flags using the fcntl(2)
417	F_GETFL operation: the returned flags will include the
418	bit O_PATH.
419	
420	• Passing the file descriptor as the dirfd argument of
421	openat() and the other "*at()" system calls. This
422	includes linkat(2) with AT_EMPTY_PATH (or via procfs
423	using AT_SYMLINK_FOLLOW) even if the file is not a
424	directory.
425	
426	• Passing the file descriptor to another process via a
427	UNIX domain socket (see SCM_RIGHTS in unix(7)).
428	
429	When O_PATH is specified in flags, flag bits other than
430	O_CLOEXEC, O_DIRECTORY, and O_NOFOLLOW are ignored.
431	
432	Opening a file or directory with the O_PATH flag requires
433	no permissions on the object itself (but does require
434	execute permission on the directories in the path prefix).
435	Depending on the subsequent operation, a check for suitable
436	file permissions may be performed (e.g., fchdir(2) requires
437	execute permission on the directory referred to by its file
438	descriptor argument). By contrast, obtaining a reference
439	to a filesystem object by opening it with the O_RDONLY flag
440	requires that the caller have read permission on the
441	object, even when the subsequent operation (e.g.,
442	fchdir(2), fstat(2)) does not require read permission on
443	the object.
444	
445	If path is a symbolic link and the O_NOFOLLOW flag is also
446	specified, then the call returns a file descriptor
447	referring to the symbolic link. This file descriptor can
448	be used as the dirfd argument in calls to fchownat(2),
449	fstatat(2), linkat(2), and readlinkat(2) with an empty
450	pathname to have the calls operate on the symbolic link.
451	
452	If path refers to an automount point that has not yet been
453	triggered, so no other filesystem is mounted on it, then
454	the call returns a file descriptor referring to the
455	automount directory without triggering a mount. fstatfs(2)
456	can then be used to determine if it is, in fact, an
457	untriggered automount point (.f_type ==
458	AUTOFS_SUPER_MAGIC).
459	
460	One use of O_PATH for regular files is to provide the
461	equivalent of POSIX.1's O_EXEC functionality. This permits
462	us to open a file for which we have execute permission but
463	not read permission, and then execute that file, with steps
464	something like the following:
465	
466	char buf[PATH_MAX];
467	fd = open("some_prog", O_PATH);
468	snprintf(buf, PATH_MAX, "/proc/self/fd/%d", fd);
469	execl(buf, "some_prog", (char *) NULL);
470	
471	An O_PATH file descriptor can also be passed as the
472	argument of fexecve(3).
473	
474	O_SYNC Write operations on the file will complete according to the
475	requirements of synchronized I/O file integrity completion
476	(by contrast with the synchronized I/O data integrity
477	completion provided by O_DSYNC.)
478	
479	By the time write(2) (or similar) returns, the output data
480	and associated file metadata have been transferred to the
481	underlying hardware (i.e., as though each write(2) was
482	followed by a call to fsync(2)). See VERSIONS.
483	
484	O_TMPFILE (since Linux 3.11)
485	Create an unnamed temporary regular file. The path
486	argument specifies a directory; an unnamed inode will be
487	created in that directory's filesystem. Anything written
488	to the resulting file will be lost when the last file
489	descriptor is closed, unless the file is given a name.
490	
491	O_TMPFILE must be specified with one of O_RDWR or O_WRONLY
492	and, optionally, O_EXCL. If O_EXCL is not specified, then
493	linkat(2) can be used to link the temporary file into the
494	filesystem, making it permanent, using code like the
495	following:
496	
497	char path[PATH_MAX];
498	fd = open("/path/to/dir", O_TMPFILE | O_RDWR,
499	S_IRUSR | S_IWUSR);
500	
501	/* File I/O on 'fd'... */
502	
503	linkat(fd, "", AT_FDCWD, "/path/for/file", AT_EMPTY_PATH);
504	
505	/* If the caller doesn't have the CAP_DAC_READ_SEARCH
506	capability (needed to use AT_EMPTY_PATH with linkat(2)),
507	and there is a proc(5) filesystem mounted, then the
508	linkat(2) call above can be replaced with:
509	
510	snprintf(path, PATH_MAX, "/proc/self/fd/%d", fd);
511	linkat(AT_FDCWD, path, AT_FDCWD, "/path/for/file",
512	AT_SYMLINK_FOLLOW);
513	*/
514	
515	In this case, the open() mode argument determines the file
516	permission mode, as with O_CREAT.
517	
518	Specifying O_EXCL in conjunction with O_TMPFILE prevents a
519	temporary file from being linked into the filesystem in the
520	above manner. (Note that the meaning of O_EXCL in this
521	case is different from the meaning of O_EXCL otherwise.)
522	
523	There are two main use cases for O_TMPFILE:
524	
525	• Improved tmpfile(3) functionality: race-free creation of
526	temporary files that (1) are automatically deleted when
527	closed; (2) can never be reached via any pathname; (3)
528	are not subject to symlink attacks; and (4) do not
529	require the caller to devise unique names.
530	
531	• Creating a file that is initially invisible, which is
532	then populated with data and adjusted to have
533	appropriate filesystem attributes (fchown(2), fchmod(2),
534	fsetxattr(2), etc.) before being atomically linked into
535	the filesystem in a fully formed state (using linkat(2)
536	as described above).
537	
538	O_TMPFILE requires support by the underlying filesystem;
539	only a subset of Linux filesystems provide that support.
540	In the initial implementation, support was provided in the
541	ext2, ext3, ext4, UDF, Minix, and tmpfs filesystems.
542	Support for other filesystems has subsequently been added
543	as follows: XFS (Linux 3.15); Btrfs (Linux 3.16); F2FS
544	(Linux 3.16); and ubifs (Linux 4.9)
545	
546	O_TRUNC
547	If the file already exists and is a regular file and the
548	access mode allows writing (i.e., is O_RDWR or O_WRONLY) it
549	will be truncated to length 0. If the file is a FIFO or
550	terminal device file, the O_TRUNC flag is ignored.
551	Otherwise, the effect of O_TRUNC is unspecified.
552	
553	creat()
554	A call to creat() is equivalent to calling open() with flags equal
555	to O_CREAT|O_WRONLY|O_TRUNC.
556	
557	openat()
558	The openat() system call operates in exactly the same way as
559	open(), except for the differences described here.
560	
561	The dirfd argument is used in conjunction with the path argument
562	as follows:
563	
564	• If the pathname given in path is absolute, then dirfd is
565	ignored.
566	
567	• If the pathname given in path is relative and dirfd is the
568	special value AT_FDCWD, then path is interpreted relative to
569	the current working directory of the calling process (like
570	open()).
571	
572	• If the pathname given in path is relative, then it is
573	interpreted relative to the directory referred to by the file
574	descriptor dirfd (rather than relative to the current working
575	directory of the calling process, as is done by open() for a
576	relative pathname). In this case, dirfd must be a directory
577	that was opened for reading (O_RDONLY) or using the O_PATH
578	flag.
579	
580	If the pathname given in path is relative, and dirfd is not a
581	valid file descriptor, an error (EBADF) results. (Specifying an
582	invalid file descriptor number in dirfd can be used as a means to
583	ensure that path is absolute.)
584	
585	openat2(2)
586	The openat2(2) system call is an extension of openat(), and
587	provides a superset of the features of openat(). It is documented
588	separately, in openat2(2).
589	
590	RETURN VALUE top
591	On success, open(), openat(), and creat() return the new file
592	descriptor (a nonnegative integer). On error, -1 is returned and
593	errno is set to indicate the error.
594	
595	ERRORS top
596	open(), openat(), and creat() can fail with the following errors:
597	
598	EACCES The requested access to the file is not allowed, or search
599	permission is denied for one of the directories in the path
600	prefix of path, or the file did not exist yet and write
601	access to the parent directory is not allowed. (See also
602	path_resolution(7).)
603	
604	EACCES Where O_CREAT is specified, the protected_fifos or
605	protected_regular sysctl is enabled, the file already
606	exists and is a FIFO or regular file, the owner of the file
607	is neither the current user nor the owner of the containing
608	directory, and the containing directory is both world- or
609	group-writable and sticky. For details, see the
610	descriptions of /proc/sys/fs/protected_fifos and
611	/proc/sys/fs/protected_regular in proc_sys_fs(5).
612	
613	EBADF (openat()) path is relative but dirfd is neither AT_FDCWD
614	nor a valid file descriptor.
615	
616	EBUSY O_EXCL was specified in flags and path refers to a block
617	device that is in use by the system (e.g., it is mounted).
618	
619	EDQUOT Where O_CREAT is specified, the file does not exist, and
620	the user's quota of disk blocks or inodes on the filesystem
621	has been exhausted.
622	
623	EEXIST path already exists and O_CREAT and O_EXCL were used.
624	
625	EFAULT path points outside your accessible address space.
626	
627	EFBIG See EOVERFLOW.
628	
629	EINTR While blocked waiting to complete an open of a slow device
630	(e.g., a FIFO; see fifo(7)), the call was interrupted by a
631	signal handler; see signal(7).
632	
633	EINVAL The filesystem does not support the O_DIRECT flag. See
634	NOTES for more information.
635	
636	EINVAL Invalid value in flags.
637	
638	EINVAL O_TMPFILE was specified in flags, but neither O_WRONLY nor
639	O_RDWR was specified.
640	
641	EINVAL O_CREAT and O_DIRECTORY were both specified in flags , and
642	the Linux kernel version is 6.4 or later. (Earlier kernels
643	were inconsistent in this area, and POSIX does not specify
644	the behavior.)
645	
646	EINVAL O_CREAT was specified in flags and the final component

760	Synchronized I/O
761	The POSIX.1-2008 "synchronized I/O" option specifies different
762	variants of synchronized I/O, and specifies the open() flags
763	O_SYNC, O_DSYNC, and O_RSYNC for controlling the behavior.
764	Regardless of whether an implementation supports this option, it
765	must at least support the use of O_SYNC for regular files.
766	
767	Linux implements O_SYNC and O_DSYNC, but not O_RSYNC. Somewhat
768	incorrectly, glibc defines O_RSYNC to have the same value as
769	O_SYNC. (O_RSYNC is defined in the Linux header file
770	<asm/fcntl.h> on HP PA-RISC, but it is not used.)
771	
772	O_SYNC provides synchronized I/O file integrity completion,
773	meaning write operations will flush data and all associated
774	metadata to the underlying hardware. O_DSYNC provides
775	synchronized I/O data integrity completion, meaning write
776	operations will flush data to the underlying hardware, but will
777	only flush metadata updates that are required to allow a
778	subsequent read operation to complete successfully. Data
779	integrity completion can reduce the number of disk operations that
780	are required for applications that don't need the guarantees of
781	file integrity completion.
782	
783	To understand the difference between the two types of completion,
784	consider two pieces of file metadata: the file last modification
785	timestamp (st_mtime) and the file length. All write operations
786	will update the last file modification timestamp, but only writes
787	that add data to the end of the file will change the file length.
788	The last modification timestamp is not needed to ensure that a
789	read completes successfully, but the file length is. Thus,
790	O_DSYNC would only guarantee to flush updates to the file length
791	metadata (whereas O_SYNC would also always flush the last
792	modification timestamp metadata).
793	
794	Before Linux 2.6.33, Linux implemented only the O_SYNC flag for
795	open(). However, when that flag was specified, most filesystems
796	actually provided the equivalent of synchronized I/O data
797	integrity completion (i.e., O_SYNC was actually implemented as the
798	equivalent of O_DSYNC).
799	
800	Since Linux 2.6.33, proper O_SYNC support is provided. However,
801	to ensure backward binary compatibility, O_DSYNC was defined with
802	the same value as the historical O_SYNC, and O_SYNC was defined as
803	a new (two-bit) flag value that includes the O_DSYNC flag value.
804	This ensures that applications compiled against new headers get at
805	least O_DSYNC semantics before Linux 2.6.33.

845	Under Linux, the O_NONBLOCK flag is sometimes used in cases where

847	read or write. For example, this may be used to open a device in
848	order to get a file descriptor for use with ioctl(2).

854	fields (respectively, time of last access, time of last status
855	change, and time of last modification; see stat(2)) are set to the
856	current time, and so are the st_ctime and st_mtime fields of the
857	parent directory. Otherwise, if the file is modified because of
858	the O_TRUNC flag, its st_ctime and st_mtime fields are set to the
859	current time.

862	descriptors of the process with the PID pid. The files in the
863	/proc/pid/fdinfo directory show even more information about these
864	file descriptors. See proc(5) for further details of both of
865	these directories.

870	Open file descriptions
871	The term open file description is the one used by POSIX to refer
872	to the entries in the system-wide table of open files. In other
873	contexts, this object is variously also called an "open file
874	object", a "file handle", an "open file table entry", or—in
875	kernel-developer parlance—a struct file.
876	
877	When a file descriptor is duplicated (using dup(2) or similar),
878	the duplicate refers to the same open file description as the
879	original file descriptor, and the two file descriptors
880	consequently share the file offset and file status flags. Such
881	sharing can also occur between processes: a child process created
882	via fork(2) inherits duplicates of its parent's file descriptors,
883	and those duplicates refer to the same open file descriptions.
884	
885	Each open() of a file creates a new open file description; thus,
886	there may be multiple open file descriptions corresponding to a
887	file inode.
888	
889	On Linux, one can use the kcmp(2) KCMP_FILE operation to test
890	whether two file descriptors (in the same process or in two
891	different processes) refer to the same open file description.
892	
893	NFS
894	There are many infelicities in the protocol underlying NFS,
895	affecting amongst others O_SYNC and O_NDELAY.
896	
897	On NFS filesystems with UID mapping enabled, open() may return a
898	file descriptor but, for example, read(2) requests are denied with
899	EACCES. This is because the client performs open() by checking
900	the permissions, but UID mapping is performed by the server upon
901	read and write requests.
902	
903	FIFOs
904	Opening the read or write end of a FIFO blocks until the other end
905	is also opened (by another process or thread). See fifo(7) for
906	further details.

908	File access mode
909	Unlike the other values that can be specified in flags, the access
910	mode values O_RDONLY, O_WRONLY, and O_RDWR do not specify
911	individual bits. Rather, they define the low order two bits of
912	flags, and are defined respectively as 0, 1, and 2. In other
913	words, the combination O_RDONLY | O_WRONLY is a logical error, and
914	certainly does not have the same meaning as O_RDWR.
915	
916	Linux reserves the special, nonstandard access mode 3 (binary 11)
917	in flags to mean: check for read and write permission on the file
918	and return a file descriptor that can't be used for reading or
919	writing. This nonstandard access mode is used by some Linux
920	drivers to return a file descriptor that is to be used only for
921	device-specific ioctl(2) operations.
922	
923	Rationale for openat() and other directory file descriptor APIs
924	openat() and the other system calls and library functions that
925	take a directory file descriptor argument (i.e., execveat(2),
926	faccessat(2), fanotify_mark(2), fchmodat(2), fchownat(2),
927	fspick(2), fstatat(2), futimesat(2), linkat(2), mkdirat(2),
928	mknodat(2), mount_setattr(2), move_mount(2), name_to_handle_at(2),
929	open_tree(2), openat2(2), readlinkat(2), renameat(2),
930	renameat2(2), statx(2), symlinkat(2), unlinkat(2), utimensat(2),
931	mkfifoat(3), and scandirat(3)) address two problems with the older
932	interfaces that preceded them. Here, the explanation is in terms
933	of the openat() call, but the rationale is analogous for the other
934	interfaces.
935	
936	First, openat() allows an application to avoid race conditions
937	that could occur when using open() to open files in directories
938	other than the current working directory. These race conditions
939	result from the fact that some component of the directory prefix
940	given to open() could be changed in parallel with the call to
941	open(). Suppose, for example, that we wish to create the file
942	dir1/dir2/xxx.dep if the file dir1/dir2/xxx exists. The problem
943	is that between the existence check and the file-creation step,
944	dir1 or dir2 (which might be symbolic links) could be modified to
945	point to a different location. Such races can be avoided by
946	opening a file descriptor for the target directory, and then
947	specifying that file descriptor as the dirfd argument of (say)
948	fstatat(2) and openat(). The use of the dirfd file descriptor
949	also has other benefits:
950	
951	• the file descriptor is a stable reference to the directory,
952	even if the directory is renamed; and
953	
954	• the open file descriptor prevents the underlying filesystem
955	from being dismounted, just as when a process has a current
956	working directory on a filesystem.
957	
958	Second, openat() allows the implementation of a per-thread
959	"current working directory", via file descriptor(s) maintained by
960	the application. (This functionality can also be obtained by
961	tricks based on the use of /proc/self/fd/dirfd, but less
962	efficiently.)
963	
964	The dirfd argument for these APIs can be obtained by using open()
965	or openat() to open a directory (with either the O_RDONLY or the
966	O_PATH flag). Alternatively, such a file descriptor can be
967	obtained by applying dirfd(3) to a directory stream created using
968	opendir(3).
969	
970	When these APIs are given a dirfd argument of AT_FDCWD or the
971	specified pathname is absolute, then they handle their pathname
972	argument in the same way as the corresponding conventional APIs.
973	However, in this case, several of the APIs have a flags argument
974	that provides access to functionality that is not available with
975	the corresponding conventional APIs.
976	
977	O_DIRECT
978	The O_DIRECT flag may impose alignment restrictions on the length
979	and address of user-space buffers and the file offset of I/Os. In
980	Linux alignment restrictions vary by filesystem and kernel version
981	and might be absent entirely. The handling of misaligned O_DIRECT
982	I/Os also varies; they can either fail with EINVAL or fall back to
983	buffered I/O.
984	
985	Since Linux 6.1, O_DIRECT support and alignment restrictions for a
986	file can be queried using statx(2), using the STATX_DIOALIGN flag.
987	Support for STATX_DIOALIGN varies by filesystem; see statx(2).
988	
989	Some filesystems provide their own interfaces for querying
990	O_DIRECT alignment restrictions, for example the XFS_IOC_DIOINFO
991	operation in xfsctl(3). STATX_DIOALIGN should be used instead
992	when it is available.
993	
994	If none of the above is available, then direct I/O support and
995	alignment restrictions can only be assumed from known
996	characteristics of the filesystem, the individual file, the
997	underlying storage device(s), and the kernel version. In Linux
998	2.4, most filesystems based on block devices require that the file
999	offset and the length and memory address of all I/O segments be
1000	multiples of the filesystem block size (typically 4096 bytes). In
1001	Linux 2.6.0, this was relaxed to the logical block size of the
1002	block device (typically 512 bytes). A block device's logical
1003	block size can be determined using the ioctl(2) BLKSSZGET
1004	operation or from the shell using the command:
1005	
1006	blockdev --getss
1007	
1008	O_DIRECT I/Os should never be run concurrently with the fork(2)
1009	system call, if the memory buffer is a private mapping (i.e., any
1010	mapping created with the mmap(2) MAP_PRIVATE flag; this includes
1011	memory allocated on the heap and statically allocated buffers).
1012	Any such I/Os, whether submitted via an asynchronous I/O interface
1013	or from another thread in the process, should be completed before
1014	fork(2) is called. Failure to do so can result in data corruption
1015	and undefined behavior in parent and child processes. This
1016	restriction does not apply when the memory buffer for the O_DIRECT
1017	I/Os was created using shmat(2) or mmap(2) with the MAP_SHARED
1018	flag. Nor does this restriction apply when the memory buffer has
1019	been advised as MADV_DONTFORK with madvise(2), ensuring that it
1020	will not be available to the child after fork(2).
1021	
1022	The O_DIRECT flag was introduced in SGI IRIX, where it has
1023	alignment restrictions similar to those of Linux 2.4. IRIX has
1024	also a fcntl(2) call to query appropriate alignments, and sizes.
1025	FreeBSD 4.x introduced a flag of the same name, but without
1026	alignment restrictions.
1027	
1028	O_DIRECT support was added in Linux 2.4.10. Older Linux kernels
1029	simply ignore this flag. Some filesystems may not implement the
1030	flag, in which case open() fails with the error EINVAL if it is
1031	used.
1032	
1033	Applications should avoid mixing O_DIRECT and normal I/O to the
1034	same file, and especially to overlapping byte regions in the same
1035	file. Even when the filesystem correctly handles the coherency
1036	issues in this situation, overall I/O throughput is likely to be
1037	slower than using either mode alone. Likewise, applications
1038	should avoid mixing mmap(2) of files with direct I/O to the same
1039	files.
1040	
1041	The behavior of O_DIRECT with NFS will differ from local
1042	filesystems. Older kernels, or kernels configured in certain
1043	ways, may not support this combination. The NFS protocol does not
1044	support passing the flag to the server, so O_DIRECT I/O will
1045	bypass the page cache only on the client; the server may still
1046	cache the I/O. The client asks the server to make the I/O
1047	synchronous to preserve the synchronous semantics of O_DIRECT.
1048	Some servers will perform poorly under these circumstances,
1049	especially if the I/O size is small. Some servers may also be
1050	configured to lie to clients about the I/O having reached stable
1051	storage; this will avoid the performance penalty at some risk to
1052	data integrity in the event of server power failure. The Linux
1053	NFS client places no alignment restrictions on O_DIRECT I/O.
1054	
1055	In summary, O_DIRECT is a potentially powerful tool that should be
1056	used with caution. It is recommended that applications treat use
1057	of O_DIRECT as a performance option which is disabled by default.
