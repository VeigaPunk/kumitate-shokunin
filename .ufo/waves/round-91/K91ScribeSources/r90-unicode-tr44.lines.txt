181	Note: the information in
182	this annex is not intended as an exhaustive description of the use and
183	interpretation of Unicode character properties and behavior. It must be used in conjunction with
184	the data in the other files in the Unicode Character Database, and relies on the notation and
185	definitions supplied in The Unicode
186	Standard. All chapter references are to Version
187	18.0.0 of the standard unless otherwise indicated.
188	
189	1 Introduction
190	
191	The Unicode Standard is far more than a simple encoding of characters.
192	The standard also associates a rich set of semantics with each encoded
193	character—properties that
194	are required for interoperability and correct behavior in
195	implementations, as well as for Unicode conformance.
196	These semantics are cataloged in the Unicode Character Database (UCD), a collection of data files
197	which contain the Unicode character code points and character names.
198	The data files define the Unicode character properties and mappings between
199	Unicode characters (such as case mappings).
200	
201	This annex describes the UCD and provides a guide to the various
202	documentation files associated with it. Additional information
203	about character properties and their use is contained in the
204	Unicode Standard and its annexes. In particular, implementers should familiarize themselves
205	with the formal definitions and conformance requirements for properties detailed
206	in Section 3.5, Properties in [Unicode]
207	and with the material in Chapter 4, Character Properties in
208	[Unicode].
209	Additional discussion about the Unicode
210	character property model can be found in [UTR23].
211	
212	The location of the data files associated with the UCD is documented
213	in Data Files.
214	
215	2 Conformance
216	
217	The Unicode Character Database is an integral part of the Unicode Standard.
218	
219	The UCD contains normative property and mapping information required for
220	implementation of various Unicode algorithms such as the Unicode Bidirectional
221	Algorithm, Unicode Normalization, and Unicode Casefolding. The data files also
222	contain additional informative and provisional character property information.
223	
224	Each specification of a Unicode algorithm, whether specified in the text of
225	[Unicode] or in one of the Unicode
226	Standard Annexes, designates which data file(s) in the UCD are needed to
227	provide normative property information required by that algorithm.
228	
229	For information on the meaning and application of the terms,
230	normative, informative, contributory, and provisional, see Section 3.5,
231	Properties in [Unicode].
232	
233	For information about the applicable terms of use for the
234	UCD, see the Unicode Terms of Use.
235	
236	2.1 Simple and Derived Properties
237	
238	2.1.1 Simple Properties
239	
240	Some character properties in the UCD are simple properties.
241	This status has no bearing on whether or not the properties are
242	normative, but merely indicates that their values
243	are not derived from some combination of other properties.
244	
245	2.1.2 Derived Properties
246	
247	Other character properties are derived. This means that
248	their values are derived by rule from some other
249	combination of properties. Generally such rules are
250	stated as set operations, and may or may not include
251	explicit exception lists for individual characters.
252	
253	Certain simple properties are defined merely
254	to make the statement of the rule defining a derived
255	property more compact or general. Such properties are
256	known as contributory properties.
257	Sometimes these contributory properties are defined to
258	encapsulate the messiness inherent in exception
259	lists. At other times, a contributory property may
260	be defined to help stabilize the definition of
261	an important derived property which is subject to stability
262	guarantees.
263	
264	Derived character properties are not considered
265	second-class citizens among Unicode character properties.
266	They are defined to make implementation of important
267	algorithms easier to state. Included among the
268	first-class derived properties important for such
269	implementations are: Uppercase, Lowercase, XID_Start,
270	XID_Continue, Math, and Default_Ignorable_Code_Point, all
271	defined in DerivedCoreProperties.txt, as well as derived
272	properties for the optimization of normalization, defined
273	in DerivedNormalizationProps.txt.
274	
275	Implementations should simply use the derived properties,
276	and should not try to rederive them from lists of simple
277	properties and collections of rules, because of the
278	chances for error and divergence when doing so.
279	
280	Definitions of property derivations are provided
281	for information only, typically in comment fields
282	in the data files. Such definitions may be refactored,
283	refined, or corrected over time. These
284	definitions are presented in a modified set notation, expressed
285	as set additions and/or subtractions of various other property
286	values. For example:
287	
288	
289	
290	# Derived Property: ID_Start
291	# Characters that can start an identifier.
292	# Generated from:
293	# Lu + Ll + Lt + Lm + Lo + Nl
294	# + Other_ID_Start
295	# - Pattern_Syntax
296	# - Pattern_White_Space
297	
298	
299	
300	When interpreting definitions of derived properties
301	of this sort, keep in mind that set subtraction is not a commutative
302	operation. Thus "Lo + Lm - Pattern_Syntax" defines a different set
303	than "Lo - Pattern_Syntax + Lm". The order of property set operations
304	stated in the definitions affects the composition of
305	the derived set.
306	
307	If there are any cases of mismatches
308	between the definition of a derived property as
309	listed in DerivedCoreProperties.txt or similar data
310	files in the UCD, and the definition of a derived
311	property as a set definition rule, the explicit
312	listing in the data file should always be taken
313	as the normative definition of the property. As described
314	in Stability of Releases the property
315	listing in the data files for any given version
316	of the standard will never change for that version.
317	
318	2.1.3 Properties Dependent on External Specifications
319	
320	In limited cases, a Unicode character property defined in the Unicode Character Database
321	may have an external dependency on another specification which is not a part of the Unicode Standard,
322	and whose data is not formally part of the UCD. In such cases, version stability for the UCD is attained by
323	requiring that dependency to be based on a known, published version of the external specification.
324	
325	Starting with Version 10.0 of the UCD and continuing through Version 12.1,
326	the clear example of such an external dependency was the
327	derivation of some segmentation-related character properties, in part based on emoji properties associated with
328	UTS #51, "Unicode Emoji" [UTS51]. The details of the
329	derivation were described in the respective annexes, [UAX14]
330	and [UAX29], as well as in the documentation portions of
331	the associated UCD property files. See [Data14]
332	and [Props].
333	The version of UTS #51 used for those segmentation properties
334	in each of the relevant versions of the UCD was clearly
335	identified in those annexes and data files. Starting with
336	Version 13.0 of the UCD, however, the emoji properties which the UCD previously
337	depended on have been formally incorporated
338	into the UCD, so that they no longer constitute an external dependency.
339	
340	An external dependency may impact either a simple or a derived property.
341	
342	2.2 Use of Default Values
343	
344	Unicode character properties have default values. Default
345	values are the value or values that a character property takes
346	for an unassigned code point, or in some instances, for
347	designated subranges of code points, whether assigned or
348	unassigned. For example, the default value of a binary
349	Unicode character property is always "N".
350	
351	For the formal discussion of default values, see D26 in
352	Section 3.5, Properties in [Unicode].
353	For conventions related to default values in various data files
354	of the UCD and for documentation regarding the particular default values of
355	individual Unicode character properties, see Default Values.
356	
357	2.3 Stability of Releases
358	
359	Just as for the Unicode Standard as a whole, each version of the
360	UCD, once published, is absolutely stable and will never
361	change. Each released version is archived in a directory on
362	the Unicode website, with a directory number associated with
363	that version. URLs pointing to that version's directory are also
364	stable and will be maintained in perpetuity.
365	
366	Any errors discovered for a released version of the UCD
367	are noted in [Errata],
368	and if appropriate will be corrected in a subsequent
369	version of the UCD.
370	
371	Stability guarantees constraining how Unicode character
372	properties can (or cannot) change between releases of the UCD
373	are documented in the Unicode Consortium Stability
374	Policies [Stability].
375	
376	2.3.1 Changes to Properties Between Releases
377	
378	Updates to character properties in the Unicode Character Database may be required
379	for any of three reasons:
380	
381	
382	To cover new characters added to the standard
383	To add new character properties to the standard
384	To change the assigned values for a property for some characters already in the standard
385	
386	
387	While the Unicode Consortium endeavors to keep the values of all
388	character properties as stable as possible between versions, occasionally circumstances
389	may arise which require changing them. In particular, as less well-documented scripts, such
390	as those for minority languages, or historic scripts are added to the standard, the exact
391	character properties and behavior may not fully be known when the script is first encoded.
392	The properties for some of these characters may change as further information becomes
393	available or as implementations turn up problems in the initial property assignments.
394	As far as possible, any readjustment of property values based
395	on growing implementation experience is made to be compatible with established practice.
396	
397	All changes to normative or informative property values, to the status
398	or type of a property, or to property or property value aliases, must be approved by
399	an explicit decision taken by the Unicode Technical Committee. Changes to provisional
400	property values are subject to less stringent oversight.
401	
402	Occasionally, a character property value is changed to prevent incorrect generalizations
403	about a character's use based on its nominal property values. For example, U+200B ZERO
404	WIDTH SPACE was originally classified as a space character (General_Category=Zs), but
405	it was reclassified as a Format character (General_Category=Cf) to clearly distinguish it from space characters
406	in its function as a format control for line breaking.
407	
408	There is no guarantee that a particular value for an enumerated
409	property will actually have characters associated with it. Also, because of
410	changes in property value assignments between versions of the standard, a
411	property value that once had characters associated with it may later have none.
412	Such conditions and changes are rare, but implementations must not
413	assume that all property values are associated with non-null
414	sets of characters. For example, currently the special Script property
415	value Katakana_Or_Hiragana has no characters associated with it.
416	
417	2.3.2 Obsolete Properties
418	
419	An obsolete property is one whose original use
420	case no longer exists. The original use case may have been overtaken by other
421	developments, or the property may have been supplanted by a different property,
422	and so forth.
423	For example, the ISO_Comment property was once used to keep
424	track of annotations for characters used in the production of name lists for
425	ISO/IEC 10646 code charts. As of Unicode 5.2.0 that
426	functionality was dropped, and so the property became obsolete,
427	and its value is now defaulted to the null string for all Unicode code points.
428	
429	An obsolete property is never removed from the UCD.
430	
431	Obsolete properties are not recommended for use in APIs.
432	
433	2.3.3 Deprecated Properties
434	
435	Formally declaring
436	a property to be deprecated is an indication that the property is no longer recommended for
437	use, perhaps because its original intent has been replaced by another property
438	or because its specification was somehow defective. The general
439	practice of the UTC is to deprecate properties that have become obsolete, although
440	there may be exceptions.
441	See also the discussion of Deprecation.
442	
443	A deprecated property is never removed from the UCD.
444	
445	Deprecated properties are not recommended for use in APIs.

503	2.3.4 Stabilized Properties
504	
505	A stabilized
506	property is one for which the Unicode Technical Committee has declared that it will no longer actively maintain the property or extend it for newly
507	encoded characters. The property values of a
508	stabilized property are frozen as of a particular release of the standard.
509	
510	The stabilization of a property does not indicate that the property
511	should or should not be used. For example, if the property references a subset of
512	characters that is unaffected by future additions to the repertoire, it may be
513	stabilized without becoming useless. An example of a property which could
514	be stabilized without becoming useless is ASCII_Hex_Digit, as no more such
515	digits would ever be added to the standard.
516	
517	A stabilized property is never removed from the UCD.
518

542	2.3.5 Provisional Properties
543	
544	A provisional property has no stability guarantees. It may
545	be changed arbitrarily or may be removed altogether.
546	Table 9, Property Table does not list any provisional properties;
547	however, [UAX38] documents a large number of provisional properties
548	specified in the Unihan Database. [UAX60] documents additional provisional properties associated with East Asian ideographic scripts other than Han. [UAX57] documents additional provisional properties associated with Egyptian hieroglyphs. Provisional properties are used to collect
549	various information about characters for Han and other ideographic or hieroglyphic scripts, for review and testing. On occasion, a
550	provisional property's status may change to informatiive or normative, in which
551	case it then becomes subject to the same stability guarantees as other properties.
552	
553	A provisional property may be removed in any subsequent
554	version of the UCD.
555	
556	Provisional properties are not recommended for use in APIs.

558	3 Documentation
559	
560	This annex provides the core documentation for the UCD, but
561	additional information about character properties is available in
562	other parts of the standard and in additional documentation files
563	contained within the UCD.
564	
565	3.1 Character Properties in the Standard
566	
567	The formal definitions related to character properties used
568	by the Unicode Standard are documented in
569	Section 3.5, Properties in [Unicode].
570	Understanding those definitions and related terminology is
571	essential to the appropriate use of Unicode character properties.
572	
573	See Section 4.1, Unicode Character Database, in
574	[Unicode] for a general
575	discussion of the UCD and its use in defining properties. The
576	rest of Chapter 4 provides important explanations regarding
577	the meaning and use of various normative character properties.
578	
579	3.2 The Character Property Model
580	
581	For a general discussion of the property model which underlies
582	the definitions associated with the UCD, see
583	Unicode Technical Report #23, "The Unicode Character Property Model" [UTR23].
584	That technical report is informative, but over the years various
585	content from it has been incorporated into normative portions
586	of the Unicode Standard, particularly for the definitions in
587	Chapter 3.
588	
589	UTR #23 presents the important distinction
590	between properties defined for strings (in contrast to properties defined for
591	characters or code points) and character properties that have values that are strings.
592	The latter are referred to as string-valued properties in UTR #23
593	and in this annex. UTR #23 also discusses string functions and their relation to
594	character properties.
595	
596	3.3 NamesList.html
597	
598	NamesList.html formally describes the format of the NamesList.txt data file in BNF.
599	That data file is used to drive the PDF formatting
600	of the Unicode code charts and names list. See also Section 24.1,
601	Character Names List, in [Unicode]
602	for a detailed discussion of the conventions used in the Unicode names list as
603	formatted for the online code charts.
604	
605	3.4 StandardizedVariants.html
606	
607	StandardizedVariants.html has been obsoleted
608	as of Version 9.0 of the UCD. This file formerly
609	documented standardized variants, showing a
610	representative glyph for each. It was closely tied to the data file,
611	StandardizedVariants.txt, which defines those sequences normatively.
612	
613	The function of StandardizedVariants.html to show representative
614	glyphs for standardized variants has been superseded. There are now better means
615	of illustrating the glyphs. Many standardized variation sequences are shown
616	in the Unicode code charts directly, in summary sections at the ends of the
617	names list for any block which contains them. Glyphs for standardized variants
618	of CJK compatibility ideographs are also shown directly in the Unicode
619	code charts.
620	
621	3.5 Emoji Variation Sequences
622	
623	Emoji variation sequences are a special class of variation
624	sequences involving emoji characters. They are divided into two subtypes:
625	an emoji presentation sequence, consisting of an emoji character base followed
626	by the variation selector U+FE0F, and a text presentation sequence,
627	consisting of an emoji character base followed by the variation selector U+FE0E.
628	Such sequences come in pairs: the text presentation sequence shown
629	with a black and white presentation, as seen in the Unicode code charts,
630	and the emoji presentation sequence shown with a colorful icon, as
631	usually seen in implementations on mobile devices and elsewhere.
632	
633	Starting with Version 9.0.0, the following page in the Unicode emoji
634	subsite area shows appropriate representative glyphs for all emoji variation
635	sequences, with separate columns for text
636	presentation sequences and for emoji presentation sequences:
637	
638	https://www.unicode.org/emoji/charts/emoji-variants.html
639	
640	The data file which defines the exact list of emoji variation
641	sequences is emoji-variation-sequences.txt. That file is maintained in the
642	UCD, but emoji variation sequences are documented in
643	Unicode Technical Standard #51, Unicode Emoji
644	[UTS51].
645	
646	3.6 Unihan and UAX #38
647	
648	Unicode Standard Annex #38, "Unicode Han Database (Unihan)"
649	[UAX38] describes
650	the format and content of the Unihan Database [Unihan],
651	which collects together all property information
652	for CJK unified ideographs. That annex also specifies in detail
653	which of the Unihan character properties are normative,
654	informative, or provisional.
655	
656	The Unihan Database contains extensive and detailed mapping
657	information for CJK unified ideographs encoded in the Unicode Standard,
658	but it is aimed only at those ideographs, not at other characters used in the East
659	Asian context in general.
660	In contrast, East Asian legacy character sets, including important
661	commercial and national character set standards, contain many non-CJK
662	characters. As a result, the Unihan Database must be supplemented from
663	other sources to establish mapping tables for those character sets.
664	
665	The majority of the content of the Unihan Database is
666	released for each version of the Unicode Standard as a collection of Unihan data
667	files in the UCD. Because of their large size, these data files are released only as
668	a zipped file, Unihan.zip. The details of the particular data files in Unihan.zip
669	and the CJK properties each one contains are provided in [UAX38].
670	For versions of the UCD prior to Version 5.2.0, all of the CJK properties were
671	listed together in a very large, single file, Unihan.txt.
672	
673	3.7 UTC-Source Ideographs and UAX #45
674	
675	Unicode Standard Annex #45, "U-Source Ideographs"
676	[UAX45] describes the format of USourceData.txt,
677	which lists all of the information for UTC-Source ideographs.
678	
679	3.8 East Asian Scripts and UAX #60
680	
681	Unicode Standard Annex #60, "Data for East Asian Scripts"
682	[UAX60] describes the formats of TangutSources.txt,
683	NushuSources.txt, JurchenSources.txt, and SealSources.txt, which list all of the normative source information for those ideographic scripts. Those data files contain other
684	provisional property data specific to each of those scripts.
685	
686	3.9 Data File Comments
687	
688	In addition to the specific documentation files for the UCD, individual data
689	files often contain extensive header comments describing their content and any
690	special conventions used in the data.
691	
692	In some instances, individual property
693	definition sections also contain comments with information about how the property
694	may be derived. Such comments are informative; while they are intended
695	to convey the intent of the derivation, in case of any mismatch between
696	a statement of a derivation in a comment field and the actual
697	listing of the derived property, the list is considered to be definitive.
698	See Simple and Derived Properties.
699	
700	3.10 Obsolete Documentation Files
701	
702	UCD.html was formerly the primary documentation file for the UCD. As of Version 5.2.0, its
703	content has been wholly incorporated into this document.
704	
705	Unihan.html was formerly the primary documentation file for
706	the Unihan Database. As of Version 5.1.0, its
707	content has been wholly incorporated into [UAX38].
708	
709	Versions of the Unicode Standard
710	prior to Version 4.0.0 contained small, focused
711	documentation files, UnicodeCharacterDatabase.html, PropList.html, and
712	DerivedProperties.html, which were later consolidated into UCD.html.
713	
714	StandardizedVariants.html has been obsoleted as of Version 9.0.0.
715	See Section 3.4, StandardizedVariants.html.

717	4 Data Files
718	
719	Each release of the Unicode Standard and those of the Unicode Technical Standard (UTS) specifications which are version-synchronized with the Unicode Standard is accompanied by the publication of a large number of data files. Those data files define character properties, but also provide many other kinds of information used in the specification of various algorithms, as well as many kinds of test data.
720	
721	This section describes the structure of the versioned directory where those data files are published. It also describes how the UCD relates to other collections of properties and data files that are maintained in synchronization, but which are not part of the UCD proper. It describes the format conventions used in the data files, particularly for the data files that are part of the UCD. And it provides documentation for the UCD data files that are not documented elsewhere in this annex.
722	
723	4.1 Directory Structure
724	
725	The data files associated with each release are published in a numbered version directory under the Public directory on the Unicode website. The content of that numbered version directory is complete for that release. It is also stable—once published, all of the data files will be archived permanently in that directory, unchanged, located at a stable URL.
726	
727	Although all of the data files are version-specific for a release and most contain
728	internal date and version stamps, the file names of the released data files do not
729	differ from version to version. When linking to a version-specific data file, the
730	version will be indicated by the version number of the directory for the release.
731	
732	The specific files for this version of the Unicode Standard (18.0.0) and all the version-synchronized Unicode Technical Standards are located at:
733	
734	https://www.unicode.org/Public/18.0.0/
735	
736	
737	The latest released version of those data files is always accessible via the
738	following stable URL:
739	
740	https://www.unicode.org/Public/latest/
741	
742	
743	When draft versions of those data files have started their development cycle for a subsequent release, they can be found at the following stable URL:
744	
745	https://www.unicode.org/Public/draft/
746

844	4.1.1 UCD Files Proper
845	
846	The UCD proper is located in the ucd subdirectory of the numbered version directory for each release. That subdirectory contains all of the documentation files and most of the data files for the UCD, including some data files for derived properties.
847	
848	All files for derived extracted properties are in the extracted
849	subdirectory of the ucd subdirectory.
850	See Derived Extracted Properties for
851	documentation regarding those data files and their content.
852	
853	A number of auxiliary properties are specified in files in the auxiliary
854	subdirectory of the ucd subdirectory. It contains
855	data files specifying properties associated with
856	Unicode Standard Annex #29, "Unicode Text Segmentation" [UAX29]
857	and with
858	Unicode Standard Annex #14, "Unicode Line Breaking Algorithm" [UAX14],
859	as well as test data for those algorithms.
860	See Segmentation Test Files and Documentation
861	for more information about the test data.
862	
863	Certain data files associated with emoji properties are maintained
864	in the emoji subdirectory of the ucd subdirectory. Those data
865	files define the simple character properties associated with emoji characters,
866	as well as the emoji variation sequences. Other data files associated with
867	emoji, including those which define
868	the RGI ("recommended for general interchange") sets of various
869	types of emoji sequences, as well as emoji test data, are maintained elsewhere,
870	and are not considered formally a part of the UCD.
871	See [UTS51] for documentation regarding those data files and their content.
872	
873	Prior to Version 6.3.0, access to the latest released version
874	of the UCD was via the following stable URL:
875	
876	https://www.unicode.org/Public/UNIDATA/
877	
878	
879	That "UNIDATA" URL will be maintained, but is no longer recommended, because
880	it points to the ucd subdirectory of the latest release, rather than to the parent numbered version
881	directory for the release. The "UNIDATA" naming convention is also very old, and does not follow
882	the directory naming conventions currently used for other data releases in the
883	Public directory on the Unicode website.
884	
885	4.1.2 UCD XML Files
886	
887	The XML version of the UCD is located in the ucdxml subdirectory of the
888	numbered version directory. See the UCD in XML for
889	more details.

891	4.1.3 Charts
892	
893	The code charts specific to a version of Unicode are located in the charts subdirectory of the
894	numbered version directory. In addition to the collection of code charts there is also a single large PDF file that archives the full set in a single file. This directory also contains auxiliary charts which display collation, casing, and other information about characters. See the web page explaining the
895	Unicode Code Charts for
896	more details.

898	4.1.4 Beta Review Considerations
899	
900	Prior to the formal release of a version of the UCD, draft files
901	are made available for review in a subdirectory named draft, under the
902	/Public directory on the Unicode server. The files in this
903	directory may include temporary files, including documentation of differences between
904	draft versions. The number of reviews is not fixed—a beta review will
905	always take place, but an alpha review is optional.
906	
907	Notices contained in a ReadMe.txt file in the draft directory during the
908	beta review period also make it clear that that directory contains
909	preliminary material under review, rather than a final, stable release.

911	4.1.5 File Directory Differences for Early Releases
912	
913	The UCD in XML was introduced in Version 5.1.0,
914	so UCD directories prior to that do not contain the ucdxml subdirectory.
915	
916	UCD directories prior to Version 13.0.0 do not contain the emoji
917	subdirectory.
918	
919	UCD directories prior to Version 4.1.0 do not contain the auxiliary
920	subdirectory.
921	
922	UCD directories prior to Version 3.2.0 do not contain the extracted
923	subdirectory.
924	
925	The general structure of the file directory for a released version of the UCD
926	described above applies to Versions 4.1.0 and later. Prior to Version 4.1.0,
927	versions of the UCD were not self-contained, complete sets of data files
928	for that version, but instead only contained any new data files or any data files
929	which had changed since the prior release.
930	
931	Because of this, the property files for a given version
932	prior to Version 4.1.0 can be spread over several directories. Consult the
933	component listings at
934	Enumerated Versions
935	to find out which files in which directories comprise a complete set of data
936	files for that version.
937	
938	The directory naming conventions and the file naming conventions also
939	differed prior to Version 4.1.0. So, for example, Version 4.0.0 of the UCD
940	is contained in a directory named 4.0-Update, and Version 4.0.1 of
941	the UCD in a directory named 4.0-Update1. Furthermore, for these
942	earlier versions, the data file names do contain explicit version
943	numbers.

945	4.2 File Format Conventions
946	
947	Files in the UCD use the format conventions described in
948	this section, unless otherwise specified.
949	
950	4.2.1 Data Fields
951	
952	
953	Each line of data consists of fields separated by semicolons. The fields are numbered
954	starting with zero.
955	The first field (0) of each line in the Unicode Character Database files represents a code
956	point or range. The remaining fields (1..n) are properties associated with that code point.
957	Leading and trailing spaces within a field are not significant.
958	However, no leading or trailing spaces
959	are allowed in any field of UnicodeData.txt.
960	The Unihan data files [Unihan] in the UCD have a separate format, using tab characters
961	instead of semicolons to separate fields. See [UAX38]
962	for the detailed specification of the format of the Unihan data files. The
963	data files TangutSources.txt, NushuSources.txt, JurchenSources.txt, SealSources.txt, and Unikemet.txt also use this format.
964	
965	
966	4.2.2 Code Points and Sequences
967	
968	
969	Code points are expressed as hexadecimal numbers with four to six digits.
970	(See Appendix A, Notational Conventions in
971	[Unicode]
972	for a full, formal definition of this convention.)
973	They are written without the "U+" prefix in
974	all data files except the Unihan data files, the other data files associated with East Asian ideographic scripts, and Unikemet.txt. Those data files use the "U+" prefix for
975	all Unicode code points, to distinguish them from other decimal and hexadecimal
976	numerical references occurring in their data fields.
977	When a data field contains a sequence of code points, spaces separate
978	the code points.
979	
980	
981	
982	4.2.3 Code Point Ranges
983	
984	
985	A range of code points is specified by the form "X..Y".
986	Each code point in a range has the
987	associated property value specified on a data file. For example (from Blocks.txt):
988	
989	
990	0000..007F; Basic Latin
991	0080..00FF; Latin-1 Supplement
992	
993	
994	
995	
996	For backward compatibility, ranges in the file UnicodeData.txt
997	are specified by entries for the
998	start and end characters of the range, rather than by the form "X..Y".
999	The start character is indicated by a range identifier, followed by a comma
1000	and the string "First", in angle brackets. This entry takes the
1001	place of a regular character name in field 1 for that line.
1002	The end character is indicated on the next line with the same range identifier,
1003	followed by a comma and the string "Last", in angle brackets:
1004	
1005	
1006	
1007	4E00;<CJK Ideograph, First>;Lo;0;L;;;;;N;;;;;
1008	9FEF;<CJK Ideograph, Last>;Lo;0;L;;;;;N;;;;;
1009	
1010	
1011	For character ranges using this convention, the names of all characters in the range
1012	are algorithmically derivable.
1013	See Section 4.8, Name
1014	in [Unicode] for more information on
1015	derivation of character names for such ranges.
1016	
1017	
1018	4.2.4 Comments
1019	
1020	
1021	U+0023 NUMBER SIGN ("#") is used to indicate comments: all
1022	characters from the number sign to the end
1023	of the line are considered part of the comment, and are disregarded when parsing data.
1024	In many files, the comments on data
1025	lines use a common format, as illustrated here (from Scripts.txt):
1026	
1027	09B2 ; Bengali # Lo BENGALI LETTER LA
1028	
1029	
1030	The first part of a comment using this common format is the General_Category value,
1031	provided for information. This is followed by the character name for
1032	the code point in the first field (0).
1033	The printing of the General_Category value is suppressed in instances where
1034	it would be redundant, as for DerivedGeneralCategory.txt, in which the value
1035	of the property value in the data field is already the General_Category value.
1036	The symbol "L&"
1037	indicates characters of General_Category Lu, Ll, or Lt (uppercase, lowercase,
1038	or titlecase letter). For example:
1039	
1040	0386 ; Greek # L& GREEK CAPITAL LETTER ALPHA WITH TONOS
1041	
1042	L& as used in these comments is an alias for
1043	the derived LC value (cased letter) for the General_Category property, as documented in
1044	PropertyValueAliases.txt.
1045	When the data line contains a range of code points, this common format
1046	for a comment also indicates a range of character names, separated by "..", as
1047	illustrated here (from DerivedNumericType.txt):
1048	
1049	00BC..00BE ; Numeric # No [3] VULGAR FRACTION ONE QUARTER..VULGAR FRACTION THREE QUARTERS
1050	
1051	
1052	Normally, consecutive characters with the same property value would be
1053	represented by a single code point range. In data files using this
1054	comment convention, such ranges are subdivided so that all
1055	characters in a range also
1056	have the same General_Category value (or LC).
1057	While this convention results in more ranges than are strictly necessary, it
1058	makes the contents of the ranges clearer.
1059	When a code point range occurs, the number of items in the range is
1060	included in the comment (in square brackets), immediately following the General_Category value.
1061	The comments are purely informational, and may change format or be omitted in the
1062	future. They should not be parsed for content. However, see Section 4.2.10 @missing Conventions.
1063	
1064	
1065	4.2.5 Code Point Labels
1066	
1067	
1068	Surrogate code points, private-use characters, control codes, noncharacters,
1069	and unassigned code points have no names. When such code points are
1070	listed in the data files, for example to list their General_Category
1071	values, the comments use code point labels instead of character
1072	names. For example (from DerivedCoreProperties.txt):
1073	
1074	2065 ; Default_Ignorable_Code_Point # Cn <reserved-2065>
1075	
1076	
1077	Although code point labels are not formally character names
1078	and are not considered values of the Name property for characters, they are
1079	designed to be maintained as unique values within the namespace for Unicode
1080	character names. Hence, implementations can safely use them as identifiers
1081	for code points without overlap with actual character names.
1082	Code point labels use one of the tags as documented in

1084	in [Unicode] and as shown in Table 3,
1085	followed by "-" and the code point expressed in hexadecimal. The

1149	property value of "Y" (= True) are listed. For example (from PropList.txt):

1159	4.2.8 Multiple Values for Properties
1160	
1161	
1162	When a data file defines a property which may take multiple values for a single code
1163	point, the multiple values are expressed in a space-delimited list. For example (from ScriptExtensions.txt):
1164	
1165	
1166	0640 ; Adlm Arab Mand Mani Phlp Rohg Sogd Syrc # Lm ARABIC TATWEEL
1167	
1168	
1169	
1170	In some cases—but not all—the order of multiple elements in a space-delimited
1171	list may be significant. When the order of multiple elements is significant, it is documented
1172	along with the property itself. For example (from Unihan_Readings.txt), for the tag kMandarin,
1173	when there are two values for a code point, the first value is used to
1174	indicate a preferred pronunciation for zh-Hans (CN) and the second a
1175	preferred pronunciation for zh-Hant (TW).
1176	
1177	For further discussion, see Section 5.7.6 Properties Whose Values Are Sets of Values.
1178	
1179	
1180	4.2.9 Default Values
1181	
1182	
1183	Entries for a code point may be omitted in a data file if the
1184	code point has a default value for the property in question.
1185	
1186	For most string-valued properties,
1187	including the definition of foldings and mappings, the
1188	default value is the code point of the character itself.
1189	
1190	For some string-valued properties which define a property that
1191	applies primarily to a small, defined set of code points, the default
1192	value is <none>, which is interpreted as no value is defined. (This
1193	contrasts with specification of an actual value consisting of an
1194	empty string. See
1195	Section 4.2.11 Empty Fields.) Current examples include
1196	Bidi_Paired_Bracket, as well as some Unihan-related properties.
1197	
1198	For miscellaneous properties which take strings as values,
1199	such as the Unicode Name property, the default value is an empty
1200	string.
1201	
1202	For binary properties except for Extended_Pictographic,
1203	the default value is always "N" (= False)
1204	and is always omitted.
1205	
1206	For enumerated and catalog properties, the default value is listed in a comment. For
1207	example (from Scripts.txt):
1208	
1209	
1210	# All code points not explicitly listed for Script
1211	# have the value Unknown (Zzzz).
1212	
1213	
1214	
1215	
1216	A few properties of the enumerated type have multiple default values. In
1217	those cases, comments in the file explain the code point ranges for applicable values.
1218	See also Table 4.
1219	
1220	Default values are also listed in specially-formatted comment lines,
1221	using the keyword "@missing". Parsers which extract and process
1222	these lines can algorithmically determine the default values for all code points.
1223	See @missing Conventions
1224	for details about the syntax and use of these lines.
1225	
1226	
1227	Because of the legacy format constraints for UnicodeData.txt, that
1228	file contains no specific information about default values for properties.
1229	The default values for fields in UnicodeData.txt are documented
1230	in Table 4 below
1231	if they cannot be derived from the general rules about default values
1232	for properties.
1233	
1234	The file ArabicShaping.txt is also exceptional, because it omits the listing
1235	of many characters whose property value (jt=T) can be derived by rule. Adding an "@missing" line
1236	to that file would result in the wrong interpretation of Joining_Type values for omitted characters.
1237	The full explicit listing of Joining_Type values and the correct "@missing" line for
1238	the default Joining_Type value (jt=U) can be found in the file DerivedJoiningType.txt instead.
1239	The values of Joining_Type listed in DerivedJoiningType.txt should
1240	be taken as definitive, because of the difficulty of deriving the correct values for all
1241	characters based only on the entries in ArabicShaping.txt.

1328	4.2.9.1 Complex Default Values
1329	
1330	Complex default values are those which take multiple values, contingent on
1331	code point ranges or other conditions. Complex default values other than those specified in the
1332	"@missing" line are explicitly listed in the relevant property file, except for instances
1333	noted in this section. This means that a parser extracting property values from
1334	the UCD should never encounter an ambiguous condition for which the default value of a property
1335	for a particular code point is unclear.
1336	
1337	
1338	Bidi_Class: See
1339	Unicode Standard Annex #9, "Unicode Bidirectional Algorithm" [UAX9]
1340	and DerivedBidiClass.txt for full details.
1341	East_Asian_Width: This property defaults to Neutral for most code points, but defaults to Wide
1342	for unassigned code points in blocks associated with CJK ideographs.
1343	See Unicode Standard Annex #11, "East Asian Width"
1344	[UAX11] and
1345	EastAsianWidth.txt for documentation of the default values
1346	and DerivedEastAsianWidth.txt for the full listing of values.
1347	Line_Break: This property defaults to Unknown for most code points, but defaults to ID
1348	for unassigned code points in blocks associated with CJK ideographs, and
1349	in blocks in the ranges U+1F000..U+1FAFF
1350	and U+1FC00..U+1FFFD.
1351	The property defaults to PR for unassigned code
1352	points in the Currency Symbols block. See Unicode Standard Annex #14, "Unicode Line Breaking Algorithm"
1353	[UAX14]
1354	and LineBreak.txt for documentation of the default values
1355	and DerivedLineBreak.txt for the full listing of values.
1356	Extended_Pictographic: This property defaults to N (= False) for most code points, but defaults to
1357	Y (= True) for unassigned code points in blocks in the ranges U+1F000..U+1FAFF and U+1FC00..U+1FFFD.
1358	Those ranges are correlated with the ranges associated with default values for the Line_Break
1359	property, and have the same rationale. They help future-proof the behavior of Unicode segmentation
1360	algorithms for code point ranges most likely to be used for future assignment of new emoji characters.
1361	Vertical_Orientation: This property defaults to Rotated (R) for most code points,
1362	but defaults to Upright (U)
1363	for unassigned code points in blocks associated with scripts that are themselves predominantly
1364	Upright, in blocks for
1365	some notational systems, and in blocks predominantly associated with pictographic
1366	symbols and emoji.
1367	See Unicode Standard Annex #50, "Unicode Vertical Text Layout"
1368	[UAX50] and VerticalOrientation.txt for full details.

1371	4.2.10 @missing Conventions
1372	
1373	Specially-formatted comment lines with the keyword "@missing" are
1374	used to define default property values for ranges of code points not explicitly listed
1375	in a data file. These lines follow regular conventions that make them
1376	machine-readable.
1377	
1378	An @missing line starts with the comment character "#", followed by
1379	a space, then the "@missing" keyword, followed by a colon, another space, a code
1380	point range, and a semicolon. Then the
1381	line typically continues with a semicolon-delimited list of one or more
1382	default property values. For example:
1383	
1384	
1385	
1386	# @missing: 0000..10FFFF; Unknown
1387	
1388	
1389	
1390	In general, the code point range and semicolon-delimited list follow
1391	the same syntactic conventions as the data file in which the @missing line occurs, so
1392	that any parser which interprets that data file can easily be adapted to also
1393	parse and interpret an @missing line to pick up default property values for code points.
1394	
1395	@missing lines are also supplied for many properties in the file
1396	PropertyValueAliases.txt. In this case, because there are many @missing lines in that
1397	single data file, each @missing line in that file
1398	uses the syntactic pattern code_point_range; property_name; default_prop_val.
1399	
1400	An @missing line is never provided for a binary property, because the
1401	default value for binary properties is always "N" and need not be defined redundantly
1402	for each binary property.
1403	
1404	Because of the
1405	addition of property names when @missing lines are included in PropertyValueAliases.txt,
1406	there are currently two syntactic patterns used for @missing lines, as
1407	summarized schematically below:
1408	
1409	
1410	code_point_range; default_prop_val
1411	code_point_range; property_name; default_prop_val
1412	
1413	
1414	In this schematic representation, "default_prop_val" stands in for
1415	either an explicit property value or for a special tag such as <none> or
1416	<script>.
1417	
1418	Pattern #1 is used in most primary and derived UCD files. For example:
1419	
1420	
1421	
1422	# @missing: 0000..10FFFF; <none>
1423	
1424	
1425	
1426	Pattern #2 is used in PropertyValueAliases.txt and in
1427	DerivedNormalizationProps.txt, both of which contain values associated with many
1428	properties. For example:
1429	
1430	
1431	
1432	# @missing: 0000..10FFFF; NFD_QC; Yes
1433	
1434	
1435	
1436	The special tag values which may occur in the default_prop_val field
1437	in an @missing line are interpreted as follows:
1438	
1439	
1440	
1441	
1442	
1443	Tag
1444	Interpretation
1445	
1446	
1447	<none>
1448	no value is defined
1449	
1450	
1451	<code point>
1452	the string representation of the code point value
1453	
1454	
1455	<script>
1456	the value equal to the Script property value for this code point
1457	
1458	
1459	
1460	
1461	
1462	
1463	Starting with Version 15.0, some data files in the UCD may
1464	contain multiple @missing lines defined for the same property. When
1465	multiple @missing lines are defined this way, they are to be interpreted as
1466	follows: Each successive @missing line specifies an overriding range
1467	value for all previous @missing definitions. This convention allows a generic
1468	default value to be specified first for the entire Unicode code point range,
1469	followed by other specific default values for more constrained, specific
1470	sub-ranges. This enables an easy-to-understand and easy-to-maintain way of handling
1471	complex default values, as for the Bidi_Class or Line_Break properties.
1472	(See Complex Default Values.) The
1473	following simple example for East_Asian_Width, extracted from
1474	DerivedEastAsianWidth.txt, illustrates this mechanism:
1475	
1476	
1477	
1478	# @missing: 0000..10FFFF; Neutral
1479	# @missing: 3400..4DBF; Wide
1480	# @missing: 4E00..9FFF; Wide
1481	# @missing: F900..FAFF; Wide
1482	# @missing: 20000..2FFFD; Wide
1483	# @missing: 30000..3FFFD; Wide
1484	
1485	
1486	
1487	Implementation of parsing for multiple @missing lines for
1488	a single property is straightforward. Each time an @missing line is encountered,
1489	simply assign the given default value to the specified range. With this
1490	strategy, each successive @missing line will automatically override any
1491	prior assigned values for a given sub-range.
1492	
1493	4.2.11 Empty Fields
1494	
1495	The data file UnicodeData.txt defines many property values in each record. When a
1496	field in a data line for a code point is empty, that indicates that the property takes
1497	the default value for that code point. For example:
1498	
1499	
1500	
1501	0022;QUOTATION MARK;Po;0;ON;;;;;N;;;;;
1502	
1503	
1504	
1505	In that data line, the empty numeric fields indicate that the value of Numeric_Value for
1506	U+0022 is NaN and that the value of Numeric_Type is None. The empty case mapping fields indicate
1507	that the value of Simple_Uppercase_Mapping for U+0022 takes the default value, namely the
1508	code point itself, and so forth.
1509	
1510	The interpretation of empty fields in other data files of the UCD differs. In the
1511	case of data files which define string-valued properties,
1512	the omission of an entry for a code point
1513	indicates that the property takes the default value for that code point. However, if there
1514	is an entry for a code point, but the property value field for that entry is empty, that
1515	indicates that the property value is an explicit empty string (""). For example, the derived
1516	property NFKC_Casefold may map a code point to a sequence of code points, to a single different code
1517	point, to the same single code point, or to no code point at all (an empty string). See the following entries from
1518	the data file DerivedNormalizationProps.txt:
1519	
1520	
1521	
1522	00AA ; NFKC_CF; 0061 # Lo FEMININE ORDINAL INDICATOR
1523	00AD ; NFKC_CF; # Cf SOFT HYPHEN
1524	00AF ; NFKC_CF; 0020 0304 # Sk MACRON
1525	
1526	
1527	
1528	The empty field for U+00AD indicates that the property NFKC_Casefold maps SOFT HYPHEN
1529	to an empty string. By contrast, the absence of the entry for U+00AE in the data file indicates
1530	that the property NFKC_Casefold maps U+00AE REGISTERED SIGN to itself—the default value.
1531

1533	4.2.12 Text Encoding
1534	
1535	
1536	The data files use UTF-8. Unless otherwise noted, non-ASCII characters only
1537	appear in comments.
1538	The Unihan data files [Unihan] in the UCD make extensive use of UTF-8 in data fields.
1539	(See [UAX38] for details.)
1540	For legacy reasons, NamesList.txt was exceptional; it was encoded
1541	in Latin-1 prior to Unicode 6.2. For
1542	Unicode 6.2 and later, the encoding is UTF-8. See NamesList.html.
1543	Segmentation test data files, such as WordBreakTest.txt, make
1544	use of non-ASCII (UTF-8) characters as delimiters for data fields.
1545	
1546	
1547	4.2.13 Line Termination
1548	
1549	
1550	All data files in the UCD use LF line termination (not CRLF line termination).
1551	When copied to different systems, these line endings may be automatically changed to
1552	use the native line termination conventions for that system. Make sure your editor (or parser) can
1553	deal with the line termination
1554	style in the local copy of the data files.

1570	4.2.15 Other File Formats
1571	
1572	
1573	The data format for Unihan data files and for
1574	TangutSources.txt, NushuSources.txt, JurchenSources.txt, SealSources.txt, and Unikemet.txt
1575	in the UCD differs from the standard format.
1576	See the discussion of Unihan and UAX #38
1577	and East Asian Scripts and UAX #60 earlier in this annex for more information.
1578	The format for NamesList.txt, which documents the Unicode names
1579	list and which is used programmatically to drive the formatting
1580	program for Unicode code charts, also differs significantly from regular UCD data files.
1581	See NamesList.html
1582	Index.txt is another exception. It uses a tab-delimited format, with field 0
1583	consisting of an index entry string, and field 1 a code point. Index.txt is used to
1584	maintain the
1585	Unicode Character Name Index.
1586	The various segmentation test data files make use of "#" to delimit comments,
1587	but have distinct conventions for their data fields. See the documentation
1588	in their header sections for details of the data field formats for
1589	those files.
1590	The XML version of the UCD has its own file format conventions.
1591	In those files, "#" is used to stand for the code point in
1592	algorithmically derivable character names such as CJK UNIFIED IDEOGRAPH-4E00
1593	or TANGUT IDEOGRAPH-17000,
1594	so as to allow for name sharing in more compact representations of the data.
1595	See Unicode Standard Annex #42, "Unicode Character Database in XML"
1596	[UAX42] for details.

2117	example, the file NamedSequences.txt defines names (which are themselves string
2118	values) for a certain set of specific character sequences. Properties of strings
2119	are not explicitly listed for the UCD in the Property Table, and hence are given no
2120	specific type symbol in the Property Type Key.
2121	Numeric properties specify the actual numeric values
2122	for digits and other characters associated with numbers in some way.
2123	Miscellaneous properties are those properties that do not fit neatly into the other
2124	property categories; they currently include character names, comments about characters,
2125	the Script_Extensions property,
2126	and the Unicode_Radical_Stroke property
2127	(a combination of numeric values)
2128	documented in Unicode Standard Annex #38, "Unicode Han Database (Unihan)"
2129	[UAX38].

3380	5.3.1 Derivation of Indic_Conjunct_Break
3381	
3382	The derivation of the values for the Indic_Conjunct_Break (InCB) property
3383	is fairly complex. First the set of characters in the applicable scripts is defined.
3384	Then the values InCB=Linker and InCB=Consonant are defined by inclusion in that set
3385	and certain Indic_Syllabic_Category (InSC) values. Subsequently, the value InCB=Extend is
3386	defined by set subtraction and certain Grapheme_Cluster_Break (GCB) values. The resulting
3387	values for InCB are then used in the Grapheme Cluster Break algorithm, to get better break
3388	behavior for syllabic clusters in Indic scripts.
3389	
3390	In more detail, these steps are defined as follows:
3391	
3392	Define the set of scripts whose conjunct forms are created using
3393	a conjoiner with the property value InSC=Virama. This includes all the scripts that were defined for
3394	this set in Unicode 15.1 (and 16.0)—Bengali, Devanagari, Gujarati,
3395	Malayalam, Oriya, and Telugu—but also adding Balinese and Javanese starting with
3396	Unicode 17.0:
3397	
3398	
3399	viramaScripts = [ \p{scx=Bali} \p{scx=Beng} \p{scx=Deva} \p{scx=Gujr} \p{scx=Java} \p{scx=Mlym} \p{scx=Orya} \p{scx=Telu} ]
3400	
3401	
3402	Define the set of scripts whose conjunct forms are created using
3403	a conjoiner with the property value InSC=Invisible_Stacker. This consists of
3404	Chakma, Dives Akuru, Kawi, Kharoshthi, Khmer, Meetei Mayek, Myanmar, Soyombo,
3405	Sundanese, Tai Tham (Lanna), Tulu-Tigalari, and Zanabazar Square:
3406	
3407	
3408	invisibleStackerScripts = [ \p{scx=Cakm} \p{scx=Diak} \p{scx=Kawi} \p{scx=Khar} \p{scx=Khmr} \p{scx=Lana} \p{scx=Mtei} \p{scx=Mymr} \p{scx=Soyo} \p{scx=Sund} \p{scx=Tutg} \p{scx=Zanb} ]
3409	
3410	
3411	Note that \p{scx=𝑆} means the set of characters that have 𝑆 as one of their Script_Extensions values.
3412	
3413	Take the union of those two sets:
3414	
3415	
3416	conjunctLinkingScripts = [ viramaScripts invisibleStackerScripts ]
3417	
3418	
3419	Define the set of characters with InCB=Linker as those characters in the set conjunctLinkingScripts which have the Indic_Syllabic_Category values of Virama, Invisible_Stacker, or Consonant_With_Stacker:
3420	
3421	
3422	\p{InCB = Linker} ≔ [
3423	conjunctLinkingScripts &
3424	[ \p{Indic_Syllabic_Category=Virama} \p{Indic_Syllabic_Category=Invisible_Stacker} \p{Indic_Syllabic_Category=Consonant_With_Stacker} ]
3425	]
3426	
3427	
3428	Define the set of characters with InCB=Consonant as those characters in the set conjunctLinkingScripts which have the Indic_Syllabic_Category value of Consonant, as well as those characters in the invisibleStackerScripts which have the Indic_Syllabic_Category value of Vowel_Independent, plus two exceptional Balinese characters which also take conjunct forms:
3429	
3430	
3431	\p{InCB = Consonant} ≔ [
3432	[ conjunctLinkingScripts & \p{Indic_Syllabic_Category=Consonant} ]
3433	[ invisibleStackerScripts & \p{Indic_Syllabic_Category=Vowel_Independent} ]
3434	[ \u1B0B \u1B0C ]
3435	]
3436	
3437	
3438	Define the set of characters with InCB=Extend by taking the set of characters with Grapheme_Cluster_Break = Extend and subtracting those characters just determined to have either InCB = Linker or InCB = Consonant values (plus some other minor adjustments for ZWJ and ZWNJ):
3439	
3440	
3441	\p{InCB = Extend} ≔ [
3442	\p{gcb=Extend}
3443	\p{gcb=ZWJ}
3444	- \p{InCB=Linker}
3445	- \p{InCB=Consonant}
3446	- [\u200C]
3447	]
3448	
3449	
3450	The default value for InCB is None, which applies to all other characters:
3451	
3452	
3453	\p{InCB = None} ≔ [
3454	[ \x{0000} - \x{10FFFF} ]
3455	- \p{InCB = Linker}
3456	- \p{InCB = Consonant}
3457	- \p{InCB = Extend}
3458	]

3589	characters listed in the Unihan data files.
3590	
3591	Numeric_Type is extracted as follows. If fields 6, 7, and 8 in UnicodeData.txt
3592	are all non-empty, then Numeric_Type=Decimal. Otherwise, if fields 7 and 8 are both
3593	non-empty, then Numeric_Type=Digit. Otherwise, if field 8 is non-empty, then
3594	Numeric_Type=Numeric.
3595	For characters listed in the Unihan data files,
3596	Numeric_Type=Numeric for characters that have kPrimaryNumeric, kAccountingNumeric,
3597	or kOtherNumeric tags. The default value is Numeric_Type=None.

3599	The listing of Joining_Type in DerivedJoiningType.txt should be considered
3600	as definitive, because of the complexity of trying to derive the correct values directly
3601	from field 2 of ArabicShaping.txt.

3603	5.5 Contributory Properties
3604	
3605	Contributory properties contain sets of exceptions used in the generation of
3606	other properties derived from them. The contributory properties specifically concerned with
3607	identifiers and casing contribute to the maintenance of
3608	stability guarantees for properties and/or to invariance relationships
3609	between related properties. Other contributory properties are simply
3610	defined as a convenience for property derivation.
3611	
3612	Most contributory properties have names using
3613	the pattern "Other_XXX" and are used to derive the corresponding "XXX" property.
3614	For example, the Other_Alphabetic property is used in the derivation of the Alphabetic
3615	property.
3616	
3617	Contributory properties are typically defined in
3618	PropList.txt and the corresponding derived property
3619	is then listed in
3620	DerivedCoreProperties.txt.
3621	
3622	Jamo_Short_Name is an unusual contributory
3623	property, both in terms of its name and how it is used. It is defined in
3624	its own property file, Jamo.txt, and is used to derive the Name
3625	property value for Hangul syllable characters, according to the rules
3626	spelled out in Section 3.12, Conjoining Jamo Behavior in
3627	[Unicode].
3628	
3629	Contributory is considered to be a distinct status for a Unicode
3630	character property. Contributory properties are neither normative nor
3631	informative. This distinct status is marked with
3632	the symbol "C" in the status column in the property table.

3825	5.7.1 General Category Values
3826	
3827	The General_Category property of a code point provides for the
3828	most general classification of that code point. It is usually
3829	determined based on the primary characteristic of the assigned
3830	character for that code point. For example, is the character a letter,
3831	a mark, a number, punctuation, or a symbol, and if so, of what
3832	type? Other General_Category values define the classification of
3833	code points which are not assigned to regular graphic characters,
3834	including such statuses as private-use, control, surrogate code
3835	point, and reserved unassigned.
3836	
3837	Many characters have multiple uses, and not all such cases
3838	can be captured entirely by the General_Category value. For example,
3839	the General_Category value of Latin, Greek, or Hebrew letters does not
3840	attempt to cover (or preclude) the numerical use of such letters
3841	as Roman numerals or in other numerary systems. Conversely, the
3842	General_Category of ASCII digits 0..9 as Nd (decimal digit)
3843	neither attempts to cover (or preclude) the occasional use of
3844	these digits as letters in various orthographies. The General_Category
3845	is simply the first-order, most usual categorization of a
3846	character.
3847	
3848	For more information about the General_Category
3849	property, see Chapter 4, Character Properties in [Unicode].

4271	5.7.3 Character Decomposition Mapping
4272	
4273	The value of the Decomposition_Mapping property for a character is provided
4274	in field 5 of UnicodeData.txt. This is a string-valued property, consisting of a sequence
4275	of one or more Unicode code points. The default value of the Decomposition_Mapping
4276	property is the code point of the character itself. The use of the default value
4277	for a character is indicated by leaving field 5 empty in UnicodeData.txt.
4278	Informally, the value of the Decomposition_Mapping property for a character
4279	is known simply as its decomposition mapping. When a character's decomposition
4280	mapping is other than the default value, the decomposition mapping is printed out
4281	explicitly in the names list for the Unicode code charts.
4282	
4283	The prefixed tags supplied with a subset of the decomposition mappings generally indicate formatting
4284	information. Where no such tag is given, the mapping is canonical. Conversely, the presence of a
4285	formatting tag also indicates that the mapping is a compatibility mapping and not a canonical
4286	mapping. In the absence of other formatting information in a compatibility mapping, the tag is
4287	used to distinguish it from canonical mappings.
4288	
4289	In some instances a canonical mapping or a compatibility mapping may consist of a single
4290	character. For a canonical mapping, this indicates that the character is a canonical equivalent of
4291	another single character. For a compatibility mapping, this indicates that the character is a
4292	compatibility equivalent of another single character.
4293	
4294	A canonical mapping may also consist of a pair of characters, but is never
4295	longer than two characters. When a canonical mapping consists of a pair of characters,
4296	the first character may itself be a character with a decomposition mapping, but the
4297	second character never has a decomposition mapping.
4298	
4299	Compatibility mappings can be much longer than canonical mappings. For historical reasons, the
4300	longest compatibility mapping is 18 characters long. Compatibility mappings are guaranteed
4301	to be no longer than 18 characters, although most consist of just a few characters.

4384	values (mappings) are defined in UnicodeData.txt, while the decomposition (also termed "full
4385	decomposition") is defined in Section 3.7, Decomposition in
4386	[Unicode] to use those mappings recursively.
4387	
4388	
4389	The canonical decomposition is formed by recursively applying the canonical mappings, then
4390	applying the Canonical Ordering Algorithm.
4391	The compatibility decomposition is formed by recursively applying the canonical and
4392	compatibility mappings, then applying the Canonical Ordering Algorithm.
4393	
4394	
4395	Starting from Unicode 2.1.9, the decomposition mappings in
4396	UnicodeData.txt can be used to derive the
4397	full decomposition of any single character in canonical order, without
4398	the need to separately apply the Canonical Ordering Algorithm.
4399	However, canonical ordering of combining character sequences must still be applied
4400	in decomposition when normalizing source text which contains any combining marks.
4401	
4402	The normalization of Hangul conjoining jamos and of Hangul syllables depends on algorithmic
4403	mapping, as specified in Section 3.12, Conjoining Jamo Behavior in
4404	[Unicode].
4405	That algorithm specifies the full decomposition of all precomposed Hangul syllables, but
4406	effectively it is equivalent to the recursive application of pairwise decomposition
4407	mappings, as for all other Unicode characters. Formally, the Decomposition_Mapping
4408	property value for a Hangul syllable is the pairwise decomposition and not the full
4409	decomposition.
4410	
4411	Each character with the Hangul_Syllable_Type
4412	value LVT will have a Decomposition_Mapping consisting of a character with an LV value and a
4413	character with a T value. Thus for U+CE31 the Decomposition_Mapping is <U+CE20, U+11B8>,
4414	rather than <U+110E, U+1173, U+11B8>.
4415	
4416	The Unihan property kCompatibilityVariant consists of a listing of the
4417	canonical Decomposition_Mapping property values just for CJK compatibility ideographs. Because its values are
4418	derived from UnicodeData.txt, it is formally considered to be a derived property. The exact statement
4419	of the derivation for kCompatibilityVariant is listed in Unicode Standard Annex #38, "Unicode Han Database (Unihan)"
4420	[UAX38].

4710	5.7.6 Properties Whose Values Are Sets of Values
4711	
4712	Most properties have a single value associated with each code point.
4713	However, some properties may instead associate a set of multiple
4714	different values with each code point. For example, the provisional
4715	kVietnamese property, which lists Vietnamese pronunciations
4716	for unified CJK ideographs, has values which consist of a set of
4717	zero or more pronunciation strings. Thus, the Unihan
4718	Database contains an entry:
4719	
4720	
4721	
4722	U+6258 kVietnamese thác thách thốc thước thướt
4723	
4724	
4725	
4726	This line is to be interpreted as associating a set of
4727	five string values, {"thác", "thách", "thốc", "thước", "thướt"} with the kVietnamese property
4728	for U+6258.
4729	
4730	Similarly, the Script_Extensions property has values which
4731	consist of a set of one or more Script property values. Thus the
4732	property file ScriptExtensions.txt in the UCD contains an entry:
4733	
4734	
4735	
4736	0640 ; Adlm Arab Mand Mani Phlp Rohg Sogd Syrc # Lm ARABIC TATWEEL
4737	
4738	
4739	
4740	This line is to be interpreted as associating a set of
4741	eight enumerated
4742	Script property values, {Adlm, Arab, Mand, Mani, Phlp, Rohg, Sogd, Syrc}, with the Script_Extensions
4743	property for U+0640.
4744	
4745	In the case of Script_Extensions, in particular, the set of sets which
4746	constitute meaningful values of the property is relatively small, and could be explicitly
4747	evaluated for any particular Unicode version. For example:
4748	
4749	
4750	
4751	{{Adlm, Arab, Mand, Mani, Phlp, Rohg, Sogd, Syrc}, {Arab, Copt}, {Arab, Rohg}, {Arab, Syrc}, {Arab, Thaa}, {Arab, Syrc, Thaa}, {Armn, Geor}, ...}
4752	
4753	
4754	
4755	However, an enumeration of this set of set values is unlikely to be
4756	of much implementation value, and would be likely to change significantly between
4757	versions of the standard. In other cases, such as for properties defining pronunciation
4758	readings for unified CJK ideographs, these sets of sets are completely open-ended, and there
4759	is no point to attempting to provide explicit enumerations of such sets in the UCD.
4760	
4761	The order of the element values in such sets may or may not be significant.
4762	For example, the order among the element values for kCantonese and for
4763	Script_Extensions is not significant. By way of contrast, when the kMandarin
4764	property shows two values for a code point, the first value is used to
4765	indicate a preferred pronunciation for zh-Hans (CN) and the second a
4766	preferred pronunciation for zh-Hant (TW).
4767	
4768	For data file format considerations regarding properties which take
4769	sets of values, see Section 4.2.8 Multiple Values for Properties.
4770	For considerations regarding validation of such
4771	properties, see Section 5.11.5 Validation of Multivalued Properties.
4772	See also Unicode Technical Standard #18, "Unicode Regular Expressions"
4773	[UTS18] for a discussion of how to handle
4774	such properties when processing regular expressions.

4777	
4778	Both Unicode character properties themselves and their values are
4779	given symbolic aliases. The formal lists of aliases are provided so that
4780	well-defined symbolic values are available for XML formats of the UCD
4781	data, for regular expression property tests, and for other
4782	programmatic textual descriptions of Unicode data.
4783	The aliases for properties are defined in
4784	PropertyAliases.txt. The aliases for property values are defined in
4785	PropertyValueAliases.txt.
4786	
4787	Table 17. Alias Files in the UCD
4788	
4789

4809	Aliases are defined as ASCII-compatible identifiers, using only uppercase or
4810	lowercase A-Z, digits, and underscore "_". Case is not significant
4811	when comparing aliases, but the preferred form used in the data files
4812	for longer aliases is to titlecase them for clarity. Once a
4813	particular alias is defined in the data files, its spelling is stable
4814	and will not be updated in future versions. See
4815	Alias Stability Policy. This stability guarantee makes it possible to use property aliases and
4816	property value aliases as stable identifiers.
4817	
4818	Each entry in PropertyAliases.txt and PropertyValueAliases.txt
4819	contains at least two entries for aliases, and may contain more. The first two entries have a
4820	special status as the preferred aliases. The first of the two preferred aliases
4821	is typically a short or abbreviated form, while the second is a longer, more formal
4822	alias, often treated as the official designation of the property or property value
4823	in documentation.
4824	
4825	In some cases, the entries for preferred aliases may contain
4826	identical strings. Formally, this is considered to be a single alias entered
4827	twice in the data file, rather than two distinct aliases. Contrast, for example, the
4828	entries for the General_Category property and the Emoji property in PropertyAliases.txt:
4829	
4830	
4831	gc ; General_Category
4832	Emoji ; Emoji
4833	
4834	
4835	In such cases, a future revision of the UCD may introduce a new, distinct alias.
4836	The new, distinct alias would then replace either one of the two occurrences of the single alias.
4837	
4838	The purpose of alias stability is to permanently reserve the relation between any specific alias and the property or property value it refers to. This guarantees that regular expressions or API calls that use a given alias will continue to succeed.
4839	However, there is no guarantee as to the exact order of occurrence of that
4840	alias in the data line in PropertyAliases.txt or PropertyValueAliases.txt.
4841	A new alias may be introduced, displacing an existing value
4842	from the first or second position to a later position in the line. This means
4843	that implementations parsing these data files for aliases must not assume immutability of the
4844	string for an alias in a particular field of the data lines. Alias stability applies
4845	rather to the complete set of aliases defined on each data line.
4846	
4847	Aliases may be translated in appropriate environments, and additional
4848	aliases may be useful in certain contexts. There is no requirement that
4849	only the aliases defined in the alias files of the UCD be used when
4850	referring to Unicode character properties or their values; however, their
4851	use is recommended for interoperability in data formats or in
4852	programmatic contexts.
4853	
4854	Aliases may be provided
4855	for provisional properties. There are stability guarantees for property aliases and property
4856	value aliases, but no stability guarantees for provisional properties or other
4857	provisional data files; consequently, there can also be
4858	no stability guarantee for property aliases or property value aliases associated with provisional
4859	properties.
4860	
4861	5.8.1 Property Aliases
4862	
4863	In PropertyAliases.txt, the first field typically specifies an abbreviated
4864	symbolic name for the property, and the second field specifies the
4865	long symbolic name for the property. These are the preferred aliases.
4866	Additional aliases for a few properties are specified in the third
4867	or subsequent fields.
4868	
4869	Aliases for normative and informative
4870	properties defined in the Unihan data files are included in PropertyAliases.txt,
4871	beginning with Version 5.2.
4872	
4873	The long symbolic name alias is self-descriptive, and is
4874	treated as the official name of
4875	a Unicode character property. For clarity it is used whenever possible
4876	when referring to that
4877	property in this annex and elsewhere in the Unicode Standard.
4878	For example: "The Line_Break property is discussed in Unicode Standard Annex #14, "Unicode Line
4879	Breaking Algorithm" [UAX14]."
4880	
4881	The abbreviated symbolic name alias is usually short and less mnemonic,
4882	but is useful for expressions such as "lb=BA" in data or in other
4883	contexts where the meaning is clear. Note that although
4884	the UCD documentation refers to this first symbolic name alias as "abbreviated", there
4885	is no requirement that the first field be an actual abbreviation or even that
4886	it be shorter than the "long" symbolic name alias. If the long symbolic name alias is
4887	already a short identifier, in many cases the "abbreviated" symbolic name alias is
4888	identical to the value in the second field. There is also one principled class where the
4889	"abbreviated" field is actually longer than the "long" field—the property aliases
4890	for the Unihan tags. In that case, the second field deliberately matches the Unihan
4891	tags exactly, so that it can serve its function as being the official property value
4892	identifier. Then, because there was no systematic way to abbreviate Unihan tags, while
4893	still retaining any reasonable comprehensibility for them, the first field in
4894	PropertyAliases.txt was created by systematically prefixing "cj" to each Unihan tag, resulting
4895	in labels with the mnemonic "cjk" prefix. Thus it is not a mistake that in such
4896	cases the first field contains a longer string than the second field. Implementations
4897	should not build in assumptions about the relative length of these symbolic name aliases.
4898	
4899	The property aliases specified in PropertyAliases.txt constitute
4900	a unique namespace. When using these symbolic values, no
4901	alias for one property will match an alias for another property.
4902

4906	abbreviated alias for a Unicode property, the second field specifies
4907	an abbreviated symbolic name for a value of that property, and
4908	the third field specifies the
4909	long symbolic name for that value of that property. These are the
4910	preferred aliases.
4911	Additional aliases for some property values may be specified in the fourth
4912	or subsequent fields. For example, for binary properties, the
4913	abbreviated alias for the True value is "Y", and the long alias
4914	is "Yes", but each entry also specifies "T" and "True" as
4915	additional aliases for that value, as shown in Table 18.

4942	properties, which have well-defined, enumerated values. It does not
4943	make sense to specify property value aliases, for example, for
4944	the Numeric_Value property, whose value could be any number, or
4945	for a string-valued property such as Simple_Lowercase_Mapping, whose values
4946	are mappings from one code point to another.

4948	The Canonical_Combining_Class property requires special handling
4949	in PropertyValueAliases.txt. The values of this property are numeric,
4950	but they comprise a closed, enumerated set of values. The more
4951	important of those values are given symbolic name aliases.

4964	Taken by themselves, property value aliases do not constitute
4965	a unique namespace. The abbreviated aliases, in particular,
4966	are often re-used as aliases for values for different properties.
4967	All of the binary property value aliases, for example, make
4968	use of the same "Y", "Yes", "T", "True" symbols. Property value
4969	aliases may also overlap the symbols used for property aliases.
4970	For example, "Sc" is the abbreviated alias for the
4971	"Currency_Symbol" value of the General_Category property, but
4972	it is also the abbreviated alias for the Script property.
4973	However, the aliases for values for any single property are
4974	always unique within the context of that property. That
4975	means that expressions that combine a property alias and
4976	a property value alias, such as "lb=BA" or "gc=Sc" always
4977	refer unambiguously just to one value of one given property,
4978	and will not match any other value of any other property.
4979	
4980	Prior to Version 6.1.0, the property value alias entries for three properties,
4981	Age, Block, and Joining_Group, made use of a special metavalue
4982	"n/a" in the field for the abbreviated alias. This should
4983	be understood as meaning that no abbreviated alias was
4984	defined for that value for that property, rather than as
4985	an alias per se. Starting with Version 6.1.0, all property values for those
4986	three properties have abbreviated aliases, so there is no current use of the "n/a" metavalue.
4987	
4988	In a few cases, because of longstanding legacy practice
4989	in referring to values of a property by short identifiers,
4990	the abbreviated alias and the long alias are the same. Examples include some property value aliases
4991	for the Line_Break property and the Grapheme_Cluster_Break
4992	property. In a number of other cases,
4993	there is no need for short or abbreviated
4994	aliases distinct from longer aliases, so no abbreviations have
4995	been introduced. Examples include property value aliases associated
4996	with the Indic_Positional_Category, Indic_Syllabic_Category, and
4997	the Jamo_Short_Name properties.
4998	
4999	The property Script_Extensions
5000	consists of enumerated sets of Script property values. The set of those sets is potentially
5001	open-ended, and no property value aliases are defined for them.

5003	5.9 Matching Rules
5004	
5005	When matching Unicode character property names
5006	and values, it is strongly recommended that all
5007	Property and Property Value Aliases
5008	be recognized. For best results in matching, rather than using
5009	exact binary comparisons, the following loose matching rules
5010	should be observed.
5011	
5012	5.9.1 Matching Numeric Property Values
5013	For all numeric properties, and for properties such as Unicode_Radical_Stroke
5014	which are constructed from combinations
5015	of numeric values, use loose matching rule UAX44-LM1 when comparing property values.
5016	
5017	UAX44-LM1. Apply numeric equivalences.
5018	
5019	"01.00" is equivalent to "1".
5020	"1.666667" in the UCD is a repeating fraction, and
5021	equivalent to "10/6" or "5/3".
5022	
5023	
5024	5.9.2 Matching Character Names
5025	Unicode character names constitute a special case. Formally, they are values
5026	of the Name property. While each Unicode character name for an assigned character
5027	is guaranteed to be unique, names are assigned in such a way that
5028	the presence or absence of spaces cannot be used to distinguish them.
5029	Furthermore, implementations sometimes create identifiers from Unicode
5030	character names by inserting underscores for spaces. For best results
5031	in comparing Unicode character names, use loose matching rule UAX44-LM2.
5032	
5033	UAX44-LM2. Ignore case, whitespace, underscore ('_'), and all medial hyphens except the hyphen in
5034	U+1180 HANGUL JUNGSEONG O-E.
5035	
5036	"zero-width space" is equivalent to "ZERO WIDTH SPACE" or "zerowidthspace"
5037	"character -a" is not equivalent to "character a"
5038	
5039	
5040	In this rule "medial hyphen" is to be construed as a hyphen
5041	occurring immediately between two
5042	alphanumeric characters [A..Z, 0..9] in the normative Unicode character
5043	name, as published in the Unicode names list in the UCD, and not to any hyphen that may
5044	transiently occur medially as a result of removing whitespace before removing hyphens in
5045	a particular implementation of matching.
5046	(See Section 4.8, Name in
5047	[Unicode] for the normative
5048	specification of the Unicode Name property and of name uniqueness.)
5049	
5050	Thus the hyphens in the following examples of character names are medial,
5051	and should be ignored in loose matching:
5052	
5053	
5054	U+10089 LINEAR B IDEOGRAM B107M HE-GOAT
5055	U+2F800 CJK COMPATIBILITY IDEOGRAPH-2F800
5056	U+1FB23 BLOCK SEXTANT-136
5057	U+10749 LINEAR A SIGN A709-2 L2
5058	U+1F090 DOMINO TILE VERTICAL-06-03
5059	
5060	
5061	In contrast, the hyphens in the following examples of character
5062	names are not medial, and should not be ignored in loose matching.
5063	
5064	
5065	U+0F39 TIBETAN MARK TSA -PHRU
5066	U+11C88 MARCHEN LETTER -A
5067	
5068	
5069	An implementation of this loose matching rule can obtain
5070	the correct results when comparing two strings by doing the following three
5071	operations, in order:
5072	
5073	
5074	remove all medial hyphens (except the medial hyphen in the name for U+1180)
5075	remove all whitespace and underscore characters
5076	apply toLowercase() to both strings
5077	
5078	
5079	After applying these three operations, if the two strings
5080	compare binary equal, then they are considered to match.
5081	
5082	This is a logical statement of how the rule works. If programmed
5083	carefully, an implementation of the matching rule can transform the strings in
5084	a single pass. It is also possible to compare two name strings for loose matching
5085	while transforming each string incrementally.
5086	
5087	Loose matching rule UAX44-LM2 is also appropriate for matching
5088	character name aliases, the names of named character sequences, and code point labels, which all share the
5089	unique namespace (and matching behavior) of Unicode character names. See Section 4.8, Name in
5090	[Unicode]
5091	
5092	Examples of medial hyphens in character name aliases include:
5093	
5094	
5095	U+008E SINGLE-SHIFT-2
5096	U+11EC HANGUL JONGSEONG YESIEUNG-KIYEOK
5097	
5098	
5099	Examples of non-medial hyphens in character name aliases include:
5100	
5101	
5102	U+0FD0 TIBETAN MARK BKA- SHOG GI MGO RGYAN
5103	
5104	
5105	Examples of medial hyphens in named character sequences include:
5106	
5107	
5108	MODIFIER LETTER EXTRA-HIGH EXTRA-LOW CONTOUR TONE BAR;02E5 02E9
5109	
5110	
5111	
5112	
5113	Implementations of name matching should use extreme care when matching
5114	non-standard, alternative names for particular characters. The Name Uniqueness Policy
5115	in the Unicode Consortium Stability
5116	Policies [Stability] guarantees that
5117	the Unicode Standard will never add a character whose name would match an existing
5118	encoded character, according to matching rule UAX44-LM2. However, any other
5119	name for a character might be used in the future.
5120	
5121	The following is a concrete example of the kind of trouble that can occur.
5122	Prior to Unicode 6.0 some implementations of regex allowed matching of the name "BELL" for
5123	the control code U+0007. When Unicode 6.0 added a different encoded character,
5124	U+1F514 BELL for emoji symbols, those regex implementations broke.
5125	
5126	As of Version 6.1 of the Unicode Standard, the most commonly occurring
5127	alternative names for control codes, as well as many commonly used abbreviations for
5128	Unicode format characters, have been added as character name aliases. This automatically
5129	excludes all such alternative names and abbreviations from the potential pool for
5130	future Unicode character names, because name uniqueness is defined over the namespace
5131	which includes both character names and character name aliases. That exclusion should
5132	reduce the potential for surprises similar to the "BELL" case, where implementers
5133	assume that a name for a control code is already well-defined.
5134	
5135	5.9.3 Matching Symbolic Values
5136	Property aliases and property value aliases are symbolic values. When
5137	comparing them, use loose matching rule UAX44-LM3.
5138	
5139	UAX44-LM3. Ignore case, whitespace, underscore ('_'),
5140	hyphens, and any initial prefix string "is".
5141	
5142	"linebreak" is equivalent to "Line_Break" or "Line-break"
5143	"lb=BA" is equivalent to "lb=ba" or "LB=BA"
5144	"Script=Greek" is equivalent to "Script=isGreek" or "Script=Is_Greek"
5145	
5146	
5147	Loose matching is generally appropriate for the property values of
5148	Catalog, Enumeration, and Binary properties, which have symbolic aliases
5149	defined for their values.
5150	Loose matching should not be done for the property values of String-valued properties,
5151	which do not have symbolic aliases defined for their values; exact
5152	matching for String-valued property values is important, as
5153	case distinctions or other distinctions in those values may be significant.
5154	
5155	For loose matching of symbolic values, an initial prefix string "is" is
5156	ignored. The reason for this is that APIs returning property values are often
5157	named using the convention of prefixing "is" (or "Is" or "Is_", and so forth) to
5158	a property value. Ignoring any initial "is" on a symbolic value during loose
5159	matching is likely to produce the best results in application areas such as
5160	regex. Removal of an initial "is" string for a loose matching comparison only
5161	needs to be done once for a symbolic value, and need not be tested recursively.
5162	There are no property aliases or property value aliases of the form
5163	"isisisisistooconvoluted" defined just to test implementation edge cases.
5164	
5165	Existing and future property aliases and property value
5166	aliases are guaranteed to be unique within their relevant namespaces, even
5167	if an initial prefix string "is" is ignored. The existing cases of note
5168	for aliases that do start with "is" are: dt=Iso (Decomposition_Type=Isolated)
5169	and lb=IS. The Decomposition_Type value alias does not cause any problem,
5170	because there is no contrasting value alias dt=o (Decomposition_Type=olated).
5171	For lb=IS, note that the "IS" is the entire property value alias, and
5172	is not a prefix. There is no null value for the Line_Break property for it
5173	to contrast with, but implementations of loose matching should be careful
5174	of this edge case, so that "lb=IS" is not misinterpreted as matching a null
5175	value.
5176	
5177	There is one other edge case involving the interaction
5178	of an "is" prefix string with loose matching. The short property alias
5179	for the string-valued property Iso_Comment is "isc". An implementation that is using
5180	loose matching and using an abbreviatory convention for General_Category
5181	values, taking "isLu", "isPo", "isNd", etc., to stand for particular
5182	property value aliases, might end up interpreting "isc" as equivalent
5183	to "isC", intended instead as meaning General_Category=Other (gc=C).
5184	Appropriate caution is advised.
5185	
5186	Implementations sometimes use other syntactic constructs
5187	that interact with loose matching. For example, the property matching
5188	expression \p{L} may be defaulted to refer to the Unicode General_Category
5189	property: \p{General_Category=L}. For more information about
5190	the use of property values in regular expressions and other environments,
5191	see Section 1.2, Properties, in Unicode Technical Standard #18,
5192	"Unicode Regular Expressions" [UTS18].
5193	
5194	5.10 Invariants
5195	
5196	Property values in the UCD may be subject to correction
5197	in subsequent versions of the standard, as errors are found. Furthermore, any
5198	new version of the Unicode Standard may introduce new property values for
5199	a given property, except where the set of allowable values is fixed
5200	by the property type (such as for binary properties), or where the
5201	set of allowable values is subject to a provision of the Unicode
5202	Character Encoding Stability Policy [Stability].
5203	Finally, a new version may also
5204	introduce new properties or new data files in the UCD.
5205	
5206	Implementers of the UCD need to be aware of
5207	such changes when updating to new versions. However, some property values
5208	and some aspects of the file formats are considered
5209	invariant. This section documents such invariants.
5210	
5211	5.10.1 Character Property Invariants
5212	
5213	All formally guaranteed invariants for properties or property values
5214	are described in
5215	the Unicode Character Encoding Stability Policy
5216	[Stability].
5217	That policy and the list of invariants it enumerates are
5218	maintained outside the context of the Unicode Standard per se.
5219	They are not part of the standard, but rather are constraints
5220	on what can and cannot change in the standard between versions,
5221	and on what decisions the Unicode Technical Committee can and
5222	cannot take regarding the standard.
5223	
5224	In addition to the formally guaranteed invariants described
5225	in the Unicode Character Encoding Stability Policy, this section
5226	notes a few additional points regarding character property
5227	invariants in the UCD.
5228	
5229	Some character properties are simply considered immutable: once
5230	assigned, they are never changed. For example, a character's name
5231	is immutable, because of its importance in exact identification

5233	Decomposition_Mapping of a character are immutable, because of their

5393	5.10.2 UCD File Format Invariants
5394	
5395	There are also some constraints on allowable change in the
5396	file formats for UCD files. In general, the
5397	file format conventions are
5398	changed as little as possible, to minimize the impact on
5399	implementations which parse the machine-readable data files.
5400	However, some of the constraints on allowable file format
5401	change go beyond conservatism in format and instead have
5402	the status of invariants. These guarantees apply in particular
5403	to UnicodeData.txt, the very first data file associated with
5404	the UCD.
5405	
5406	The number and order of the fields in UnicodeData.txt is fixed.
5407	Any additional information about character properties to be added
5408	to the UCD in the future will
5409	appear in separate data files, rather than being added as an
5410	additional field to UnicodeData.txt or by reinterpretation
5411	of any of the existing fields.
5412	
5413	5.10.3 Invariants in Implementations
5414	
5415	Applications may wish to take the various character property
5416	and file format
5417	invariants into account when choosing how to implement character properties.
5418	
5419	The Canonical_Combining_Class offers a good example. The
5420	character property invariants regarding Canonical_Combining_Class
5421	guarantee that values, once assigned, will never change, and
5422	that all values used will be in the range 0..254. This means
5423	that the Canonical_Combining_Class can be safely implemented
5424	in an unsigned byte and that any value stored in a table for
5425	an existing character will not need to be updated dynamically
5426	for a later version.
5427	
5428	In practice, for Canonical_Combining_Class far fewer
5429	than 256 values are used. Unicode 3.0 used 53 values;
5430	Unicode 3.1 through Unicode 4.1 used 54 values; and Unicode 5.0
5431	through Unicode 9.0 used 55 values. New, non-zero
5432	Canonical_Combining_Class values are seldom added to the standard.
5433	(For details about this history, see
5434	DerivedCombiningClass.txt.)
5435	Implementations may take advantage of this fact for compression,
5436	because only the ordering of
5437	the non-zero values, and not their absolute values, matters for
5438	the Canonical Ordering Algorithm. In principle, it would be
5439	possible for up to 255 values to be used in the future, but
5440	the chances of the actual number of values exceeding 128
5441	are remote at this point. There are implementation advantages
5442	in restricting the number of internal class values to
5443	128—for example, the ability to use signed bytes without
5444	implicit widening to the int data type in Java.
5445	
5446	5.11 Validation
5447	
5448	The Unicode character
5449	property values in the UCD files can be validated by means of regular
5450	expressions. Such validation can also be useful in testing of
5451	implementations that return property values. The method of validation
5452	depends on the type of property, as described below.
5453	These expressions use Perl syntax, but may
5454	of course be converted to other formal conventions for use
5455	with other regular expression engines.
5456	
5457	The regular expressions which are appropriate for validation
5458	of particular properties may change in each subsequent version of the UCD.
5459	However, because of stability guarantees for character property aliases, these
5460	regular expressions for one version of
5461	the Unicode Standard will match valid values for previous versions
5462	of the standard.
5463	
5464	5.11.1 Enumerated and Binary Properties
5465	
5466	Enumerated and binary character properties can be validated by
5467	generating a regular expression using the PropertyValueAliases.txt file. Because
5468	enumerated properties have a defined list of possible values, the validating
5469	regular expression simply ORs together all of the possible values. Binary properties
5470	are a special case of enumerated property, with a predefined very short
5471	list of possible values.
5472	
5473	For example, to validate the East_Asian_Width property in
5474	the UCD, or to test an implementation that returns the East_Asian_Width property,
5475	parse the following relevant lines from PropertyValueAliases.txt and produce a
5476	regular expression that concatenates each of the short and long property alias
5477	values.
5478	
5479	
5480	
5481	# East_Asian_Width (ea)
5482	
5483	ea ; A ; Ambiguous
5484	ea ; F ; Fullwidth
5485	ea ; H ; Halfwidth
5486	ea ; N ; Neutral
5487	ea ; Na ; Narrow
5488	ea ; W ; Wide
5489	
5490	
5491	
5492	The resulting regular expression would then be:
5493	
5494	
5495	
5496	/A|Ambiguous|F|Fullwidth|H|Halfwidth|N|Neutral|Na|Narrow|W|Wide/
5497	
5498	
5499	
5500	For each Unicode binary character property, the regular
5501	expression can be precomputed simply as:
5502	
5503	
5504	
5505	/N|No|F|False|Y|Yes|T|True/
5506	
5507	
5508	
5509	The Catalog properties, Age, Block, and Script, are another
5510	type of enumerated character property. All possible values of those properties
5511	for any given version of the Unicode Standard are listed in PropertyValueAliases.txt,
5512	so a validating regular expression for a Catalog property for that given version of the UCD can be
5513	generated by concatenating values, as for the other enumerated properties.
5514	
5515	5.11.2 Canonical_Combining_Class Property
5516	
5517	The Canonical_Combining_Class (ccc) property is a hybrid type. The
5518	possible values defined for it in UnicodeData.txt range from 0 to 254 and are numeric
5519	values. However, Canonical_Combining_Class also has symbolic aliases defined for those particular values
5520	that are in actual use; those symbolic aliases are listed in PropertyValueAliases.txt.
5521	To produce a validating regular expression for Canonical_Combining_Class, concatenate
5522	together the symbolic aliases from PropertyValueAliases.txt, and then add the numeric
5523	range 0..254.
5524	
5525	The value 255 is reserved for use by implementations. When the
5526	ccc values are represented by bytes, that additional value of 255 may be used
5527	by an implementation for other purposes.
5528	
5529	The value 133 is reserved. No characters have that value. The property value alias
5530	CCC133 is retained in accordance with the stability policy regarding property value aliases.
5531

5533	
5534	The validating regular expressions for each property tag defined
5535	in the Unihan database are described in detail in [UAX38].

5780	5.11.5 Validation of Multivalued Properties
5781	
5782	Some properties, such as Script_Extensions of kCantonese, have property
5783	values each consisting of a set of element values. In the data files, these element values
5784	are separated by spaces. Validation of the property values is performed by first splitting
5785	each set into element values at the spaces, and then validating each element value
5786	individually. For example, the elements for Script_Extensions are values of the
5787	Script property; they are validated according to the validation requirements for the
5788	Script property. See also Section 5.7.6 Properties Whose Values Are Sets of Values.
5789	
5790	The Name_Alias property has values which consist of sets of one or
5791	more name strings. In the data file for this property, each element value occurs on
5792	a separate line and can be validated as a separate element.

5794	5.12 Deprecation
5795	
5796	In the Unicode Standard, the term deprecation is used somewhat
5797	differently than it is in some other standards. Deprecation is used to
5798	mean that a character or other feature is strongly discouraged from use.
5799	This should not, however, be taken as indicating that anything has been
5800	removed from the standard, nor that anything is planned for removal
5801	from the standard. Any such change is constrained by the
5802	Unicode Consortium Stability Policies [Stability].
5803	
5804	For the Unicode Character Database, there are two important types
5805	of deprecation to be noted. First, an encoded character may be
5806	deprecated. Second, a character property may be deprecated.
5807	
5808	When an encoded character is strongly discouraged from use, it is
5809	given the property value Deprecated=True. The Deprecated property
5810	is a binary property defined specifically to carry this information about
5811	Unicode characters. Very few characters are ever formally
5812	deprecated this way; it is not enough that a character be uncommon, obsolete,
5813	disliked, or not preferred. Only those few characters which have been
5814	determined by the UTC to have serious architectural defects or which
5815	have been determined to cause significant implementation problems are
5816	ever deprecated. Even in the most severe cases, such as the
5817	deprecated format control characters (U+206A..U+206F), an encoded character
5818	is never removed from the standard. Furthermore, although deprecated
5819	characters are strongly discouraged from use, and should be avoided in
5820	favor of other, more appropriate mechanisms, they may occur in data.
5821	Conformant implementations of Unicode processes such a Unicode normalization must
5822	handle even deprecated characters correctly.
5823	
5824	In the Unicode Character Database, a character property may
5825	also become strongly discouraged—usually because it no longer
5826	serves the purpose it was originally defined for. In such cases, the
5827	property is labelled "deprecated" in
5828	Table 9, Property Table.
5829	For example, see the Grapheme_Link property.
5830	Deprecated properties are not recommended for
5831	exposure in public APIs that support Unicode character properties.
5832	
5833	5.13 Property APIs
5834	
5835	The Unicode Standard does not specify the exact form of APIs which may be defined
5836	in software libraries to surface Unicode character properties to applications. However, there
5837	are some recommendations and general guidelines to follow, which should serve to reduce
5838	potential confusion and to promote better interoperability between applications using
5839	the Unicode Character Database.
5840	In the discussion which follows here, the term API is
5841	used to refer to a particular function or method, whereas the term API collection
5842	is used to refer to a related group of APIs, which might constitute a set of functions
5843	exported from a library, a class definition, or other groupings of related functionality.
5844	A distinction is also made between a public API, which is exported for general
5845	application use, and a private API, which may be kept hidden within a library or
5846	class, intended for internal use.
5847	
5848	First, if an API surfaces values of a particular Unicode character property
5849	and purports that value to represent a Unicode character property, it should exactly
5850	follow the specification of that property in the UCD. This principle follows from the
5851	general approach to conformance for the Unicode Standard: If you say it is Unicode,
5852	then it should follow the Unicode Standard specification.
5853	
5854	Second, an API should be clear about which version of the UCD it
5855	supports. This can be done, for example, with documentation, either external or
5856	included in the source in header files, class definition notes, and so forth.
5857	For an API collection, an even better option is to include an API which explicitly
5858	reports which version of the UCD is supported.
5859	This provision should reduce confusion regarding particular property
5860	values which might change between versions of the Unicode Standard, as well as making
5861	it clear which repertoire of encoded characters is intended to be covered. There is
5862	no principled constraint on an API supporting more than one version of the UCD, as long
5863	as it is clear about how it does so.
5864	
5865	Third, although there is no constraint on an API declaring that it
5866	only supports a designated subset of Unicode characters, best practice for a general
5867	purpose character property API would be to support the entire range of Unicode
5868	code points, providing determinant and well-documented property values for any valid Unicode
5869	code point input. That would include providing correct default property values for
5870	any unassigned code point. See Section 2.2, Use of Default Values
5871	for an explanation of that concept.
5872	
5873	Fourth, a Unicode character property API is not precluded from
5874	extending or tailoring its support of character properties, as long as such
5875	behavior is clearly documented, so that applications understand the values they
5876	will be getting by calling the API. For example, an API might surface an
5877	extended new property such as IsDanda, which is not formally part of the
5878	properties specified by the UCD, but which can be inferred from the
5879	documentation of the Unicode Standard. An API supporting a particular
5880	tailoring of the Unicode Line Breaking Algorithm could surface tailored
5881	Line_Break property values to support that behavior. Alternatively, an API supporting
5882	a particular private use agreement could surface privately-defined properties
5883	for a designated range of PUA characters. All such use of APIs should be
5884	considered conformant ways of extending API collections using the UCD.
5885	
5886	Designers of API collections to support Unicode character properties must
5887	also be aware that not all Unicode character properties are equal. There is no
5888	requirement, express or implied, that all Unicode character properties
5889	should be supported in a given API collection. In fact, an approach that simply parses
5890	the UCD and surfaces all Unicode character properties verbatim is
5891	very likely to result in a bad design. Character properties need to be
5892	understood in the context of the various Unicode algorithms they are designed
5893	to support.
5894	The following subtypes of
5895	Unicode character properties should generally not be exposed in APIs,
5896	except in limited circumstances. They may not be useful, particularly
5897	in public API collections, and may instead prove misleading to the users
5898	of such API collections.
5899	
5900	
5901	Contributory properties are not recommended for public APIs.
5902	A subset of Unicode normalization-related properties are not recommended for public APIs. See
5903	Section 5.7.5, Decompositions and Normalization.
5904	Deprecated properties are not recommended for public APIs. See
5905	Section 5.12, Deprecation.
5906	Provisional properties are not recommended for public APIs.

5909	5.14 Character Age
5910	
5911	The Age property indicates the first version in which a
5912	particular Unicode character was assigned. For example, U+20AC € EURO SIGN was
5913	added to Version 2.1 of the Unicode Standard, so it has age=2.1, while
5914	U+20B9 ₹ INDIAN RUPEE SIGN was added to Version 6.0 of the Unicode Standard,
5915	so it has age=6.0.
5916	
5917	Formally, the Age property is a catalog
5918	property whose enumerated values correspond to a list of tuples consisting
5919	of a major version integer and a minor version integer. The major version is
5920	a positive integer constrained to the range 1..255. The minor version is a
5921	non-negative integer constrained to the range 0..255. These range limitations
5922	are specified so that implementations can be guaranteed that all valid,
5923	assigned Age values can be represented in a sequence of two unsigned bytes.
5924	A third value corresponding to the Unicode update version is not required,
5925	because new characters are never assigned in update versions of
5926	the standard.
5927	
5928	The short values listed in PropertyValueAliases.txt for
5929	the Age property for assigned (designated) code points are of the form "m.n",
5930	with the first field corresponding to the major version, and the second field corresponding
5931	to the minor version.
5932	The long values listed in PropertyValueAliases.txt
5933	for the Age property for assigned code points start with
5934	a "V" and use an underscore instead
5935	of a dot between the major and minor version numbers: V2_1, V6_0, and so on. This
5936	makes the long format more useful as an identifier in programming languages. It is
5937	also useful in regular expressions, where the dot has other significance.
5938	
5939	The default value of the Age property, used for unassigned (undesignated) code points,
5940	is expressed with labels that depart from the numerical versioning scheme
5941	of the Age property for assigned code points; the short form for the default is "NA",
5942	and the long form for the default is "Unassigned". Implementations of parsers
5943	which manipulate the Age property need to be prepared for this special case,
5944	rather than expecting the default value to be expressed numerically, as "0.0", for example.
5945	
5946	The Age property is
5947	based on when a character is encoded in the standard. It is normative and immutable, and
5948	cannot be meaningfully tailored.
5949	
5950	The minimum value of the Age property is "1.1",
5951	instead of "1.0", because of the substantial and
5952	incompatible changes to the standard resulting from the merger of code points and
5953	character names between the Unicode Standard and ISO/IEC 10646 for their 1993
5954	publications. For Hangul syllable characters, which were
5955	extensively augmented in Unicode 2.0, the Age value is set to "2.0", even
5956	though a subset of the Hangul syllables had been published in earlier versions,
5957	at different code points.
5958	
5959	Private use characters, noncharacter code points, and surrogate code
5960	points also get Age values. The private use characters and noncharacter code
5961	points on the BMP have age=1.1. However, the full architecture for UTF-16 and multiple planes
5962	was not fully documented until Unicode 2.0, so the private use characters and
5963	noncharacter code points on supplementary planes, as well as the surrogate
5964	code points in the range D800..DFFF, are given the value age=2.0.
5965	
5966	The Age property cannot be derived from the other
5967	data files in any single version of the Unicode Character Database. Its derivation
5968	is done, rather, by tools that compare the assigned characters between
5969	subsequent versions. The data file DerivedAge.txt
5970	provides the definitive listing of the
5971	Age property value for all code points, as of that version of the standard.
5972	
5973	The typical use case for the Age property in regular expressions
5974	is to search for all characters that were
5975	present in a given version. For this reason,
5976	an expression such as "\p{age=V3_0}" is exceptionally
5977	defined to match all of the code
5978	points assigned in Version 3.0—that is, all the code points with
5979	a value less than or equal to the value 3.0 for the Age property, rather than
5980	just the subset of those code points with the value 3.0. This interprets
5981	"\p{age=V3_0}"
5982	as the set of all characters assigned as of Unicode 3.0, rather than
5983	as just the set of characters added to Unicode 3.0 subsequent to the
5984	prior version. For more
5985	information, see Unicode Technical Standard #18,
5986	"Unicode Regular Expressions" [UTS18].

6082	6.2 Segmentation Test Files and Documentation
6083	
6084	LineBreakTest.txt, located in the auxiliary directory of the UCD,
6085	contains data which can be used
6086	to test an implementation of the Unicode Line Breaking Algorithm.
6087	(See [UAX14] and [Tests14].) The header of
6088	that file specifies the data format and the use of the test data to
6089	specify line break opportunities. Note that non-ASCII characters are used
6090	in this test data as field delimiters.
6091	
6092	There is an associated documentation file, LineBreakTest.html, which displays
6093	the results of the Line Breaking Algorithm in an interactive chart form, with a
6094	documented listing of the rules.
6095	
6096	The Unicode text segmentation test data files are also located in the
6097	auxiliary directory of the UCD. (See [Tests29].) They
6098	contain data which can be used to test an implementation of the segmentation
6099	algorithms specified in [UAX29].
6100	The headers of
6101	those file specify the data format and the use of the test data to
6102	specify text segmentation opportunities. Note that non-ASCII characters are used
6103	in this test data as field delimiters.
6104	
6105	There are also associated documentation
6106	files, which display the results of the segmentation algorithms in an
6107	interactive chart form, with a documented listing of the rules:
6108	
6109	GraphemeBreakTest.html
6110	SentenceBreakTest.html
6111	WordBreakTest.html
6112	
6113	
6114	Unlike the Unicode Normalization Algorithm, the Unicode Line Breaking
6115	Algorithm and the various text segmentation algorithms are tailorable,
6116	and there is every expectation that implementations will tailor these
6117	algorithms to produce results as needed. The test data files only test
6118	the default behavior of the algorithms. Testing of tailored implementations
6119	will need to modify and/or extend the test cases as appropriate to match
6120	any documented tailoring.
6121	
6122	6.3 Bidirectional Test Files
6123	
6124	These files contain data
6125	which can be used to test an implementation of the
6126	Unicode Bidirectional Algorithm.
6127	(See [UAX9] and [Tests9].)
6128	
6129	The data in BidiTest.txt is intended to exhaustively test
6130	all possible combinations of Bidi_Class values for strings of length four or less.
6131	To allow for the resulting very large number of test cases,
6132	the data file has a somewhat complicated format which is
6133	described in the header. Fundamentally, for each input string and for each
6134	possible input paragraph level, the test data specifies the resulting bidi levels and
6135	expected reordering.
6136	
6137	The data in BidiCharacterTest.txt is provided to test various
6138	edge cases for the algorithm. It contains an extra field which allows for explicit
6139	control of the overall directional context for each test case.
6140	
6141	The Unicode Bidirectional Algorithm is tailorable within certain limits.
6142	Conformant implementations with no tailoring are expected to produce the results as
6143	specified in BidiTest.txt and BidiCharacterTest.txt,
6144	and should not deviate from those results. Tailored
6145	implementations can also use the data in
6146	the test files to test for overall conformance
6147	to the algorithm by changing the assignment of properties to characters to reflect
6148	the details of their tailoring.
