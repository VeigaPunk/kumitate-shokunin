# QUESTION. In every Registry row of every fleet lane's corpus/SOURCES.md (current) and every
# committed revision of the kumitate lane's corpus/SOURCES.md: does any of the 11 cells carry, at
# either edge, a character that ECMAScript String.prototype.trim() strips but the POSIX "blank"
# class /^[ \t]+|[ \t]+$/ does NOT strip?
#
# EDGE SEMANTICS (why "at either edge" is measured after the blank run).
#   A cell "|  X  |" has fields ["", "  X  ", ""]. The blank class removes the leading/trailing
#   [ \t] run; JS trim() removes that run PLUS the TRIM_ONLY characters adjacent to it. So the
#   probe is: strip the leading [ \t] run, then look for TRIM_ONLY chars immediately after it
#   (and symmetrically at the trailing edge). A TRIM_ONLY char buried mid-cell is not an edge pad.
#
# TRIM_ONLY is computed from the JS runtime itself (see pad-survey.mjs), not hand-listed:
#   every code point c with c.trim() === '' (JS TrimString, ECMA-262 S276) that /^[ \t]$/ does
#   not match. Measured on node v24.21.0: 23 code points —
#     U+000A U+000B U+000C U+000D U+00A0 U+1680 U+2000..U+200A U+2028 U+2029 U+202F U+205F
#     U+3000 U+FEFF
#   i.e. LF VT FF CR NBSP OGHAM_SPACE EN_QUAD..HAIRSP LS PS NNBSP MMSP IDEOGRAPHIC_SPACE ZWNBSP.
#   (JS regex \s is the SAME 25-point set — the JS trim set plus SP and TAB — see class-compare.mjs.)
#
# SCRIPT USED: .ufo/waves/round-99/K99Scout/pad-survey.mjs (this directory) and its driver
#   .ufo/waves/round-99/K99Scout/survey-revs.mjs. Both are committed alongside this file.
#   Run:
#     node .ufo/waves/round-99/K99Scout/pad-survey.mjs <lane> <file> ...   > pads-current.tsv
#   Section grammar mirrors sources-check.mjs (r97) / census row_pass: heading `^ {0,3}##[ \t]`
#   opens a section whose name is the trimmed heading text; `^ {0,3}#[ \t]` clears it; a table row
#   is `^ {0,3}\|`; the separator row (id cell "id" or /^:?-{3,}:?$/) is not a data row.
