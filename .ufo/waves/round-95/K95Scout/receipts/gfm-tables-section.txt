   2| 4.10Tables (extension)
   3| 
   4| GFM enables the table extension, where an additional leaf block type is
   5| available.
   6| A table is an arrangement of data with rows and columns, consisting of a
   7| single header row, a delimiter row separating the header from the data, and
   8| zero or more data rows.
   9| Each row consists of cells containing arbitrary text, in which inlines are
  10| parsed, separated by pipes (|).  A leading and trailing pipe is also
  11| recommended for clarity of reading, and if there’s otherwise parsing ambiguity.
  12| Spaces between pipes and cell content are trimmed.  Block-level elements cannot
  13| be inserted in a table.
  14| The delimiter row consists of cells whose only content are hyphens (-),
  15| and optionally, a leading or trailing colon (:), or both, to indicate left,
  16| right, or center alignment respectively.
  17| 
  18| 
  19| Example 198
  20| 
  21| 
  22| | foo | bar |
  23| | --- | --- |
  24| | baz | bim |
  25| 
  26| 
  27| 
  28| <table>
  29| <thead>
  30| <tr>
  31| <th>foo</th>
  32| <th>bar</th>
  33| </tr>
  34| </thead>
  35| <tbody>
  36| <tr>
  37| <td>baz</td>
  38| <td>bim</td>
  39| </tr>
  40| </tbody>
  41| </table>
  42| 
  43| 
  44| 
  45| Cells in one column don’t need to match length, though it’s easier to read if
  46| they are. Likewise, use of leading and trailing pipes may be inconsistent:
  47| 
  48| 
  49| Example 199
  50| 
  51| 
  52| | abc | defghi |
  53| :-: | -----------:
  54| bar | baz
  55| 
  56| 
  57| 
  58| <table>
  59| <thead>
  60| <tr>
  61| <th align="center">abc</th>
  62| <th align="right">defghi</th>
  63| </tr>
  64| </thead>
  65| <tbody>
  66| <tr>
  67| <td align="center">bar</td>
  68| <td align="right">baz</td>
  69| </tr>
  70| </tbody>
  71| </table>
  72| 
  73| 
  74| 
  75| Include a pipe in a cell’s content by escaping it, including inside other
  76| inline spans:
  77| 
  78| 
  79| Example 200
  80| 
  81| 
  82| | f\|oo  |
  83| | ------ |
  84| | b `\|` az |
  85| | b **\|** im |
  86| 
  87| 
  88| 
  89| <table>
  90| <thead>
  91| <tr>
  92| <th>f|oo</th>
  93| </tr>
  94| </thead>
  95| <tbody>
  96| <tr>
  97| <td>b <code>|</code> az</td>
  98| </tr>
  99| <tr>
 100| <td>b <strong>|</strong> im</td>
 101| </tr>
 102| </tbody>
 103| </table>

 256| 5Container blocks
 257| 
 258| A container block is a block that has other
 259| blocks as its contents.  There are two basic kinds of container blocks:
 260| block quotes and list items.
 261| Lists are meta-containers for list items.
 262| We define the syntax for container blocks recursively.  The general
 263| form of the definition is:
 264| 
 265| If X is a sequence of blocks, then the result of
 266| transforming X in such-and-such a way is a container of type Y
 267| with these blocks as its content.
 268| 
 269| So, we explain what counts as a block quote or list item by explaining
 270| how these can be generated from their contents. This should suffice
 271| to define the syntax, although it does not give a recipe for parsing
 272| these constructions.  (A recipe is provided below in the section entitled
 273| A parsing strategy.)
 274| 
 275| 5.1Block quotes
 276| 
 277| A block quote marker
 278| consists of 0-3 spaces of initial indent, plus (a) the character > together
 279| with a following space, or (b) a single character > not followed by a space.
 280| The following rules define block quotes:
 281| 
 282| 
 283| Basic case.  If a string of lines Ls constitute a sequence
 284| of blocks Bs, then the result of prepending a block quote
 285| marker to the beginning of each line in Ls
 286| is a block quote containing Bs.
 287| 
 288| 
 289| Laziness.  If a string of lines Ls constitute a block
 290| quote with contents Bs, then the result of deleting
 291| the initial block quote marker from one or
 292| more lines in which the next non-whitespace character after the block
 293| quote marker is paragraph continuation
 294| text is a block quote with Bs as its content.
 295| Paragraph continuation text is text
 296| that will be parsed as part of the content of a paragraph, but does
 297| not occur at the beginning of the paragraph.
 298| 
 299| 
 300| Consecutiveness.  A document cannot contain two block
 301| quotes in a row unless there is a blank line between them.
 302| 
 303| 
 304| Nothing else counts as a block quote.
 305| Here is a simple example:
 306| 
 307| 
 308| Example 206
 309| 
 310| 
 311| > # Foo
 312| > bar
 313| > baz
 314| 
 315| 
 316| 
 317| <blockquote>
 318| <h1>Foo</h1>
 319| <p>bar
 320| baz</p>
 321| </blockquote>
 322| 
 323| 
 324| 
 325| The spaces after the > characters can be omitted:
 326| 
 327| 
 328| Example 207
 329| 
 330| 
 331| ># Foo
 332| >bar
 333| > baz
 334| 
 335| 
 336| 
 337| <blockquote>
 338| <h1>Foo</h1>
 339| <p>bar
 340| baz</p>
 341| </blockquote>
 342| 
 343| 
 344| 
 345| The > characters can be indented 1-3 spaces:
 346| 
 347| 
 348| Example 208
 349| 
 350| 
 351|    > # Foo
 352|    > bar
 353|  > baz
 354| 
 355| 
 356| 
 357| <blockquote>
 358| <h1>Foo</h1>
 359| <p>bar
 360| baz</p>
 361| </blockquote>
 362| 
 363| 
 364| 
 365| Four spaces gives us a code block:
 366| 
 367| 
 368| Example 209
 369| 
 370| 
 371|     > # Foo
 372|     > bar
 373|     > baz
 374| 
 375| 
 376| 
 377| <pre><code>&gt; # Foo
 378| &gt; bar
 379| &gt; baz
 380| </code></pre>
 381| 
 382| 
 383| 
 384| The Laziness clause allows us to omit the > before
 385| paragraph continuation text:
 386| 
 387| 
 388| Example 210

 391| > # Foo
 392| > bar
 393| baz

 400| baz</p>
 401| </blockquote>

 405| A block quote can contain some lazy and some non-lazy
 406| continuation lines:
 407| 
 408| 
 409| Example 211
 410| 
 411| 
 412| > bar
 413| baz
 414| > foo
 415| 
 416| 
 417| 
 418| <blockquote>
 419| <p>bar
 420| baz
 421| foo</p>
 422| </blockquote>
 423| 
 424| 
 425| 
 426| Laziness only applies to lines that would have been continuations of
 427| paragraphs had they been prepended with block quote markers.
 428| For example, the >  cannot be omitted in the second line of
 429| > foo
 430| > ---
 431| 
 432| without changing the meaning:
 433| 
 434| 
 435| Example 212
 436| 
 437| 
 438| > foo
 439| ---
 440| 
 441| 
 442| 
 443| <blockquote>
 444| <p>foo</p>
 445| </blockquote>
 446| <hr />
 447|

 449| 
 450| Similarly, if we omit the >  in the second line of
 451| > - foo
 452| > - bar
 453| 
 454| then the block quote ends after the first line:
 455| 
 456| 
 457| Example 213
 458| 
 459| 
 460| > - foo
 461| - bar
 462|

 464| 
 465| <blockquote>
 466| <ul>

 468| </ul>
 469| </blockquote>
 470| <ul>
 471| <li>bar</li>
 472| </ul>

 477| subsequent lines of an indented or fenced code block:
 478|

 484|     bar

 487| 
 488| <blockquote>
 489| <pre><code>foo

 823| 5.2List items
 824| 
 825| A list marker is a
 826| bullet list marker or an ordered list marker.
 827| A bullet list marker
 828| is a -, +, or * character.
 829| An ordered list marker
 830| is a sequence of 1–9 arabic digits (0-9), followed by either a
 831| . character or a ) character.  (The reason for the length
 832| limit is that with 10 digits we start seeing integer overflows
 833| in some browsers.)
 834| The following rules define list items:
 835| 
 836| 
 837| Basic case.  If a sequence of lines Ls constitute a sequence of
 838| blocks Bs starting with a non-whitespace character, and M is a
 839| list marker of width W followed by 1 ≤ N ≤ 4 spaces, then the result
 840| of prepending M and the following spaces to the first line of
 841| Ls, and indenting subsequent lines of Ls by W + N spaces, is a
 842| list item with Bs as its contents.  The type of the list item
 843| (bullet or ordered) is determined by the type of its list marker.
 844| If the list item is ordered, then it is also assigned a start
 845| number, based on the ordered list marker.
 846| Exceptions:
 847| 
 848| When the first list item in a list interrupts
 849| a paragraph—that is, when it starts on a line that would
 850| otherwise count as paragraph continuation text—then (a)
 851| the lines Ls must not begin with a blank line, and (b) if
 852| the list item is ordered, the start number must be 1.
 853| If any line is a thematic break then
 854| that line is not a list item.
 855| 
 856| 
 857| 
 858| For example, let Ls be the lines
 859| 
 860| 
 861| Example 231
 862| 
 863| 
 864| A paragraph
 865| with two lines.
 866| 
 867|     indented code
 868| 
 869| > A block quote.
 870| 
 871| 
 872| 
 873| <p>A paragraph
 874| with two lines.</p>
 875| <pre><code>indented code
 876| </code></pre>
 877| <blockquote>
 878| <p>A block quote.</p>
 879| </blockquote>
 880| 
 881| 
 882| 
 883| And let M be the marker 1., and N = 2.  Then rule #1 says
 884| that the following is an ordered list item with start number 1,
 885| and the same contents as Ls:
 886| 
 887| 
 888| Example 232
 889| 
 890| 
 891| 1.  A paragraph
 892|     with two lines.
 893| 
 894|         indented code
 895| 
 896|     > A block quote.
 897| 
 898| 
 899| 
 900| <ol>
 901| <li>
 902| <p>A paragraph
 903| with two lines.</p>
 904| <pre><code>indented code
 905| </code></pre>
 906| <blockquote>
 907| <p>A block quote.</p>
 908| </blockquote>
 909| </li>
 910| </ol>
 911| 
 912| 
 913| 
 914| The most important thing to notice is that the position of
 915| the text after the list marker determines how much indentation
 916| is needed in subsequent blocks in the list item.  If the list
 917| marker takes up two spaces, and there are three spaces between
 918| the list marker and the next non-whitespace character, then blocks
 919| must be indented five spaces in order to fall under the list
 920| item.
 921| Here are some examples showing how far content must be indented to be
 922| put under the list item:
 923| 
 924| 
 925| Example 233
 926| 
 927| 
 928| - one
 929| 
 930|  two
 931| 
 932| 
 933| 
 934| <ul>
 935| <li>one</li>
 936| </ul>
 937| <p>two</p>
 938| 
 939| 
 940| 
 941| 
 942| 
 943| Example 234
 944| 
 945| 
 946| - one
 947| 
 948|   two
 949| 
 950| 
 951| 
 952| <ul>
 953| <li>
 954| <p>one</p>
 955| <p>two</p>
 956| </li>
 957| </ul>
 958| 
 959| 
 960| 
 961| 
 962| 
 963| Example 235
 964| 
 965| 
 966|  -    one
 967| 
 968|      two
 969| 
 970| 
 971| 
 972| <ul>
 973| <li>one</li>
 974| </ul>
 975| <pre><code> two
 976| </code></pre>
 977| 
 978| 
 979| 
 980| 
 981| 
 982| Example 236
 983| 
 984| 
 985|  -    one
 986| 
 987|       two
 988| 
 989| 
 990| 
 991| <ul>
 992| <li>
 993| <p>one</p>
 994| <p>two</p>
 995| </li>
 996| </ul>
 997| 
 998| 
 999| 
1000| It is tempting to think of this in terms of columns:  the continuation
1001| blocks must be indented at least to the column of the first
1002| non-whitespace character after the list marker. However, that is not quite right.
1003| The spaces after the list marker determine how much relative indentation
1004| is needed.  Which column this indentation reaches will depend on
1005| how the list item is embedded in other constructions, as shown by
1006| this example:
1007| 
1008| 
1009| Example 237
1010| 
1011| 
1012|    > > 1.  one
1013| >>
1014| >>     two
1015| 
1016| 
1017| 
1018| <blockquote>
1019| <blockquote>
1020| <ol>
1021| <li>
1022| <p>one</p>
1023| <p>two</p>
1024| </li>
1025| </ol>
1026| </blockquote>
1027| </blockquote>
1028| 
1029| 
1030| 
1031| Here two occurs in the same column as the list marker 1.,
1032| but is actually contained in the list item, because there is
1033| sufficient indentation after the last containing blockquote marker.
1034| The converse is also possible.  In the following example, the word two

2008| 5.2.1Motivation
2009| 
2010| John Gruber’s Markdown spec says the following about list items:
2011| 
2012| 
2013| “List markers typically start at the left margin, but may be indented
2014| by up to three spaces. List markers must be followed by one or more
2015| spaces or a tab.”
2016| 
2017| 
2018| “To make lists look nice, you can wrap items with hanging indents….
2019| But if you don’t want to, you don’t have to.”
2020| 
2021| 
2022| “List items may consist of multiple paragraphs. Each subsequent
2023| paragraph in a list item must be indented by either 4 spaces or one
2024| tab.”
2025| 
2026| 
2027| “It looks nice if you indent every line of the subsequent paragraphs,
2028| but here again, Markdown will allow you to be lazy.”
2029| 
2030| 
2031| “To put a blockquote within a list item, the blockquote’s >
2032| delimiters need to be indented.”
2033| 
2034| 
2035| “To put a code block within a list item, the code block needs to be
2036| indented twice — 8 spaces or two tabs.”
2037| 
2038| 
2039| These rules specify that a paragraph under a list item must be indented
2040| four spaces (presumably, from the left margin, rather than the start of
2041| the list marker, but this is not said), and that code under a list item
2042| must be indented eight spaces instead of the usual four.  They also say
2043| that a block quote must be indented, but not by how much; however, the
2044| example given has four spaces indentation.  Although nothing is said
2045| about other kinds of block-level content, it is certainly reasonable to
2046| infer that all block elements under a list item, including other
2047| lists, must be indented four spaces.  This principle has been called the
2048| four-space rule.
2049| The four-space rule is clear and principled, and if the reference
2050| implementation Markdown.pl had followed it, it probably would have
2051| become the standard.  However, Markdown.pl allowed paragraphs and
2052| sublists to start with only two spaces indentation, at least on the
2053| outer level.  Worse, its behavior was inconsistent: a sublist of an
2054| outer-level list needed two spaces indentation, but a sublist of this
2055| sublist needed three spaces.  It is not surprising, then, that different
2056| implementations of Markdown have developed very different rules for
2057| determining what comes under a list item.  (Pandoc and python-Markdown,
2058| for example, stuck with Gruber’s syntax description and the four-space
2059| rule, while discount, redcarpet, marked, PHP Markdown, and others
2060| followed Markdown.pl’s behavior more closely.)
2061| Unfortunately, given the divergences between implementations, there
2062| is no way to give a spec for list items that will be guaranteed not
2063| to break any existing documents.  However, the spec given here should
2064| correctly handle lists formatted with either the four-space rule or
2065| the more forgiving Markdown.pl behavior, provided they are laid out
2066| in a way that is natural for a human to read.
2067| The strategy here is to let the width and indentation of the list marker
2068| determine the indentation necessary for blocks to fall under the list
2069| item, rather than having a fixed and arbitrary number.  The writer can
2070| think of the body of the list item as a unit which gets indented to the
2071| right enough to fit the list marker (and any indentation on the list
2072| marker).  (The laziness rule, #5, then allows continuation lines to be
2073| unindented if needed.)
2074| This rule is superior, we claim, to any rule requiring a fixed level of
2075| indentation from the margin.  The four-space rule is clear but
2076| unnatural. It is quite unintuitive that
2077| - foo
2078| 
2079|   bar
2080| 
2081|   - baz
2082| 
2083| should be parsed as two lists with an intervening paragraph,
2084| <ul>
2085| <li>foo</li>
2086| </ul>
2087| <p>bar</p>
2088| <ul>
2089| <li>baz</li>
2090| </ul>
2091| 
2092| as the four-space rule demands, rather than a single list,
2093| <ul>
2094| <li>
2095| <p>foo</p>
2096| <p>bar</p>
2097| <ul>
2098| <li>baz</li>
2099| </ul>
2100| </li>
2101| </ul>
2102| 
2103| The choice of four spaces is arbitrary.  It can be learned, but it is
2104| not likely to be guessed, and it trips up beginners regularly.
2105| Would it help to adopt a two-space rule?  The problem is that such
2106| a rule, together with the rule allowing 1–3 spaces indentation of the
2107| initial list marker, allows text that is indented less than the
2108| original list marker to be included in the list item. For example,
2109| Markdown.pl parses
2110|    - one
2111| 
2112|   two
2113| 
2114| as a single list item, with two a continuation paragraph:
2115| <ul>
2116| <li>
2117| <p>one</p>
2118| <p>two</p>
2119| </li>
2120| </ul>
2121| 
2122| and similarly
2123| >   - one
2124| >
2125| >  two
2126| 
2127| as
2128| <blockquote>
2129| <ul>
2130| <li>
2131| <p>one</p>
2132| <p>two</p>
2133| </li>
2134| </ul>
2135| </blockquote>
2136| 
2137| This is extremely unintuitive.
2138| Rather than requiring a fixed indent from the margin, we could require
2139| a fixed indent (say, two spaces, or even one space) from the list marker (which
2140| may itself be indented).  This proposal would remove the last anomaly
2141| discussed.  Unlike the spec presented above, it would count the following
2142| as a list item with a subparagraph, even though the paragraph bar
2143| is not indented as far as the first paragraph foo:
2144|  10. foo
2145| 
2146|    bar  
2147| 
2148| Arguably this text does read like a list item with bar as a subparagraph,
2149| which may count in favor of the proposal.  However, on this proposal indented
2150| code would have to be indented six spaces after the list marker.  And this
2151| would break a lot of existing Markdown, which has the pattern:
2152| 1.  foo
2153| 
2154|         indented code
2155| 
2156| where the code is indented eight spaces.  The spec above, by contrast, will
2157| parse this text as expected, since the code block’s indentation is measured
2158| from the beginning of foo.
2159| The one case that needs special treatment is a list item that starts
2160| with indented code.  How much indentation is required in that case, since
2161| we don’t have a “first paragraph” to measure from?  Rule #2 simply stipulates
2162| that in such cases, we require one space indentation from the list marker
2163| (and then the normal four spaces for the indented code).  This will match the
2164| four-space rule in cases where the list marker plus its initial indentation
2165| takes four spaces (a common case), but diverge in other cases.

2168| 5.3Task list items (extension)
2169| 
2170| GFM enables the tasklist extension, where an additional processing step is
2171| performed on list items.
2172| A task list item is a list item where the first block in it
2173| is a paragraph which begins with a task list item marker and at least one
2174| whitespace character before any other content.
2175| A task list item marker consists of an optional number of spaces, a left
2176| bracket ([), either a whitespace character or the letter x in either
2177| lowercase or uppercase, and then a right bracket (]).
2178| When rendered, the task list item marker is replaced with a semantic checkbox element;
2179| in an HTML output, this would be an <input type="checkbox"> element.
2180| If the character between the brackets is a whitespace character, the checkbox
2181| is unchecked.  Otherwise, the checkbox is checked.
2182| This spec does not define how the checkbox elements are interacted with: in practice,
2183| implementors are free to render the checkboxes as disabled or inmutable elements,
2184| or they may dynamically handle dynamic interactions (i.e. checking, unchecking) in
2185| the final rendered document.

2192| - [x] bar

2197| <li><input disabled="" type="checkbox"> foo</li>
2198| <li><input checked="" disabled="" type="checkbox"> bar</li>

2230| 5.4Lists
2231| 
2232| A list is a sequence of one or more
2233| list items of the same type.  The list items
2234| may be separated by any number of blank lines.
2235| Two list items are of the same type
2236| if they begin with a list marker of the same type.
2237| Two list markers are of the
2238| same type if (a) they are bullet list markers using the same character
2239| (-, +, or *) or (b) they are ordered list numbers with the same
2240| delimiter (either . or )).
2241| A list is an ordered list
2242| if its constituent list items begin with
2243| ordered list markers, and a
2244| bullet list if its constituent list
2245| items begin with bullet list markers.
2246| The start number
2247| of an ordered list is determined by the list number of
2248| its initial list item.  The numbers of subsequent list items are
2249| disregarded.
2250| A list is loose if any of its constituent
2251| list items are separated by blank lines, or if any of its constituent
2252| list items directly contain two block-level elements with a blank line
2253| between them.  Otherwise a list is tight.
2254| (The difference in HTML output is that paragraphs in a loose list are
2255| wrapped in <p> tags, while paragraphs in a tight list are not.)
2256| Changing the bullet or ordered list delimiter starts a new list:

2329| In CommonMark, we do allow lists to interrupt paragraphs, for
2330| two reasons.  First, it is natural and not uncommon for people
2331| to start lists without blank lines:
2332| I need to buy
2333| - new shoes
2334| - a coat
2335| - a plane ticket

2337| Second, we are attracted to a
2338| 
2339| principle of uniformity:
2340| if a chunk of text has a certain
2341| meaning, it will continue to have the same meaning when put into a
2342| container block (such as a list item or blockquote).
2343| 
2344| (Indeed, the spec for list items and block quotes presupposes
2345| this principle.) This principle implies that if
2346|   * I need to buy
2347|     - new shoes
2348|     - a coat
2349|     - a plane ticket
2350| 
2351| is a list item containing a paragraph followed by a nested sublist,
2352| as all Markdown implementations agree it is (though the paragraph
2353| may be rendered without <p> tags, since the list is “tight”),
2354| then
2355| I need to buy
2356| - new shoes
2357| - a coat
2358| - a plane ticket

2360| by itself should be a paragraph followed by a nested sublist.
2361| Since it is well established Markdown practice to allow lists to
2362| interrupt paragraphs inside list items, the principle of
2363| uniformity requires us to allow this outside list items as

3216| 6.2Entity and numeric character references
3217| 
3218| Valid HTML entity references and numeric character references
3219| can be used in place of the corresponding Unicode character,
3220| with the following exceptions:
3221| 
3222| 
3223| Entity and character references are not recognized in code
3224| blocks and code spans.
3225| 
3226| 
3227| Entity and character references cannot stand in place of
3228| special characters that define structural elements in
3229| CommonMark.  For example, although &#42; can be used
3230| in place of a literal * character, &#42; cannot replace
3231| * in emphasis delimiters, bullet list markers, or thematic
3232| breaks.
3233| 
3234| 
3235| Conforming CommonMark parsers need not store information about
3236| whether a particular character was represented in the source
3237| using a Unicode character or an entity reference.
3238| Entity references consist of & + any of the valid
3239| HTML5 entity names + ;. The
3240| document https://html.spec.whatwg.org/multipage/entities.json
3241| is used as an authoritative source for the valid entity
3242| references and their corresponding code points.
3243| 
3244| 
3245| Example 321
3246| 
3247| 
3248| &nbsp; &amp; &copy; &AElig; &Dcaron;
3249| &frac34; &HilbertSpace; &DifferentialD;
3250| &ClockwiseContourIntegral; &ngE;
3251| 
3252| 
3253| 
3254| <p>  &amp; © Æ Ď
3255| ¾ ℋ ⅆ
3256| ∲ ≧̸</p>
3257| 
3258| 
3259| 
3260| Decimal numeric character
3261| references
3262| consist of &# + a string of 1–7 arabic digits + ;. A
3263| numeric character reference is parsed as the corresponding
3264| Unicode character. Invalid Unicode code points will be replaced by
3265| the REPLACEMENT CHARACTER (U+FFFD).  For security reasons,
3266| the code point U+0000 will also be replaced by U+FFFD.
3267| 
3268| 
3269| Example 322
3270| 
3271| 
3272| &#35; &#1234; &#992; &#0;
3273| 
3274| 
3275| 
3276| <p># Ӓ Ϡ �</p>
3277| 
3278| 
3279| 
3280| Hexadecimal numeric character
3281| references consist of &# +
3282| either X or x + a string of 1-6 hexadecimal digits + ;.
3283| They too are parsed as the corresponding Unicode character (this
3284| time specified with a hexadecimal numeral instead of decimal).
3285| 
3286| 
3287| Example 323
3288| 
3289|

3293|

3516| 6.3Code spans
3517| 
3518| A backtick string
3519| is a string of one or more backtick characters (`) that is neither
3520| preceded nor followed by a backtick.
3521| A code span begins with a backtick string and ends with
3522| a backtick string of equal length.  The contents of the code span are
3523| the characters between the two backtick strings, normalized in the
3524| following ways:
3525| 
3526| First, line endings are converted to spaces.
3527| If the resulting string both begins and ends with a space
3528| character, but does not consist entirely of space
3529| characters, a single space character is removed from the
3530| front and back.  This allows you to include code that begins
3531| or ends with backtick characters, which must be separated by
3532| whitespace from the opening or closing backtick strings.
3533| 
3534| This is a simple code span:
3535| 
3536| 
3537| Example 338
3538| 
3539| 
3540| `foo`
3541| 
3542| 
3543| 
3544| <p><code>foo</code></p>
3545| 
3546| 
3547| 
3548| Here two backticks are used, because the code contains a backtick.
3549| This example also illustrates stripping of a single leading and
3550| trailing space:
3551| 
3552| 
3553| Example 339
3554| 
3555| 
3556| `` foo ` bar ``
3557| 
3558| 
3559| 
3560| <p><code>foo ` bar</code></p>
3561| 
3562| 
3563| 
3564| This example shows the motivation for stripping leading and trailing
3565| spaces:
3566| 
3567| 
3568| Example 340
3569| 
3570| 
3571| ` `` `
3572| 
3573| 
3574| 
3575| <p><code>``</code></p>
3576| 
3577| 
3578| 
3579| Note that only one space is stripped:
3580| 
3581| 
3582| Example 341
3583| 
3584| 
3585| `  ``  `
3586| 
3587| 
3588| 
3589| <p><code> `` </code></p>
3590| 
3591| 
3592| 
3593| The stripping only happens if the space is on both
3594| sides of the string:
3595| 
3596| 
3597| Example 342
3598| 
3599| 
3600| ` a`
3601| 
3602| 
3603| 
3604| <p><code> a</code></p>
3605| 
3606| 
3607|

3609| stripped in this way:
3610| 
3611|

3613|

3616| 
3617| 
3618| 
3619| <p><code> b </code></p>
3620|

3624|

3627|

3868| 6.4Emphasis and strong emphasis
3869| 
3870| John Gruber’s original Markdown syntax
3871| description says:
3872| 
3873| Markdown treats asterisks (*) and underscores (_) as indicators of
3874| emphasis. Text wrapped with one * or _ will be wrapped with an HTML
3875| <em> tag; double *’s or _’s will be wrapped with an HTML <strong>
3876| tag.
3877| 
3878| This is enough for most users, but these rules leave much undecided,
3879| especially when it comes to nested emphasis.  The original
3880| Markdown.pl test suite makes it clear that triple *** and
3881| ___ delimiters can be used for strong emphasis, and most
3882| implementations have also allowed the following patterns:
3883| ***strong emph***
3884| ***strong** in emph*
3885| ***emph* in strong**
3886| **in strong *emph***
3887| *in emph **strong***
3888| 
3889| The following patterns are less widely supported, but the intent
3890| is clear and they are useful (especially in contexts like bibliography
3891| entries):
3892| *emph *with emph* in it*
3893| **strong **with strong** in it**
3894| 
3895| Many implementations have also restricted intraword emphasis to
3896| the * forms, to avoid unwanted emphasis in words containing
3897| internal underscores.  (It is best practice to put these in code
3898| spans, but users often do not.)
3899| internal emphasis: foo*bar*baz
3900| no emphasis: foo_bar_baz
3901| 
3902| The rules given below capture all of these patterns, while allowing
3903| for efficient parsing strategies that do not backtrack.
3904| First, some definitions.  A delimiter run is either
3905| a sequence of one or more * characters that is not preceded or
3906| followed by a non-backslash-escaped * character, or a sequence
3907| of one or more _ characters that is not preceded or followed by
3908| a non-backslash-escaped _ character.
3909| A left-flanking delimiter run is
3910| a delimiter run that is (1) not followed by Unicode whitespace,
3911| and either (2a) not followed by a punctuation character, or
3912| (2b) followed by a punctuation character and
3913| preceded by Unicode whitespace or a punctuation character.
3914| For purposes of this definition, the beginning and the end of
3915| the line count as Unicode whitespace.
3916| A right-flanking delimiter run is
3917| a delimiter run that is (1) not preceded by Unicode whitespace,
3918| and either (2a) not preceded by a punctuation character, or
3919| (2b) preceded by a punctuation character and
3920| followed by Unicode whitespace or a punctuation character.
3921| For purposes of this definition, the beginning and the end of
3922| the line count as Unicode whitespace.
3923| Here are some examples of delimiter runs.
3924| 
3925| 
3926| left-flanking but not right-flanking:
3927| ***abc
3928|   _abc
3929| **"abc"
3930|  _"abc"
3931| 
3932| 
3933| 
3934| right-flanking but not left-flanking:
3935|  abc***
3936|  abc_
3937| "abc"**
3938| "abc"_
3939| 
3940| 
3941| 
3942| Both left and right-flanking:
3943|  abc***def
3944| "abc"_"def"
3945| 
3946| 
3947| 
3948| Neither left nor right-flanking:
3949| abc *** def
3950| a _ b
3951| 
3952| 
3953| 
3954| (The idea of distinguishing left-flanking and right-flanking
3955| delimiter runs based on the character before and the character
3956| after comes from Roopesh Chander’s
3957| vfmd.
3958| vfmd uses the terminology “emphasis indicator string” instead of “delimiter
3959| run,” and its rules for distinguishing left- and right-flanking runs
3960| are a bit more complex than the ones given here.)
3961| The following rules define emphasis and strong emphasis:
3962| 
3963| 
3964| A single * character can open emphasis
3965| iff (if and only if) it is part of a left-flanking delimiter run.
3966| 
3967| 
3968| A single _ character can open emphasis iff
3969| it is part of a left-flanking delimiter run
3970| and either (a) not part of a right-flanking delimiter run
3971| or (b) part of a right-flanking delimiter run
3972| preceded by punctuation.
3973| 
3974| 
3975| A single * character can close emphasis
3976| iff it is part of a right-flanking delimiter run.
3977| 
3978| 
3979| A single _ character can close emphasis iff
3980| it is part of a right-flanking delimiter run
3981| and either (a) not part of a left-flanking delimiter run
3982| or (b) part of a left-flanking delimiter run
3983| followed by punctuation.
3984| 
3985| 
3986| A double ** can open strong emphasis
3987| iff it is part of a left-flanking delimiter run.
3988| 
3989| 
3990| A double __ can open strong emphasis iff
3991| it is part of a left-flanking delimiter run
3992| and either (a) not part of a right-flanking delimiter run
3993| or (b) part of a right-flanking delimiter run
3994| preceded by punctuation.
3995| 
3996| 
3997| A double ** can close strong emphasis
3998| iff it is part of a right-flanking delimiter run.
3999| 
4000| 
4001| A double __ can close strong emphasis iff
4002| it is part of a right-flanking delimiter run
4003| and either (a) not part of a left-flanking delimiter run
4004| or (b) part of a left-flanking delimiter run
4005| followed by punctuation.
4006| 
4007| 
4008| Emphasis begins with a delimiter that can open emphasis and ends
4009| with a delimiter that can close emphasis, and that uses the same
4010| character (_ or *) as the opening delimiter.  The
4011| opening and closing delimiters must belong to separate
4012| delimiter runs.  If one of the delimiters can both
4013| open and close emphasis, then the sum of the lengths of the
4014| delimiter runs containing the opening and closing delimiters
4015| must not be a multiple of 3 unless both lengths are
4016| multiples of 3.
4017| 
4018| 
4019| Strong emphasis begins with a delimiter that
4020| can open strong emphasis and ends with a delimiter that
4021| can close strong emphasis, and that uses the same character
4022| (_ or *) as the opening delimiter.  The
4023| opening and closing delimiters must belong to separate
4024| delimiter runs.  If one of the delimiters can both open
4025| and close strong emphasis, then the sum of the lengths of
4026| the delimiter runs containing the opening and closing
4027| delimiters must not be a multiple of 3 unless both lengths
4028| are multiples of 3.
4029| 
4030| 
4031| A literal * character cannot occur at the beginning or end of
4032| *-delimited emphasis or **-delimited strong emphasis, unless it
4033| is backslash-escaped.
4034| 
4035| 
4036| A literal _ character cannot occur at the beginning or end of
4037| _-delimited emphasis or __-delimited strong emphasis, unless it
4038| is backslash-escaped.
4039| 
4040| 
4041| Where rules 1–12 above are compatible with multiple parsings,
4042| the following principles resolve ambiguity:
4043| 
4044| 
4045| The number of nestings should be minimized. Thus, for example,
4046| an interpretation <strong>...</strong> is always preferred to
4047| <em><em>...</em></em>.
4048| 
4049| 
4050| An interpretation <em><strong>...</strong></em> is always
4051| preferred to <strong><em>...</em></strong>.
4052| 
4053| 
4054| When two potential emphasis or strong emphasis spans overlap,
4055| so that the second begins before the first ends and ends after
4056| the first ends, the first takes precedence. Thus, for example,
4057| *foo _bar* baz_ is parsed as <em>foo _bar</em> baz_ rather
4058| than *foo <em>bar* baz</em>.
4059| 
4060| 
4061| When there are two potential emphasis or strong emphasis spans
4062| with the same closing delimiter, the shorter one (the one that
4063| opens later) takes precedence. Thus, for example,
4064| **foo **bar baz** is parsed as **foo <strong>bar baz</strong>
4065| rather than <strong>foo **bar baz</strong>.
4066| 
4067| 
4068| Inline code spans, links, images, and HTML tags group more tightly
4069| than emphasis.  So, when there is a choice between an interpretation
4070| that contains one of these elements and one that does not, the
4071| former always wins.  Thus, for example, *[foo*](bar) is
4072| parsed as *<a href="bar">foo*</a> rather than as
4073| <em>[foo</em>](bar).

5976| 6.6Links
5977| 
5978| A link contains link text (the visible text), a link destination
5979| (the URI that is the link destination), and optionally a link title.
5980| There are two basic kinds of links in Markdown.  In inline links the
5981| destination and title are given immediately after the link text.  In
5982| reference links the destination and title are defined elsewhere in
5983| the document.
5984| A link text consists of a sequence of zero or more
5985| inline elements enclosed by square brackets ([ and ]).  The
5986| following rules apply:
5987| 
5988| 
5989| Links may not contain other links, at any level of nesting. If
5990| multiple otherwise valid link definitions appear nested inside each
5991| other, the inner-most definition is used.
5992| 
5993| 
5994| Brackets are allowed in the link text only if (a) they
5995| are backslash-escaped or (b) they appear as a matched pair of brackets,
5996| with an open bracket [, a sequence of zero or more inlines, and
5997| a close bracket ].
5998| 
5999| 
6000| Backtick code spans, autolinks, and raw HTML tags bind more tightly
6001| than the brackets in link text.  Thus, for example,
6002| [foo`]` could not be a link text, since the second ]
6003| is part of a code span.
6004| 
6005| 
6006| The brackets in link text bind more tightly than markers for
6007| emphasis and strong emphasis. Thus, for example, *[foo*](url) is a link.
6008| 
6009| 
6010| A link destination consists of either
6011| 
6012| 
6013| a sequence of zero or more characters between an opening < and a
6014| closing > that contains no line breaks or unescaped
6015| < or > characters, or
6016| 
6017| 
6018| a nonempty sequence of characters that does not start with
6019| <, does not include ASCII space or control characters, and
6020| includes parentheses only if (a) they are backslash-escaped or
6021| (b) they are part of a balanced pair of unescaped parentheses.
6022| (Implementations may impose limits on parentheses nesting to
6023| avoid performance issues, but at least three levels of nesting
6024| should be supported.)
6025| 
6026| 
6027| A link title  consists of either
6028| 
6029| 
6030| a sequence of zero or more characters between straight double-quote
6031| characters ("), including a " character only if it is
6032| backslash-escaped, or
6033| 
6034| 
6035| a sequence of zero or more characters between straight single-quote
6036| characters ('), including a ' character only if it is
6037| backslash-escaped, or
6038| 
6039| 
6040| a sequence of zero or more characters between matching parentheses
6041| ((...)), including a ( or ) character only if it is
6042| backslash-escaped.

6045| Although link titles may span multiple lines, they may not contain
6046| a blank line.
6047| An inline link consists of a link text followed immediately
6048| by a left parenthesis (, optional whitespace, an optional
6049| link destination, an optional link title separated from the link
6050| destination by whitespace, optional whitespace, and a right
6051| parenthesis ). The link’s text consists of the inlines contained
6052| in the link text (excluding the enclosing square brackets).
6053| The link’s URI consists of the link destination, excluding enclosing
6054| <...> if present, with backslash-escapes in effect as described
6055| above.  The link’s title consists of the link title, excluding its
6056| enclosing delimiters, with backslash-escapes in effect as described
6057| above.

6690| There are three kinds of reference links:
6691| full, collapsed,
6692| and shortcut.
6693| A full reference link
6694| consists of a link text immediately followed by a link label
6695| that matches a link reference definition elsewhere in the document.
6696| A link label  begins with a left bracket ([) and ends
6697| with the first right bracket (]) that is not backslash-escaped.
6698| Between these brackets there must be at least one non-whitespace character.
6699| Unescaped square bracket characters are not allowed inside the
6700| opening and closing square brackets of link labels.  A link
6701| label can have at most 999 characters inside the square
6702| brackets.
6703| One label matches
6704| another just in case their normalized forms are equal.  To normalize a
6705| label, strip off the opening and closing brackets,
6706| perform the Unicode case fold, strip leading and trailing
6707| whitespace and collapse consecutive internal
6708| whitespace to a single space.  If there are multiple
6709| matching reference link definitions, the one that comes first in the
6710| document is used.  (It is desirable in such cases to emit a warning.)
6711| The link’s URI and title are provided by the matching link
6712| reference definition.
6713| Here is a simple example:
6714| 
6715| 
6716| Example 536
6717| 
6718| 
6719| [foo][bar]
6720| 
6721| [bar]: /url "title"
6722| 
6723| 
6724| 
6725| <p><a href="/url" title="title">foo</a></p>
6726|

6991| description, which explicitly allows whitespace between the link
6992| text and the link label.  It brings reference links in line with
6993| inline links, which (according to both original Markdown and
6994| this spec) cannot have whitespace after the link text.  More
6995| importantly, it prevents inadvertent capture of consecutive
6996| shortcut reference links. If whitespace is allowed between the
6997| link text and the link label, then in the following we will have
6998| a single reference link, not two shortcut reference links, as
6999| intended:
7000| [foo]
7001| [bar]
7002| 
7003| [foo]: /url1
7004| [bar]: /url2
7005| 
7006| (Note that shortcut reference links were introduced by Gruber
7007| himself in a beta version of Markdown.pl, but never included
7008| in the official syntax description.  Without shortcut reference
7009| links, it is harmless to allow space between the link text and
7010| link label; but once shortcut references are introduced, it is
7011| too dangerous to allow this, as it frequently leads to
7012| unintended results.)
7013| When there are multiple matching link reference definitions,
7014| the first is used:
7015| 
7016| 
7017| Example 553
7018| 
7019| 
7020| [foo]: /url1
7021| 
7022| [foo]: /url2
7023| 
7024| [bar][foo]
7025| 
7026| 
7027| 
7028| <p><a href="/url1">bar</a></p>
7029| 
7030| 
7031| 
7032| Note that matching is performed on normalized strings, not parsed
7033| inline content.  So the following does not match, even though the
7034| labels define equivalent inline content:
7035| 
7036| 
7037| Example 554
7038| 
7039| 
7040| [bar][foo\!]
7041| 
7042| [foo!]: /url
7043| 
7044| 
7045| 
7046| <p>[bar][foo!]</p>
7047| 
7048|

7051| backslash-escaped:
7052|

7058| 
7059| [ref[]: /uri
7060|

7067|

7074|

7076|

7082|

7168| A collapsed reference link
7169| consists of a link label that matches a
7170| link reference definition elsewhere in the
7171| document, followed by the string [].
7172| The contents of the first link label are parsed as inlines,
7173| which are used as the link’s text.  The link’s URI and title are
7174| provided by the matching reference link definition.  Thus,
7175| [foo][] is equivalent to [foo][foo].

7179| 
7180| 
7181| [foo][]
7182| 
7183| [foo]: /url "title"

7204|

7207|

7493| 6.7Images
7494| 
7495| Syntax for images is like the syntax for links, with one
7496| difference. Instead of link text, we have an
7497| image description.  The rules for this are the
7498| same as for link text, except that (a) an
7499| image description starts with ![ rather than [, and
7500| (b) an image description may contain links.
7501| An image description has inline elements
7502| as its contents.  When an image is rendered to HTML,
7503| this is standardly used as the image’s alt attribute.
7504| 
7505| 
7506| Example 581
7507| 
7508| 
7509| ![foo](/url "title")
7510| 
7511| 
7512| 
7513| <p><img src="/url" alt="foo" title="title" /></p>
7514| 
7515| 
7516| 
7517| 
7518| 
7519| Example 582
7520| 
7521| 
7522| ![foo *bar*]
7523| 
7524| [foo *bar*]: train.jpg "train & tracks"
7525| 
7526| 
7527| 
7528| <p><img src="train.jpg" alt="foo bar" title="train &amp; tracks" /></p>
7529| 
7530| 
7531| 
7532| 
7533| 
7534| Example 583
7535| 
7536| 
7537| ![foo ![bar](/url)](/url2)
7538|

7542| 
7543| 
7544| 
7545| 
7546| 
7547| Example 584
7548| 
7549| 
7550| ![foo [bar](/url)](/url2)
7551| 
7552| 
7553| 
7554| <p><img src="/url2" alt="foo bar" /></p>
7555| 
7556| 
7557| 
7558| Though this spec is concerned with parsing, not rendering, it is
7559| recommended that in rendering to HTML, only the plain string content
7560| of the image description be used.  Note that in
7561| the above example, the alt attribute’s value is foo bar, not foo [bar](/url) or foo <a href="/url">bar</a>.  Only the plain string
7562| content is rendered, without formatting.

7841| 6.8Autolinks
7842| 
7843| Autolinks are absolute URIs and email addresses inside
7844| < and >. They are parsed as links, with the URL or email address
7845| as the link label.
7846| A URI autolink consists of <, followed by an
7847| absolute URI followed by >.  It is parsed as
7848| a link to the URI, with the URI as the link’s label.
7849| An absolute URI,
7850| for these purposes, consists of a scheme followed by a colon (:)
7851| followed by zero or more characters other than ASCII
7852| whitespace and control characters, <, and >.  If
7853| the URI includes these characters, they must be percent-encoded
7854| (e.g. %20 for a space).
7855| For purposes of this spec, a scheme is any sequence
7856| of 2–32 characters beginning with an ASCII letter and followed
7857| by any combination of ASCII letters, digits, or the symbols plus
7858| (“+”), period (“.”), or hyphen (“-”).
7859| Here are some valid autolinks:
7860| 
7861| 
7862| Example 603
7863| 
7864| 
7865| <http://foo.bar.baz>
7866| 
7867| 
7868| 
7869| <p><a href="http://foo.bar.baz">http://foo.bar.baz</a></p>
7870| 
7871| 
7872| 
7873| 
7874| 
7875| Example 604
7876| 
7877| 
7878| <http://foo.bar.baz/test?q=hello&id=22&boolean>
7879| 
7880| 
7881| 
7882| <p><a href="http://foo.bar.baz/test?q=hello&amp;id=22&amp;boolean">http://foo.bar.baz/test?q=hello&amp;id=22&amp;boolean</a></p>
7883| 
7884| 
7885| 
7886| 
7887| 
7888| Example 605
7889| 
7890| 
7891| <irc://foo.bar:2233/baz>
7892| 
7893| 
7894| 
7895| <p><a href="irc://foo.bar:2233/baz">irc://foo.bar:2233/baz</a></p>
7896| 
7897| 
7898| 
7899| Uppercase is also fine:
7900| 
7901| 
7902| Example 606
7903| 
7904| 
7905| <MAILTO:FOO@BAR.BAZ>
7906| 
7907| 
7908| 
7909| <p><a href="MAILTO:FOO@BAR.BAZ">MAILTO:FOO@BAR.BAZ</a></p>
7910|

8129| 
8130| 6.9Autolinks (extension)
8131| 
8132| GFM enables the autolink extension, where autolinks will be recognised in a
8133| greater number of conditions.
8134| Autolinks can also be constructed without requiring the use of < and to >
8135| to delimit them, although they will be recognized under a smaller set of
8136| circumstances.  All such recognized autolinks can only come at the beginning of
8137| a line, after whitespace, or any of the delimiting characters *, _, ~,
8138| and (.
8139| An extended www autolink will be recognized
8140| when the text www. is found followed by a valid domain.
8141| A valid domain consists of segments
8142| of alphanumeric characters, underscores (_) and hyphens (-)
8143| separated by periods (.).
8144| There must be at least one period,
8145| and no underscores may be present in the last two segments of the domain.
8146| The scheme http will be inserted automatically:
8147| 
8148| 
8149| Example 622
8150| 
8151| 
8152| www.commonmark.org
8153| 
8154| 
8155| 
8156| <p><a href="http://www.commonmark.org">www.commonmark.org</a></p>
8157| 
8158| 
8159| 
8160| After a valid domain, zero or more non-space non-< characters may follow:
8161| 
8162| 
8163| Example 623
8164| 
8165| 
8166| Visit www.commonmark.org/help for more information.
8167| 
8168| 
8169| 
8170| <p>Visit <a href="http://www.commonmark.org/help">www.commonmark.org/help</a> for more information.</p>
8171| 
8172| 
8173| 
8174| We then apply extended autolink path validation as follows:
8175| Trailing punctuation (specifically, ?, !, ., ,, :, *, _, and ~)
8176| will not be considered part of the autolink, though they may be included in the
8177| interior of the link:
8178| 
8179| 
8180| Example 624
8181| 
8182| 
8183| Visit www.commonmark.org.
8184| 
8185| Visit www.commonmark.org/a.b.
8186| 
8187| 
8188| 
8189| <p>Visit <a href="http://www.commonmark.org">www.commonmark.org</a>.</p>
8190| <p>Visit <a href="http://www.commonmark.org/a.b">www.commonmark.org/a.b</a>.</p>
8191| 
8192| 
8193| 
8194| When an autolink ends in ), we scan the entire autolink for the total number
8195| of parentheses.  If there is a greater number of closing parentheses than
8196| opening ones, we don’t consider the unmatched trailing parentheses part of the
8197| autolink, in order to facilitate including an autolink inside a parenthesis:
8198| 
8199| 
8200| Example 625
8201| 
8202| 
8203| www.google.com/search?q=Markup+(business)
8204| 
8205| www.google.com/search?q=Markup+(business)))
8206| 
8207| (www.google.com/search?q=Markup+(business))
8208| 
8209| (www.google.com/search?q=Markup+(business)
8210| 
8211| 
8212| 
8213| <p><a href="http://www.google.com/search?q=Markup+(business)">www.google.com/search?q=Markup+(business)</a></p>
8214| <p><a href="http://www.google.com/search?q=Markup+(business)">www.google.com/search?q=Markup+(business)</a>))</p>
8215| <p>(<a href="http://www.google.com/search?q=Markup+(business)">www.google.com/search?q=Markup+(business)</a>)</p>
8216| <p>(<a href="http://www.google.com/search?q=Markup+(business)">www.google.com/search?q=Markup+(business)</a></p>
8217| 
8218| 
8219| 
8220| This check is only done when the link ends in a closing parentheses ), so if
8221| the only parentheses are in the interior of the autolink, no special rules are
8222| applied:
8223| 
8224| 
8225| Example 626
8226| 
8227| 
8228| www.google.com/search?q=(business))+ok
8229| 
8230| 
8231| 
8232| <p><a href="http://www.google.com/search?q=(business))+ok">www.google.com/search?q=(business))+ok</a></p>
8233| 
8234| 
8235| 
8236| If an autolink ends in a semicolon (;), we check to see if it appears to
8237| resemble an entity reference; if the preceding text is &
8238| followed by one or more alphanumeric characters.  If so, it is excluded from
8239| the autolink:
8240| 
8241| 
8242| Example 627
8243| 
8244| 
8245| www.google.com/search?q=commonmark&hl=en
8246| 
8247| www.google.com/search?q=commonmark&hl;
8248| 
8249| 
8250| 
8251| <p><a href="http://www.google.com/search?q=commonmark&amp;hl=en">www.google.com/search?q=commonmark&amp;hl=en</a></p>
8252| <p><a href="http://www.google.com/search?q=commonmark">www.google.com/search?q=commonmark</a>&amp;hl;</p>
8253| 
8254| 
8255| 
8256| < immediately ends an autolink.
8257| 
8258| 
8259| Example 628
8260| 
8261| 
8262| www.commonmark.org/he<lp
8263| 
8264| 
8265| 
8266| <p><a href="http://www.commonmark.org/he">www.commonmark.org/he</a>&lt;lp</p>
8267| 
8268| 
8269| 
8270| An extended url autolink will be recognised when one of the schemes
8271| http://, or https://, followed by a valid domain, then zero or
8272| more non-space non-< characters according to
8273| extended autolink path validation:
8274| 
8275| 
8276| Example 629
8277| 
8278| 
8279| http://commonmark.org
8280| 
8281| (Visit https://encrypted.google.com/search?q=Markup+(business))
8282| 
8283| 
8284| 
8285| <p><a href="http://commonmark.org">http://commonmark.org</a></p>
8286| <p>(Visit <a href="https://encrypted.google.com/search?q=Markup+(business)">https://encrypted.google.com/search?q=Markup+(business)</a>)</p>
8287| 
8288| 
8289| 
8290| An extended email autolink will be recognised when an email address is
8291| recognised within any text node.  Email addresses are recognised according to
8292| the following rules:
8293| 
8294| One ore more characters which are alphanumeric, or ., -, _, or +.
8295| An @ symbol.
8296| One or more characters which are alphanumeric, or - or _,
8297| separated by periods (.).
8298| There must be at least one period.
8299| The last character must not be one of - or _.
8300| 
8301| The scheme mailto: will automatically be added to the generated link:
8302| 
8303| 
8304| Example 630
8305| 
8306| 
8307| foo@bar.baz
8308| 
8309| 
8310| 
8311| <p><a href="mailto:foo@bar.baz">foo@bar.baz</a></p>
8312| 
8313| 
8314| 
8315| + can occur before the @, but not after.
8316| 
8317| 
8318| Example 631
8319| 
8320| 
8321| hello@mail+xyz.example isn't valid, but hello+xyz@mail.example is.
8322| 
8323| 
8324| 
8325| <p>hello@mail+xyz.example isn't valid, but <a href="mailto:hello+xyz@mail.example">hello+xyz@mail.example</a> is.</p>
8326| 
8327| 
8328| 
8329| ., -, and _ can occur on both sides of the @, but only . may occur at
8330| the end of the email address, in which case it will not be considered part of
8331| the address:
8332| 
8333| 
8334| Example 632
8335| 
8336| 
8337| a.b-c_d@a.b
8338| 
8339| a.b-c_d@a.b.
8340| 
8341| a.b-c_d@a.b-
8342| 
8343| a.b-c_d@a.b_
8344| 
8345| 
8346| 
8347| <p><a href="mailto:a.b-c_d@a.b">a.b-c_d@a.b</a></p>
8348| <p><a href="mailto:a.b-c_d@a.b">a.b-c_d@a.b</a>.</p>
8349| <p>a.b-c_d@a.b-</p>
8350| <p>a.b-c_d@a.b_</p>
8351| 
8352| 
8353| 
8354| An extended protocol autolink will be recognised when a protocol is
8355| recognised within any text node.  Valid protocols are:
8356| 
8357| mailto:
8358| xmpp:
8359| 
8360| The scheme of the protocol will automatically be added to the generated link.
8361| All the rules of email address autolinking apply.
8362| 
8363| 
8364| Example 633
8365| 
8366| 
8367| mailto:foo@bar.baz
8368| 
8369| mailto:a.b-c_d@a.b
8370| 
8371| mailto:a.b-c_d@a.b.
8372| 
8373| mailto:a.b-c_d@a.b/
8374| 
8375| mailto:a.b-c_d@a.b-
8376| 
8377| mailto:a.b-c_d@a.b_
8378| 
8379| xmpp:foo@bar.baz
8380| 
8381| xmpp:foo@bar.baz.
8382| 
8383| 
8384| 
8385| <p><a href="mailto:foo@bar.baz">mailto:foo@bar.baz</a></p>
8386| <p><a href="mailto:a.b-c_d@a.b">mailto:a.b-c_d@a.b</a></p>
8387| <p><a href="mailto:a.b-c_d@a.b">mailto:a.b-c_d@a.b</a>.</p>
8388| <p><a href="mailto:a.b-c_d@a.b">mailto:a.b-c_d@a.b</a>/</p>
8389| <p>mailto:a.b-c_d@a.b-</p>
8390| <p>mailto:a.b-c_d@a.b_</p>
8391| <p><a href="xmpp:foo@bar.baz">xmpp:foo@bar.baz</a></p>
8392| <p><a href="xmpp:foo@bar.baz">xmpp:foo@bar.baz</a>.</p>

8397| xmpp offers an optional / followed by a resource. The resource can contain

8434| 6.10Raw HTML
8435| 
8436| Text between < and > that looks like an HTML tag is parsed as a
8437| raw HTML tag and will be rendered in HTML without escaping.
8438| Tag and attribute names are not limited to current HTML tags,
8439| so custom tags (and even, say, DocBook tags) may be used.
8440| Here is the grammar for tags:
8441| A tag name consists of an ASCII letter
8442| followed by zero or more ASCII letters, digits, or
8443| hyphens (-).
8444| An attribute consists of whitespace,
8445| an attribute name, and an optional
8446| attribute value specification.
8447| An attribute name
8448| consists of an ASCII letter, _, or :, followed by zero or more ASCII
8449| letters, digits, _, ., :, or -.  (Note:  This is the XML
8450| specification restricted to ASCII.  HTML5 is laxer.)
8451| An attribute value specification
8452| consists of optional whitespace,
8453| a = character, optional whitespace, and an attribute
8454| value.
8455| An attribute value
8456| consists of an unquoted attribute value,
8457| a single-quoted attribute value, or a double-quoted attribute value.
8458| An unquoted attribute value
8459| is a nonempty string of characters not
8460| including whitespace, ", ', =, <, >, or `.
8461| A single-quoted attribute value
8462| consists of ', zero or more
8463| characters not including ', and a final '.
8464| A double-quoted attribute value
8465| consists of ", zero or more
8466| characters not including ", and a final ".
8467| An open tag consists of a < character, a tag name,
8468| zero or more attributes, optional whitespace, an optional /
8469| character, and a > character.
8470| A closing tag consists of the string </, a
8471| tag name, optional whitespace, and the character >.
8472| An HTML comment consists of <!-- + text + -->,
8473| where text does not start with > or ->, does not end with -,
8474| and does not contain --.  (See the
8475| HTML5 spec.)
8476| A processing instruction
8477| consists of the string <?, a string
8478| of characters not including the string ?>, and the string
8479| ?>.
8480| A declaration consists of the
8481| string <!, a name consisting of one or more uppercase ASCII letters,
8482| whitespace, a string of characters not including the
8483| character >, and the character >.
8484| A CDATA section consists of
8485| the string <![CDATA[, a string of characters not including the string
8486| ]]>, and the string ]]>.
8487| An HTML tag consists of an open tag, a closing tag,
8488| an HTML comment, a processing instruction, a declaration,
8489| or a CDATA section.
8490| Here are some simple open tags:
8491|

9075| 6.13Soft line breaks
9076| 
9077| A regular line break (not in a code span or HTML tag) that is not
9078| preceded by two or more spaces or a backslash is parsed as a
9079| softbreak.  (A softbreak may be rendered in HTML either as a
9080| line ending or as a space. The result will be the same in
9081| browsers. In the examples here, a line ending will be used.)
9082| 
9083| 
9084| Example 673
9085| 
9086| 
9087| foo
9088| baz
9089| 
9090| 
9091| 
9092| <p>foo
9093| baz</p>
9094| 
9095| 
9096| 
9097| Spaces at the end of the line and beginning of the next line are
9098| removed:
9099| 
9100| 
9101| Example 674
9102| 
9103| 
9104| foo 
9105|  baz
9106| 
9107| 
9108| 
9109| <p>foo
9110| baz</p>
9111| 
9112| 
9113| 
9114| A conforming parser may render a soft line break in HTML either as a
9115| line break or as a space.
9116| A renderer may also provide an option to render soft line breaks
9117| as hard line breaks.

9166| Appendix: A parsing strategy
9167| 
9168| 
9169| In this appendix we describe some features of the parsing strategy
9170| used in the CommonMark reference implementations.
9171| 
9172| Overview
9173| 
9174| Parsing has two phases:
9175| 
9176| 
9177| In the first phase, lines of input are consumed and the block
9178| structure of the document—its division into paragraphs, block quotes,
9179| list items, and so on—is constructed.  Text is assigned to these
9180| blocks but not parsed. Link reference definitions are parsed and a
9181| map of links is constructed.
9182| 
9183| 
9184| In the second phase, the raw text contents of paragraphs and headings
9185| are parsed into sequences of Markdown inline elements (strings,
9186| code spans, links, emphasis, and so on), using the map of link
9187| references constructed in phase 1.
9188| 
9189| 
9190| At each point in processing, the document is represented as a tree of
9191| blocks.  The root of the tree is a document block.  The document
9192| may have any number of other blocks as children.  These children
9193| may, in turn, have other blocks as children.  The last child of a block
9194| is normally considered open, meaning that subsequent lines of input
9195| can alter its contents.  (Blocks that are not open are closed.)
9196| Here, for example, is a possible document tree, with the open blocks
9197| marked by arrows:
9198| -> document
9199|   -> block_quote
9200|        paragraph
9201|          "Lorem ipsum dolor\nsit amet."
9202|     -> list (type=bullet tight=true bullet_char=-)
9203|          list_item
9204|            paragraph
9205|              "Qui *quodsi iracundia*"
9206|       -> list_item
9207|         -> paragraph
9208|              "aliquando id"
9209| 
9210| 
9211| Phase 1: block structure
9212| 
9213| Each line that is processed has an effect on this tree.  The line is
9214| analyzed and, depending on its contents, the document may be altered
9215| in one or more of the following ways:
9216| 
9217| One or more open blocks may be closed.
9218| One or more new blocks may be created as children of the
9219| last open block.
9220| Text may be added to the last (deepest) open block remaining
9221| on the tree.
9222| 
9223| Once a line has been incorporated into the tree in this way,
9224| it can be discarded, so input can be read in a stream.
9225| For each line, we follow this procedure:
9226| 
9227| 
9228| First we iterate through the open blocks, starting with the
9229| root document, and descending through last children down to the last
9230| open block.  Each block imposes a condition that the line must satisfy
9231| if the block is to remain open.  For example, a block quote requires a
9232| > character.  A paragraph requires a non-blank line.
9233| In this phase we may match all or just some of the open
9234| blocks.  But we cannot close unmatched blocks yet, because we may have a
9235| lazy continuation line.
9236| 
9237| 
9238| Next, after consuming the continuation markers for existing
9239| blocks, we look for new block starts (e.g. > for a block quote).
9240| If we encounter a new block start, we close any blocks unmatched
9241| in step 1 before creating the new block as a child of the last
9242| matched block.
9243| 
9244| 
9245| Finally, we look at the remainder of the line (after block
9246| markers like >, list markers, and indentation have been consumed).
9247| This is text that can be incorporated into the last open
9248| block (a paragraph, code block, heading, or raw HTML).
9249| 
9250| 
9251| Setext headings are formed when we see a line of a paragraph
9252| that is a setext heading underline.
9253| Reference link definitions are detected when a paragraph is closed;
9254| the accumulated text lines are parsed to see if they begin with
9255| one or more reference link definitions.  Any remainder becomes a
9256| normal paragraph.
9257| We can see how this works by considering how the tree above is
9258| generated by four lines of Markdown:
9259| > Lorem ipsum dolor
9260| sit amet.
9261| > - Qui *quodsi iracundia*
9262| > - aliquando id
9263| 
9264| At the outset, our document model is just
9265| -> document
9266| 
9267| The first line of our text,
9268| > Lorem ipsum dolor
9269| 
9270| causes a block_quote block to be created as a child of our
9271| open document block, and a paragraph block as a child of
9272| the block_quote.  Then the text is added to the last open
9273| block, the paragraph:
9274| -> document
9275|   -> block_quote
9276|     -> paragraph
9277|          "Lorem ipsum dolor"
9278| 
9279| The next line,
9280| sit amet.
9281| 
9282| is a “lazy continuation” of the open paragraph, so it gets added
9283| to the paragraph’s text:
9284| -> document
9285|   -> block_quote
9286|     -> paragraph
9287|          "Lorem ipsum dolor\nsit amet."
9288| 
9289| The third line,
9290| > - Qui *quodsi iracundia*
9291| 
9292| causes the paragraph block to be closed, and a new list block
9293| opened as a child of the block_quote.  A list_item is also
9294| added as a child of the list, and a paragraph as a child of
9295| the list_item.  The text is then added to the new paragraph:
9296| -> document
9297|   -> block_quote
9298|        paragraph
9299|          "Lorem ipsum dolor\nsit amet."
9300|     -> list (type=bullet tight=true bullet_char=-)
9301|       -> list_item
9302|         -> paragraph
9303|              "Qui *quodsi iracundia*"
9304| 
9305| The fourth line,
9306| > - aliquando id
9307| 
9308| causes the list_item (and its child the paragraph) to be closed,
9309| and a new list_item opened up as child of the list.  A paragraph
9310| is added as a child of the new list_item, to contain the text.
9311| We thus obtain the final tree:
9312| -> document
9313|   -> block_quote
9314|        paragraph
9315|          "Lorem ipsum dolor\nsit amet."
9316|     -> list (type=bullet tight=true bullet_char=-)
9317|          list_item
9318|            paragraph
9319|              "Qui *quodsi iracundia*"
9320|       -> list_item
9321|         -> paragraph
9322|              "aliquando id"
9323| 
9324| 
9325| Phase 2: inline structure
9326| 
9327| Once all of the input has been parsed, all open blocks are closed.
9328| We then “walk the tree,” visiting every node, and parse raw
9329| string contents of paragraphs and headings as inlines.  At this
9330| point we have seen all the link reference definitions, so we can
9331| resolve reference links as we go.
9332| document
9333|   block_quote
9334|     paragraph
9335|       str "Lorem ipsum dolor"
9336|       softbreak
9337|       str "sit amet."
9338|     list (type=bullet tight=true bullet_char=-)
9339|       list_item
9340|         paragraph
9341|           str "Qui "
9342|           emph
9343|             str "quodsi iracundia"
9344|       list_item
9345|         paragraph
9346|           str "aliquando id"
9347| 
9348| Notice how the line ending in the first paragraph has
9349| been parsed as a softbreak, and the asterisks in the first list item
9350| have become an emph.
9351| 
9352| An algorithm for parsing nested emphasis and links
9353| 
9354| By far the trickiest part of inline parsing is handling emphasis,
9355| strong emphasis, links, and images.  This is done using the following
9356| algorithm.
9357| When we’re parsing inlines and we hit either
9358| 
9359| a run of * or _ characters, or
9360| a [ or ![
9361| 
9362| we insert a text node with these symbols as its literal content, and we
9363| add a pointer to this text node to the delimiter stack.
9364| The delimiter stack is a doubly linked list.  Each
9365| element contains a pointer to a text node, plus information about
9366| 
9367| the type of delimiter ([, ![, *, _)
9368| the number of delimiters,
9369| whether the delimiter is “active” (all are active to start), and
9370| whether the delimiter is a potential opener, a potential closer,
9371| or both (which depends on what sort of characters precede
9372| and follow the delimiters).
9373| 
9374| When we hit a ] character, we call the look for link or image
9375| procedure (see below).
9376| When we hit the end of the input, we call the process emphasis
9377| procedure (see below), with stack_bottom = NULL.
9378| 
9379| look for link or image
9380| 
9381| Starting at the top of the delimiter stack, we look backwards
9382| through the stack for an opening [ or ![ delimiter.
9383| 
9384| 
9385| If we don’t find one, we return a literal text node ].
9386| 
9387| 
9388| If we do find one, but it’s not active, we remove the inactive
9389| delimiter from the stack, and return a literal text node ].
9390| 
9391| 
9392| If we find one and it’s active, then we parse ahead to see if
9393| we have an inline link/image, reference link/image, compact reference
9394| link/image, or shortcut reference link/image.
9395| 
9396| 
9397| If we don’t, then we remove the opening delimiter from the
9398| delimiter stack and return a literal text node ].
9399| 
9400| 
9401| If we do, then
9402| 
9403| 
9404| We return a link or image node whose children are the inlines
9405| after the text node pointed to by the opening delimiter.
9406| 
9407| 
9408| We run process emphasis on these inlines, with the [ opener
9409| as stack_bottom.
9410| 
9411| 
9412| We remove the opening delimiter.
9413| 
9414| 
9415| If we have a link (and not an image), we also set all
9416| [ delimiters before the opening delimiter to inactive.  (This
9417| will prevent us from getting links within links.)
9418| 
9419| 
9420| 
9421| 
9422| 
9423| 
9424| 
9425| process emphasis
9426| 
9427| Parameter stack_bottom sets a lower bound to how far we
9428| descend in the delimiter stack.  If it is NULL, we can
9429| go all the way to the bottom.  Otherwise, we stop before
9430| visiting stack_bottom.
9431| Let current_position point to the element on the delimiter stack
9432| just above stack_bottom (or the first element if stack_bottom
9433| is NULL).
9434| We keep track of the openers_bottom for each delimiter
9435| type (*, _) and each length of the closing delimiter run
9436| (modulo 3).  Initialize this to stack_bottom.
9437| Then we repeat the following until we run out of potential
9438| closers:
9439| 
9440| 
9441| Move current_position forward in the delimiter stack (if needed)
9442| until we find the first potential closer with delimiter * or _.
9443| (This will be the potential closer closest
9444| to the beginning of the input – the first one in parse order.)
9445| 
9446| 
9447| Now, look back in the stack (staying above stack_bottom and
9448| the openers_bottom for this delimiter type) for the
9449| first matching potential opener (“matching” means same delimiter).
9450| 
9451| 
9452| If one is found:
9453| 
9454| 
9455| Figure out whether we have emphasis or strong emphasis:
9456| if both closer and opener spans have length >= 2, we have
9457| strong, otherwise regular.
9458| 
9459| 
9460| Insert an emph or strong emph node accordingly, after
9461| the text node corresponding to the opener.
9462| 
9463| 
9464| Remove any delimiters between the opener and closer from
9465| the delimiter stack.
9466| 
9467| 
9468| Remove 1 (for regular emph) or 2 (for strong emph) delimiters
9469| from the opening and closing text nodes.  If they become empty
9470| as a result, remove them and remove the corresponding element
9471| of the delimiter stack.  If the closing node is removed, reset
9472| current_position to the next element in the stack.
9473| 
9474| 
9475| 
9476| 
9477| If none is found:
9478| 
9479| 
9480| Set openers_bottom to the element before current_position.
9481| (We know that there are no openers for this kind of closer up to and
9482| including this point, so this puts a lower bound on future searches.)
9483| 
9484| 
9485| If the closer at current_position is not a potential opener,
9486| remove it from the delimiter stack (since we know it can’t
9487| be a closer either).
9488| 
9489| 
9490| Advance current_position to the next element in the stack.
9491| 
9492| 
9493| 
9494| 
9495| After we’re done, we remove all delimiters above stack_bottom from the
9496| delimiter stack.
9497|
