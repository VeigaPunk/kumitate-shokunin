こんにちは！ブロックチェーン×AI Agentで自律経済圏を創るKomlock labでエンジニアをしている小原（@brto_0224）です。

https://x.com/claudedevs/status/2082164248697069935

MCPが2026年7月28日に大型アップデートされた、という話を見かけて調べてみました。公開された2026-07-28仕様はMCP発足以来もっとも大きな仕様変更で、通信の土台が作り直されたほか、認可の強化や複数機能の非推奨化まで含みます。この記事では公式ブログと仕様書の内容を整理しつつ、実際にTypeScript SDK v2（2026-07-28仕様の実装）を動かして確認したことをまとめます。

先に結論だけ書いておくと

  • MCPは各リクエストが完結した「1発リクエスト・レスポンス」モデルに変わった。initializeハンドシェイクとMcp-Session-Idが仕様から削除された
  • 状態が必要な処理は、サーバーが発行する「ハンドル」をクライアントが引数として持ち回る設計に変わった
  • ステートフルなSSEストリームに頼っていた「実行中にユーザー入力が必要になる」ケースは、requestStateを持ち回りながら呼び出しをリトライするMulti Round-Trip Requestsという仕組みに置き換わった
  • Roots・Sampling・Loggingはコア機能から非推奨に。ただし12ヶ月の移行期間が明示されている
  • 認可まわりはRFC 9207準拠のissuer検証やCIMDへの移行など、地味だが重要な締め付けが入った
  • 2026-07-28仕様の実装は、旧来の@modelcontextprotocol/sdk（v1）とは別パッケージのv2系（@modelcontextprotocol/serverなど）に切り出されている

対象読者

  • 「MCPが大型アップデートされた」という話を聞いたけど詳細を追えていない人
  • 自分でMCPサーバーやクライアントを実装・運用している人
  • 最新のMCP仕様を実際に触ってみたい人

アップデート前のMCPは何が課題だったか

本題に入る前に、この記事で何度も出てくる3つの言葉を先に説明しておきます。

  • ハンドシェイク: 通信前にやる「お互いの自己紹介・すり合わせ」です。対応バージョンや機能を最初に1往復確認してから、本題のやり取りに入ります。
  • ステートフル / ステートレス: ステートフルは「サーバーが過去のやり取りを覚えている前提」、ステートレスは「毎回のリクエストがそれ単体で完結する前提」です。窓口に例えると、ステートフルは番号札で続きが通じる窓口、ステートレスは毎回一から説明が必要な窓口です。
  • SSE（Server-Sent Events）: サーバーからクライアントへ、1本のHTTP接続を張ったまま一方向にイベントを送り続ける仕組みです。普通のHTTPが「リクエスト1回・レスポンス1回」で終わるのに対し、SSEは接続を維持したまま複数回イベントを流せます。双方向のWebSocketとは違い、あくまでサーバー→クライアントの一方向です。

これまでのMCP（Streamable HTTPトランスポート）では、最初にinitializeリクエストを送ってサーバーと機能をすり合わせるハンドシェイクが必須でした。このときMcp-Session-Idを発行するかどうかは仕様上MAY（任意）で、sessionIdGenerator: undefinedを指定すればセッションIDを発行しないステートレスなサーバーも以前から作れました。

とはいえセッションを使う構成では、サーバーが返すMcp-Session-Idをクライアントが以降のリクエストに付け続け、同じIDを持つリクエストは同じサーバーインスタンス（または状態を共有するインスタンス群）で処理する必要がありました。これが実運用だと結構つらくて、

  • セッションを利用する水平分散構成では、ロードバランサーに sticky session（同じ接続を同じインスタンスに固定するルーティング）が必要
  • インスタンスを増やすなら、その状態を共有するストアも必要
  • サーバーレス環境やエッジ環境と相性が悪い

といった問題が指摘されていました。今回のアップデートでMCPの仕様策定チームは、「セッションを使うかどうか」ではなくinitializeハンドシェイクという概念自体を仕様から取り除く方向に振り切りました。

2026-07-28仕様で何が変わったか

公式ブログ（The 2026-07-28 Specification）とリリース候補版の記事、それに実際に動かしたTypeScript SDK v2のソースを読んで整理した内容です。以下に出てくるSEP番号の詳細は公式changelogにまとまっています。

ハンドシェイク廃止（SEP-2567 / SEP-2575）

initialize/initializedのハンドシェイクとMcp-Session-Idヘッダーが仕様から削除されました。代わりに、各リクエストが単体で完結するようになり、プロトコルバージョンやクライアント機能は_metaフィールドに載せて毎回送ります。事前のハンドシェイクがなくなった分、「サーバーが何のツール・リソースを持っているか」をハンドシェイクなしに知る手段としてserver/discoverが新設されています。

POST /mcp HTTP/1.1
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: search

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "search",
    "arguments": { "q": "otters" },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {},
      "io.modelcontextprotocol/clientInfo": { "name": "my-app", "version": "1.0" }
    }
  }
}

_metaのprotocolVersionとclientCapabilitiesは必須です。これは公式ブログのサンプルには明記されていなかったのですが、後述するように実際にTypeScript SDK v2にリクエストを投げて欠けていることに気づきました。

これにより、どのリクエストをどのサーバーインスタンスに振り分けても問題なくなります。単純なラウンドロビンのロードバランサーで複数インスタンスを並べるだけで運用できて、MCPのプロトコルセッションを維持するためのsticky sessionや共有ストアは不要になります。ただし、買い物かごのようなアプリケーション自身の状態を保存する仕組み（DBなど）は、当然ながら別途必要です。

状態が必要な処理（買い物かごに商品を追加していく、みたいなケース）はどうするかというと、サーバーがツールの戻り値としてハンドル（例: basket_id）を返し、クライアントが次の呼び出しの引数としてそれを渡す、という明示的な受け渡しに変わります。プロトコルが暗黙に状態を持つのではなく、アプリケーション層で状態をやり取りする形です。

Multi Round-Trip Requests（MRTR、SEP-2260 / SEP-2322）

ステートレスになったことで困るのが、「ツール実行中にユーザーへの確認や追加入力が必要になる」ケースです。これまではSSEストリームを張りっぱなしにして双方向でやり取りする実装が多かったのですが、それ自体がステートフルな仕組みでした。

新しい仕組みでは、サーバーがresultType: "input_required"と一緒にrequestStateという文字列を返し、クライアントはinputResponsesと受け取ったrequestStateをそのまま添えて同じ呼び出しをリトライします。ストリームを維持する代わりに「途中状態をリクエストの中に折りたたんで持ち回る」ことで、別のサーバーインスタンスが続きを処理できるようにしています。

requestStateはクライアントを経由して戻ってくる、いわば信用できない入力です。実際にTypeScript SDK v2のソースを読むと、HMAC-SHA256などでこの値に署名し、対象ユーザー・元の引数・有効期限にひも付けて改ざんを防ぐためのrequestStateCodecという仕組みが用意されていました。決済の承認や追加認証を挟むような処理では、この改ざん耐性はかなり重要になりそうです。

なお、SSE自体がなくなったわけではありません。各リクエストにひも付く進捗通知や、subscriptions/listenによる変更通知では、引き続きSSEが使われます。廃止されたのは、セッションをまたいで維持するGETストリームや、そこへ独立したサーバー発のリクエストを流す仕組みの方です。

ヘッダーベースルーティング（SEP-2243）

Streamable HTTPでは、すべてのリクエストにMcp-Methodヘッダーが必須になりました。さらにtools/call・resources/read・prompts/getの3つでは、対象名を示すMcp-Nameヘッダーも必要です（実際にTypeScript SDK v2のソースを確認したところ、この3メソッドだけが対象でした）。ゲートウェイやWAF、レートリミッターがJSONボディをパースしなくても、ヘッダーだけを見てルーティングや計測ができるようになります。

キャッシュ可能なlist系レスポンス（SEP-2549）

tools/list・prompts/list・resources/list・resources/templates/list・resources/readにttlMsとcacheScopeが追加されました。ツール一覧のような滅多に変わらない情報を毎回律儀に取りに行かなくてよくなります。

認可の締め付け

地味に一番実務に効きそうなのがこのあたりです。

  • RFC 9207準拠のissuer検証（SEP-2468）: 認可サーバーはissパラメータを返すことがSHOULD（推奨）とされ、クライアントはトークン交換前にそれを検証する。認可サーバー混在攻撃（mix-up attack）対策
  • Dynamic Client Registration（DCR）の非推奨化: 正式に非推奨となり、Client ID Metadata Documents（CIMD）が新標準に。DCRは後方互換のため当面は動作し、将来のバージョンで削除予定
  • クライアント認証情報の発行者バインディング（SEP-2352）: ある認可サーバーで発行された認証情報を、別の認可サーバーに使い回せないようにする

OAuthまわりを自前で書いている人はこのへんの変更を追っておく必要がありそうです。

非推奨になったコア機能（SEP-2577）

Roots・Sampling・Loggingの3つがコア機能から非推奨になりました。代替はそれぞれツールパラメータ/サーバー設定、LLMプロバイダーAPIの直接統合、stderrまたはOpenTelemetryです。あわせてレガシーなHTTP+SSEトランスポートも非推奨に。

重要なのは、新規実装での採用は非推奨だが、少なくとも12ヶ月は仕様から削除されないという明示的なポリシーが敷かれたことです。今回のリリース自体は「これ以降は破壊的変更を避けるための土台」という位置づけのようで、拡張機能フレームワーク（io.modelcontextprotocol/tasksなど）としてTasksのような機能をコアから切り離し、今後はコアを壊さずに拡張していく方針に見えます。

このほかの変更点（この記事では深掘りしません）

このほかにも、Extensions frameworkの正式化、MCP Apps（サーバーがサンドボックスHTML UIを配信する仕組み）、Tasksの拡張機能化、ツールスキーマのJSON Schema 2020-12完全対応、W3C Trace Contextへの準拠、list結果の順序の決定性など、細かい変更が多数含まれています。本記事ではステートレス化を中心に扱うので、気になる方は公式ブログを直接あたってください。

実際にTypeScript SDK v2で2026-07-28仕様を試す

仕様を読むだけだと実感が湧かないので、2026-07-28仕様を実装しているTypeScript SDK v2でサーバーを立てて動かしてみました。typescript-sdkリポジトリのREADMEと2026-07-28対応ガイドによると、v2は次のパッケージに分かれています。

  • @modelcontextprotocol/server
  • @modelcontextprotocol/client
  • @modelcontextprotocol/core（Zodスキーマ）
  • @modelcontextprotocol/node（Node.js用トランスポート）
  • Express・Hono・Fastify向けのフレームワークアダプター

v2で「送金前に確認が要るツール」を書く

Mcp-Session-Idが無いことを確認するだけだと味気ないので、MRTRの節で説明した「実行中にユーザー確認が必要になるケース」を、実際に動くコードで検証してみることにしました。送金前に確認を挟むtransferツールを作って、確認を挟んだ途中でサーバープロセスをまるごとkill -9し、別プロセスに送金を完了させる、というちょっと意地の悪い実験です。

npm install @modelcontextprotocol/server @modelcontextprotocol/node @modelcontextprotocol/express zod
transfer-server.mjs
import { createMcpExpressApp } from "@modelcontextprotocol/express";
import { toNodeHandler } from "@modelcontextprotocol/node";
import { McpServer, createMcpHandler, inputRequired, acceptedContent } from "@modelcontextprotocol/server";
import * as z from "zod";

const factory = () => {
  const server = new McpServer({ name: "transfer-demo", version: "1.0.0" });

  server.registerTool(
    "transfer",
    {
      description: "指定した宛先に送金する（実行前に確認が必要）",
      inputSchema: { to: z.string(), amount: z.number() },
    },
    async ({ to, amount }, ctx) => {
      const confirmed = acceptedContent(ctx.mcpReq.inputResponses, "confirm");

      if (!confirmed) {
        const pending = Buffer.from(JSON.stringify({ to, amount })).toString("base64url");
        return inputRequired({
          inputRequests: {
            confirm: inputRequired.elicit({
              message: `${to}に${amount}円送金します。よろしいですか？`,
              requestedSchema: {
                type: "object",
                properties: { confirm: { type: "boolean" } },
                required: ["confirm"],
              },
            }),
          },
          requestState: pending,
        });
      }

      // 確認後は requestState "だけ" から元の送金内容を復元する（再送された引数は見ない）
      const raw = ctx.mcpReq.requestState();
      const { to: savedTo, amount: savedAmount } = JSON.parse(Buffer.from(raw, "base64url").toString());
      return {
        content: [{ type: "text", text: `[pid ${process.pid}] ${savedTo}に${savedAmount}円送金しました` }],
      };
    }
  );

  return server;
};

const handler = createMcpHandler(factory);
const app = createMcpExpressApp();
const nodeHandler = toNodeHandler(handler);
app.post("/mcp", (req, res) => nodeHandler(req, res, req.body));

app.listen(3002, () => console.log(`[pid ${process.pid}] listening on :3002`));

ポイントは、確認が取れる前はacceptedContent()がundefinedを返すのでinputRequired()でresultType: "input_required"を返す、というところと、送金先・金額をrequestStateという文字列に詰め込んで返している点です。確認後の2回目の呼び出しでは、送金内容（宛先・金額）をrequestStateから復元しています。レスポンス文にもprocess.pidを混ぜて、どのプロセスが処理したか分かるようにしました。

このデモのrequestStateはBase64化しているだけで、署名はしていません。あくまで説明用の簡略化で、本番でこのパターンを使う場合はMRTR節で触れたrequestStateCodecなどできちんと署名・検証し、改ざんされていないことを確認する必要があります。

node transfer-server.mjsで起動すると、次のようにpidが表示されます。

[pid 10339] listening on :3002

まずは普通に呼び出します。「elicitation」は、サーバーがクライアントに対して追加入力（今回で言う確認ダイアログ）を要求できる、という意味の機能です。このtransferツールは確認を求めるためにelicitation/createを使うので、クライアント側がclientCapabilitiesで「elicitationに対応している」と宣言していないと、サーバーはそもそも確認を求められません（宣言なしで呼ぶと、後述の_meta不足エラーとは別に「Cannot request input」という400が返ってきます）。

curl -s -i -X POST http://localhost:3002/mcp \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "MCP-Protocol-Version: 2026-07-28" \
  -H "Mcp-Method: tools/call" \
  -H "Mcp-Name: transfer" \
  -d '{
    "jsonrpc":"2.0","id":1,"method":"tools/call",
    "params":{
      "name":"transfer",
      "arguments":{"to":"komlock-lab","amount":50000},
      "_meta":{
        "io.modelcontextprotocol/protocolVersion":"2026-07-28",
        "io.modelcontextprotocol/clientCapabilities":{"elicitation":{"form":{}}}
      }
    }
  }'

HTTP/1.1 200 OK

{"result":{"resultType":"input_required","inputRequests":{"confirm":{"method":"elicitation/create","params":{"message":"komlock-labに50000円送金します。よろしいですか？","requestedSchema":{"type":"object","properties":{"confirm":{"type":"boolean"}},"required":["confirm"]},"mode":"form"}}},"requestState":"eyJ0byI6ImtvbWxvY2stbGFiIiwiYW1vdW50Ijo1MDAwMH0","_meta":{"io.modelcontextprotocol/serverInfo":{"name":"transfer-demo","version":"1.0.0"}}},"jsonrpc":"2.0","id":1}

送金は実行されず、「confirmしてください」というinput_requiredと、requestStateという謎の文字列が返ってきました。ここからが本番です。このrequestStateだけをメモして、さっきリクエストを処理したプロセス（pid 10339）をkill -9で問答無用で落とします。

kill -9 10339

その上で、同じマシンの別プロセスとしてサーバーを起動し直します。

[pid 11778] listening on :3002

前のプロセスから、メモリやセッション情報は何も引き継ぎません。2回目の処理に必要な送金内容は、クライアントが返したrequestStateから復元します。

  • 引き継ぐもの: requestStateとユーザーの確認結果（inputResponses）
  • 引き継がないもの: Mcp-Session-Id、前プロセスのメモリ、セッションストア

新しく上がった別プロセスに向けて、確認済みのinputResponsesとrequestStateを添えて同じ呼び出しをリトライします。

curl -s -i -X POST http://localhost:3002/mcp \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "MCP-Protocol-Version: 2026-07-28" \
  -H "Mcp-Method: tools/call" \
  -H "Mcp-Name: transfer" \
  -d '{
    "jsonrpc":"2.0","id":2,"method":"tools/call",
    "params":{
      "name":"transfer",
      "arguments":{"to":"komlock-lab","amount":50000},
      "inputResponses":{"confirm":{"action":"accept","content":{"confirm":true}}},
      "requestState":"eyJ0byI6ImtvbWxvY2stbGFiIiwiYW1vdW50Ijo1MDAwMH0",
      "_meta":{
        "io.modelcontextprotocol/protocolVersion":"2026-07-28",
        "io.modelcontextprotocol/clientCapabilities":{"elicitation":{"form":{}}}
      }
    }
  }'

HTTP/1.1 200 OK

{"result":{"content":[{"type":"text","text":"[pid 11778] komlock-labに50000円送金しました"}],"resultType":"complete","_meta":{"io.modelcontextprotocol/serverInfo":{"name":"transfer-demo","version":"1.0.0"}}},"jsonrpc":"2.0","id":2}

[pid 11778]と表示されている通り、最初にリクエストを受けたpid 10339はもうこの世に存在しません。にもかかわらず、まったく別の、しかも最初のリクエストの存在すら知らないプロセスが「komlock-labに50000円」という送金内容を正しく思い出して処理を完了しています。種を明かせば当たり前で、送金内容はrequestStateという文字列としてリクエストの中に丸ごと入っていただけなのですが、実際にプロセスを殺してから続きを別プロセスに処理させてみると、「サーバーはリクエストの外側に何も覚えていない」というステートレスの意味がようやく実感できました。

ちなみに_metaを丸ごと省いて叩くと、こちらもさっきと同じように"missing":["_meta"]という400が返ってきます。envelopeの必須チェックはツールの種類によらず共通のようです。

v2サーバーは旧クライアントもそのまま受け付ける

もうひとつ興味深かったのが、createMcpHandlerはlegacy: 'reject'を指定しない限り、initializeハンドシェイクを送ってくる旧来（v1）のクライアントもそのまま処理してくれることです。

curl -s -i -X POST http://localhost:3002/mcp \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"legacy-client","version":"1.0"}}}'

HTTP/1.1 200 OK
content-type: text/event-stream

event: message
data: {"result":{"protocolVersion":"2025-06-18","capabilities":{"tools":{"listChanged":true}},"serverInfo":{"name":"transfer-demo","version":"1.0.0"}},"jsonrpc":"2.0","id":1}

同じサーバー実装が、新しいステートレスなクライアントと古いハンドシェイク前提のクライアントの両方を捌けるようになっていました。移行期間中はこの後方互換がかなり効きそうです。

まとめ

  • MCPは2026-07-28仕様でinitializeハンドシェイクとMcp-Session-Idを廃止し、ステートレスなプロトコルに舵を切った
  • 状態管理はプロトコルの外（ハンドルやrequestStateの受け渡し）に押し出され、SSEに頼っていた双方向のやり取りはリクエストのリトライ（MRTR）に置き換わった
  • Roots・Sampling・Loggingの非推奨、認可まわりの締め付けなど、細かい変更も多いが12ヶ月の移行期間が明示されている
  • 2026-07-28仕様はTypeScript SDK v2（@modelcontextprotocol/serverなど）に実装されている。v2サーバーは旧クライアントとの後方互換も持つ
  • 実際に叩いてみると、_metaの必須キーのチェックやinput_required+requestStateのやり取りまで含めて、仕様書の記述通りに動いていることが確認できた

破壊的変更ではありますが、今後同じレベルの破壊を繰り返さないための土台作りという位置づけのようです。
