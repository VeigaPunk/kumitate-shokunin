MCP 2026-07-28 规范修订：无状态化重构、授权收紧与扩展分层

The MCP 2026-07-28 Specification Revision
H Haning 2026-07-30 · 阅读 34 MIN

Model Context Protocol（MCP）于 2026 年 7 月 28 日正式发布的规范修订，是该协议自 2024 年 11 月由 Anthropic 开源以来变更幅度最大的一次，也是其 2025 年 12 月移交 Linux Foundation 旗下 Agentic AI Foundation（AAIF）中立治理后的首个大版本。本文以官方规范正文、变更日志与规范增强提案（SEP）原文为基准材料，对本轮修订做系统评述，归纳为三个命题：修订的实质是状态管理责任从协议层向实现层的移置（P1）；次要主线是使协议可被标准 HTTP 基础设施治理（P2）；扩展机制的正式化确立了「核心收敛、变化外置」的演进结构（P3）。在此基础上，本文梳理协议的发布主体、治理结构与 SDK 分级制度，评述特性弃用与新确立的生命周期政策，分析行业意义与生态影响，并面向产品与应用设计者给出设计指引。第十四章以笔者参与建设的中国财税知识库 MCP（公测中）为例，总结定稿前跟进未定稿协议的四条工程做法及其在发布日的检验结果。本文写作横跨候选发布与正式发布，截至 2026 年 7 月 29 日已完成五轮联机核验。

一、引言：修订背景与本文范围

MCP 的版本标识采用日期格式（YYYY-MM-DD），且仅在发生向后不兼容变更时启用新版本号；向后兼容的改动持续合入当前版本，版本号不动。在这一命名规则下，每个新版本号本身即是一次不兼容变更的声明。自 2024 年 11 月首发以来，协议经历了 2025-03-26、2025-06-18、2025-11-25 三个正式版本；官方对版本另有三态划分：Draft（进行中）、Current（现行）、Final（封版不改）。本文写作横跨发布日全天：日间两轮核验时，2026-07-28 版仍处于候选发布（Release Candidate, RC）状态；至 16:47 UTC，规范仓库发布页出现标记为稳定版（非预发布）的 2026-07-28 条目，正文声明「This marks the stable release of the 2026-07-28 revision」，由两位首席维护者之一签发，GPG 签名可验证。Final 至此正式发布，核验细节与当日文档站的同步滞后现象见 3.2 节。

本轮修订的规模在协议自身的发布史上没有先例。官方在 2026 年 5 月 21 日的 RC 公告中明确说明本版包含破坏性变更，并为此设置了十周的 SDK 验证窗口；Python、TypeScript、Go、C# 四个官方 SDK 的 beta 版本于 6 月 29 日全部就位。变更覆盖传输层生命周期、授权模型、工具契约、扩展机制与特性弃用政策，其中传输层的变化（移除协议级会话）直接改写了协议自 2024 年确立的基础假设。

围绕这次修订，可以预期会出现大量以「什么坏了、怎么迁移」为切口的快讯式解读。本文的目标不同：把散落在规范正文、变更日志与十余个 SEP 中的修订内容组织成一个可检验的整体图景，并回答一个快讯不处理的问题：这些变化是否共享同一个设计动机。

本文的贡献有六处：协议发布主体与治理结构的事实梳理（第二章）；以规范正文为基准、逐条标注材料层级的修订评述（第四至九章）；按实现者角色组织的迁移影响分析（第十章）；修订的行业意义与生态影响分析（第十二章）；面向产品与应用设计的指引（第十三章）；以及一份定稿前跟进未定稿协议的工程方法，以真实产品为案例（第十四章）。官方来源清单集中于附录二。第三章交代核验方法与材料层级，后文据此引用。

二、发布主体与治理结构

2.1 从单一厂商到中立基金会

MCP 由 Anthropic 工程师 David Soria Parra 与 Justin Spahr-Summers 创建，2024 年 11 月 25 日以开放标准形式发布并开源（Anthropic, 2024）。此后协议完成了从厂商项目到中立标准的移交：2025 年 12 月 9 日，MCP 捐赠至 Agentic AI Foundation（AAIF），即 Linux Foundation 旗下新设的定向基金，该基金由 Anthropic、Block 与 OpenAI 共同发起，首批入驻项目为 MCP、goose 与 AGENTS.md（Linux Foundation, 2025）。法律实体层面，项目登记为「Model Context Protocol a Series of LF Projects, LLC」；规范与代码以 Apache 2.0 许可发布，文档（规范本身除外）以 CC BY 4.0 发布。

对本文主题的直接含义是：2026-07-28 修订是 MCP 进入中立治理之后的第一个大版本。一个包含破坏性变更的版本能够在竞争厂商共同参与的治理结构下获准发布，这一事实本身构成第十二章行业分析的起点。

2.2 技术治理结构

技术治理采用与 Python、PyTorch 同型的分层结构（治理章程见附录二）。最终决定权归属两位首席维护者（Lead Maintainer，项目沿用 BDFL 惯例）：David Soria Parra 与 Den Delimarsky，前者为协议共同创建者；另一位共同创建者 Justin Spahr-Summers 已转为荣休身份。其下为核心维护者（Core Maintainer）小组，截至核验时点共七人，负责规范与项目整体方向；再下为分管各 SDK、文档与工作组的维护者（Maintainer）。三层合称 Steering Group。

治理章程中有两条规定与协议的中立性直接相关：治理席位授予个人而非公司，章程明文规定不为任何公司保留席位；全部维护者（含核心与首席）与外部贡献者使用同一套拉取请求流程，不得直接修改仓库。规范变更的正式通道为规范增强提案（SEP），由核心维护者小组双周例会裁决；本文引用的各 SEP 编号均产生于该流程。本轮 RC 公告也由两位首席维护者署名，规范文本与治理签发在人事上连续。

2.3 SDK 分级与一致性测试

治理结构之外，项目另设一套面向实现侧的制度：SDK 分级（SDK Tiers）。本文各处出现的「第一梯队 SDK」即指该制度中的 Tier 1，其含义由官方分级页给出，非本文的修辞。

分级共三层：Tier 1 为完整支持，实现全部非实验性特性与可选能力；Tier 2 为积极维护、正在走向完整支持；Tier 3 为实验性、部分实现或专用 SDK。各层的量化义务如下表（择要）：

要求Tier 1Tier 2Tier 3
一致性测试通过率100%80%无下限
新协议特性支持规范发布前六个月内无承诺
议题分诊两个工作日内一个月内无要求
关键缺陷修复七日内两周内无要求
稳定版必须有至少一个不要求

分级并非终身制。最新稳定版上的既有一致性测试若连续四周失败，SDK 自动降级：Tier 1 降 Tier 2 的触发条件是任一一致性测试失败，Tier 2 降 Tier 3 的条件是超过百分之二十的测试失败。

这套制度对理解本轮修订有两处直接作用。Python、TypeScript、Go、C# 四个官方 SDK 的 beta 版本在验证窗口内全部就位，与 Tier 1「新协议特性须在规范发布前支持」的时限要求一致；一致性测试同时充当准入门槛与降级触发器，本文第十二章讨论扩展碎片化风险时，它是协议方手中的对冲手段之一。需要区分的是，截至 2026 年 7 月 29 日，SDK 分级页给出了制度与门槛，但没有列出当前各 SDK 的正式分级名单；后文对具体 SDK 的状态判断因此以各仓库发布页为准。

四、核心修订：协议级会话的移除

4.1 修订前的模型

在 2025-11-25 及此前版本中，MCP 连接以一次 initialize / initialized 握手开始，双方在握手中交换能力声明；服务端签发 Mcp-Session-Id 头，此后的每个请求携带该标识。协议由此持有会话状态：服务端记忆协商结果，tools/list 等列表接口的返回可因会话而异。

这一模型与协议的初始场景（本地 stdio 传输、单进程单连接）相容，但在 HTTP 部署下产生了结构性成本：会话状态驻留于特定服务实例，水平扩展要求负载均衡将同一会话固定路由到同一实例（sticky session），或引入跨实例的共享状态存储。会话语义还使请求无法独立解释：中间层（网关、代理）不解析请求体便无法获知调用内容。

4.2 修订后的模型

2026-07-28 版移除了协议级会话与 Mcp-Session-Id 头（SEP-2567）；握手的废除、server/discover 与版本错误机制则由 SEP-2575 确立。正式版的版本协商章节开宗明义：「There is no negotiation handshake」。请求成为独立的自含单元：协议元数据（含能力声明）随每个请求的 _meta 字段携带，协议版本声明于其中的 io.modelcontextprotocol/protocolVersion 键（HTTP 上同值另置于 MCP-Protocol-Version 请求头）；服务端逐请求接受或拒绝，不支持所请求版本时必须（MUST）返回错误码为 -32022 的 UnsupportedProtocolVersionError，并在错误数据中列出自身支持的版本清单，客户端据此换版重试。一次性的握手式能力交换由新增的 server/discover 方法取代，其义务分配是不对称的：服务端必须实现，客户端可以调用但不被要求，客户端同样可以直接发起任意请求，失败时再处理版本错误。列表接口的返回不再随连接变化，且规范要求服务端应当（SHOULD）以确定性顺序返回工具列表，官方给出的理由是支持客户端缓存并提高语言模型的提示缓存（prompt cache）命中率。一个传输层协议为模型推理的缓存效率规定返回顺序，说明 MCP 的设计目标函数中显式包含「作为模型上下文供给方」的角色。

这一约束并非 MCP 独创。REST 架构风格的无状态约束早已确立了同型判断：每个请求须自含理解该请求所需的全部信息，不得依赖服务器存储的会话上下文（Fielding, 2000, §5.1.3），其代价与收益（以重复传输换取可见性、可靠性与可伸缩性）在 Web 架构二十余年的实践中已被充分检验。MCP 本轮修订可视为向这一成熟约束的回归。正式发布后的规范首页也以同样的语言概括自身基础协议：「无状态、自含的请求」与「逐请求能力协商」（Stateless, self-contained requests；Per-request capability negotiation），这两行自述与本文命题 P1 的表述互为印证。

4.3 状态的去向

移除协议级会话不等于取消状态。正式版对跨调用状态给出的处置是：由服务端签发显式句柄（handle），作为普通工具参数传递。需要多次调用共享上下文的场景（如「启动分析—查询进度」），服务端在首次调用返回标识符，后续调用以参数形式回传。该模式的成本端同样应当指出：状态管理由此部分转嫁给模型，句柄含义的理解与调用顺序的正确性成为模型推理负担的一部分；简单场景（如分页）代价可忽略，多步事务类场景则需评估模型能否稳定管理状态流转。

服务端主动发起的多轮交互（elicitation）原依赖服务器发送事件（SSE）长连接挂起等待，与无状态约束冲突，本轮以官方命名的多轮请求模式（Multi Round-Trip Requests, MRTR；SEP-2322）重设计。全部结果新增必填的 resultType 字段，取值 complete 或 input_required：需要补充输入时，服务端返回 resultType 为 input_required 的 InputRequiredResult，内含所需输入的 schema 与当前处理状态（state）；客户端获得用户输入后，以 inputResponses 连同原样回传的 state 重新提交原调用。因状态随请求携带，重提交可由任意服务实例处理；未携带 resultType 的旧式返回按 complete 处理，以兼容旧服务端。

综合上述三处（业务状态归于服务端句柄、能力状态随请求携带、交互状态由客户端回传），本文提出第一个命题：

命题 P1（状态移置）：2026-07-28 修订的实质不是取消状态，而是状态管理责任从协议层向实现层的系统性移置——协议本身不再持有任何跨请求状态，状态的表示、传递与生命周期管理显式化为实现者的设计对象。

对这一移置的工程含义，笔者的判断是：短期增加实现负担，长期降低系统性风险。协议托管状态时，状态的失效时机与可见性对实现者不透明；显式化之后，状态成为可审查、可测试、可自主决定持久化策略的一等对象。该判断属于基于既有无状态架构经验的推断，本轮修订的实际效果需待社区实践检验。

4.4 配套的删除项

无状态化同时清理了一批依赖「连接持有状态」的机制（SEP-2575），共三组：

一，订阅入口统一。subscriptions/listen 取代 Streamable HTTP 的 GET 通道与 resources/subscribe、resources/unsubscribe 方法，服务端到客户端的通知自此走单一入口。

二，三个操作移除。ping、logging/setLevel 与 notifications/roots/list_changed 被直接删除，日志级别改由每请求 _meta 设置；以 ping 实现保活或健康检查的既有实现由此出现直接破坏点。

三，流恢复移除。SSE 的 Last-Event-ID 头与事件 ID 一并删除，断流后不再续传，客户端重新发起请求即可：请求已经自含全部状态，续传失去了存在理由。

这组删除共享同一判断：凡为「连接是持久对象」这一假设服务的机制，在假设被拿掉之后均无保留必要。

4.5 部署形态的变化

对协议使用者，本节所述修订几乎不可感知；对实现者，其直接后果是部署形态的变化：MCP 服务端从有状态的长连接服务变为可置于标准轮询负载均衡之后的无状态 HTTP 服务，不再需要会话粘滞或共享状态存储，无服务器与边缘环境的部署由此可行（官方公告亦以此为主要收益之一）。受益最大的是将 MCP 纳入企业基础设施的部署方；受影响最大的是已将状态耦合于连接的既有实现，其迁移路径见第十章。

五、传输与可观测性：面向基础设施的修订组

第二组修订单项幅度不大，但共享一个清晰的方向。

一，标准请求头。SEP-2243 要求 Streamable HTTP 的 POST 请求必须携带 Mcp-Method（协议方法名）与 Mcp-Name（目标名称）两个标准头；正式版另将协议版本置于 MCP-Protocol-Version 头（与请求 _meta 中的版本声明同值，见 4.2 节）。三个头合起来，网关、代理等中间层不解析请求体即可完成按方法路由、按版本分流、限流与审计决策；同一提案还引入经工具参数传递自定义头的机制（x-mcp-header）。

二，缓存元数据。可缓存结果强制携带 ttlMs 与 cacheScope 字段（SEP-2549），客户端首次获得协议级的缓存有效期依据。

三，分布式追踪。SEP-414 在 _meta 中约定 OpenTelemetry 追踪上下文的标准键（traceparent、tracestate、baggage），与 W3C Trace Context 规范（W3C, 2020）对接，跨 SDK 的调用链追踪由此有统一载体。

四，错误码规范化。部分既有实现以非标准错误码 -32002 表示资源不存在，本轮统一改用 JSON-RPC 2.0 标准错误码 -32602。依赖字面量 -32002 的客户端逻辑将静默失效，此为本轮修订中少数直接破坏既有代码的点之一。

五，错误码空间划分。本轮确立分配政策：-32000 至 -32019 归实现自定义，-32020 至 -32099 为 MCP 保留段。4.2 节的 -32022 版本错误即落于保留段内，此后协议级错误与实现级错误在码段上可辨。

五项合观，本文提出第二个命题：

命题 P2（基础设施化）：本轮修订的次要主线，是使 MCP 流量可被标准 HTTP 基础设施（负载均衡、网关、缓存、追踪系统）无侵入地治理。协议由「开发者可运行」向「组织可运维」演进。

六、工具契约：JSON Schema 2020-12 的完整支持

工具的输入输出 schema 自本轮起（SEP-2106）放开至完整的 JSON Schema 2020-12 方言，包括组合关键字（oneOf / anyOf / allOf）、条件关键字（if / then / else）与引用（$ref）。

此项修订解决的是工具契约的表达力缺口。此前，参数间的互斥、依赖等约束无法在 schema 中表达，工具作者只能将规则写入自然语言描述，其执行依赖模型的理解与调用方的自觉；修订后，此类约束可由 schema 校验器强制执行。$ref 的支持同时降低了多工具服务端中重复类型定义的维护成本。正式版工具章节与基础协议的「JSON Schema Usage」小节现已上线，明确默认方言为 2020-12，并给出 $ref 解析和组合关键字资源限制。就工具契约的性质而言，这是从「面向模型的说明文本」向「面向机器的可校验合同」的移动。

七、授权模型的收紧

授权是本轮修订中规范性语言（MUST/SHOULD）密度增加最显著的部分，官方公告称涉及六项 SEP。本章按机制而非提案编号组织，全部依据为正式版授权章节正文。

7.1 授权服务器颁发者校验

本轮修订（SEP-2468）将 RFC 9207（OAuth 2.0 授权服务器颁发者标识）纳入规范底座，其要求如下：客户端在发起授权跳转前，必须（MUST）记录所选授权服务器元数据中的 issuer 值，与 PKCE 校验码保存于同一请求记录；授权服务器应当（SHOULD）在授权响应（含错误响应）中附带 iss 参数，附带时必须在元数据中声明 authorization_response_iss_parameter_supported 为真；客户端在向任何令牌端点提交授权码之前，必须完成下表所示校验：

元数据声明支持 iss响应含 iss客户端动作
是是与记录值做简单字符串比较
是否拒绝响应
否或未声明是仍执行比较
否或未声明否放行

两处细节具有工程意义。第一，比较必须为逐字符的简单比较（RFC 3986 §6.2.1），明确禁止任何 URL 归一化——大小写折叠、默认端口省略、尾部斜杠处理、百分号解码均不允许；实现者出于「健壮性」直觉引入的归一化在此构成规范违反。第二，校验同等适用于错误响应：iss 不匹配时，客户端不得处理或展示 error、error_description、error_uri 字段，因其可能来自攻击者构造。正文同时预告，未来版本拟将授权服务器附带 iss 的要求由 SHOULD 升为 MUST。

7.2 客户端注册机制的优先级重排

正式版对客户端注册的规定出现结构性变化：动态客户端注册（Dynamic Client Registration, DCR；RFC 7591）被标记为弃用，保留仅为兼容尚不支持新机制的授权服务器；上位机制为 OAuth 客户端标识元数据文档（Client ID Metadata Documents, CIMD）：客户端以自身控制的 HTTPS URL 作为 client_id，授权服务器识别 URL 形态后反向获取该地址的元数据文档以了解客户端。三种注册机制的优先顺序为：CIMD 优先，预注册次之，DCR 兜底。

CIMD 取消了注册接口与预先建档环节，客户端身份由其公开发布的文档自证。就信任模型而言，这是将客户端身份的锚点从「授权服务器的注册记录」转移到「客户端可验证控制的网络位置」。

DCR 的弃用有两处一手佐证：授权章节正文明写其「已弃用，保留以兼容不支持 CIMD 的授权服务器」；弃用登记表亦将其列为 Deprecated，弃用生效版本为 2026-07-28，迁移路径指向 CIMD，最早移除为 2027-07-28 当日或之后的首个版本。需要如实交代的是，登记表在「弃用 SEP」一栏填写的出处为 PR #2858，而该 PR 的标题与主旨是授权章节的文档拆分重组（2026 年 6 月 4 日合入）。弃用事实本身不因此存疑（正文与登记表已构成双重确认），但读者若循编号追溯原文，会看到一份以重组为主题的提案，此处先行说明。另一处经 Final 变更日志证实的相关要求：兼容期内仍使用 DCR 注册流程的，必须显式声明 application_type（SEP-837）。

7.3 资源指示与权限语义

RFC 8707 的 resource 参数由推荐转为硬性要求：授权请求与令牌请求均必须携带，取值为目标 MCP 服务端的规范化 URI（必须含 scheme、不得含 fragment），且无论授权服务器是否支持该参数，客户端均须发送。其目的为令牌与使用对象的受众绑定，被窃令牌无法用于其他资源服务器。

权限不足的响应语义被明确切分：无令牌或令牌无效返回 401；令牌有效但权限范围（scope）不足返回 403，携带 error="insufficient_scope" 及所需 scope。客户端的对应流程为步进授权（step-up authorization）：以既有 scope 与新挑战 scope 的并集重新授权。规范明确说明，scope 的累积计算是客户端责任，其设计目的是使服务端对客户端的 scope 集合保持无状态。此处与命题 P1 构成呼应：授权线上的状态责任移置方向与传输线一致。

刷新令牌方面：客户端应当在注册元数据中声明 refresh_token 授权类型，但不得（MUST NOT）假设授权服务器一定签发；MCP 服务端作为受保护资源，不应（SHOULD NOT）将 offline_access 列入其声明的 scope，理由是长期凭证的签发属授权服务器决策，非资源侧需求。凭证的存储侧也有了绑定要求：客户端凭证必须按签发它的授权服务器键控保存，不得跨服务器复用（SEP-2352），此为受众绑定思想在客户端侧的对应。

八、扩展机制的正式化

8.1 机制设计

扩展（extensions）在本轮获得正式的协议地位。标识符采用「厂商前缀 / 扩展名」格式，官方扩展使用 io.modelcontextprotocol 前缀，第三方使用自有反向域名前缀。客户端与服务端在各自能力声明新增的 extensions 字段中声明支持项，每个扩展自定义其配置对象的 schema。机制设有两条约束：扩展一律默认关闭，须由开发者显式启用；当一方不支持某扩展时，支持方须退回核心协议行为，或在扩展为硬前提时明确拒绝请求。扩展独立于核心协议版本演进，其更新不需核心维护者审查。

治理流程（SEP-2133）设有一道值得注意的门槛：官方扩展的提案在进入评审前，必须已有至少一个官方 SDK 中的参考实现。以可运行实现为标准化前提，这一顺序设计对扩展质量构成实质约束。

8.3 演进结构的含义

命题 P3（核心收敛、变化外置）：扩展机制的正式化改变了协议的演进结构——核心协议收敛于稳定的最小集合，有争议或未成熟的能力经扩展轨道孵化，其成本与风险由显式的协商机制、默认关闭原则与独立版本化承担。

该结构的代价是碎片化风险：扩展支持在客户端间不均匀分布。官方为此维护各客户端的扩展支持矩阵（见附录二），实现选型时应先行查证。

9.2 生命周期政策

政策由 SEP-2596（《Specification Feature Lifecycle and Deprecation Policy》，2026 年 6 月 3 日合入）确立，其内容比「至少保留十二个月」这一句话细致得多。

特性状态定义为三态：Active（属于当前版本）、Deprecated（仍在规范内但已排期移除，且有成文迁移路径）、Removed（已从草案删除，将不出现在下一当前版本，但仍记载于其最后出现的 Final 版本中）。Deprecated 并非单向：一份取代原弃用 SEP 并说明情势变化的新 SEP 可将特性恢复为 Active，若日后再次弃用，窗口重新计算。

弃用提案必须写明四项：按名指认特性并链接至 schema 定义与规范正文；依据成文标准说明理由（被覆盖同场景的新特性取代、存在无法就地缓解的安全隐私或互操作风险、生态遥测或 SDK 维护者共识显示采用率相对维护成本可忽略，或核心维护者认定的其他理由）；成文的迁移路径，若指名替代特性，该特性须在弃用生效的同一版本中已是 Active；以及最短弃用窗口，不得少于十二个月。窗口的计数起点值得单独指出：自特性首次被标记为 Deprecated 的规范版本发布之日起算，而非自 SEP 定稿之日起算。窗口届满后的首个当前版本中，该特性变为「可移除」，此即登记表中的「最早移除」。可移除不等于必然移除，实际移除由核心维护者在版本准备期裁量执行，特性可以长期停留在 Deprecated 状态。

加急移除的门槛比通常引述的「至少九十天」更严格。十二个月下限仅在特性存在活跃安全风险时方可缩短，而「活跃安全风险」被定义为：已发布安全公告或有据可查的在野利用，且无就地缓解措施。缩短须经核心维护者按治理决策流程批准并记录在案，且缩短后仍须保证至少九十天。

弃用生效时的动作亦成文：schema 条目添加引用弃用 SEP 与生效版本的 @deprecated 注解、规范正文添加弃用通知、该版本变更日志在「Deprecated」标题下添加条目（Deprecated 与 Removed 已成为与 Major、Minor 并列的常设标题）、特性进入登记表。这四步共同保证了一件事：实现者不必从散落于各版本变更日志的条目中重建「什么正在退场、何时退场」的图景，登记表是这一问题的单一答案页。

政策同时对 Tier 1 SDK 施加义务：版本发布为当前版本后，Tier 1 SDK 必须在下一个发行版中用语言原生机制标注对应 API 面（Java 的 @Deprecated、.NET 的 [Obsolete]、TypeScript 的 @deprecated JSDoc、Go 的 Deprecated: 约定），并在机制允许处引用弃用 SEP 与最早移除日；应当在弃用特性被调用时按语言惯例发出运行时警告。持续不履行者进入 2.3 节所述的降级流程。

9.3 评价

对具体的三项弃用，本文的评价是：协议在正式文本中承认三项特性的设计失败并给出有序退出通道，其对协议可信度的贡献不低于任何新增能力。

对政策本身，评价更强一些。SEP-2596 把弃用从「维护者的一次性决定」变成了有窗口、有留痕、有裁决主体、有单一查询入口、并向下游 SDK 传导义务的公开流程。对依赖被弃用特性的实现者，其价值不在宽限期的长度，而在宽限期的可预期性：既包括预期它可能被延长（可移除不等于移除），也包括预期它在何种严格条件下才可能被缩短。

十、迁移影响分析

兼容性问题上，公告口径与正文条款的差异在本章最为具体，需先厘清。SDK beta 公告（2026-06-29）的表述是：「Nothing breaks today, and nothing breaks on July 28 either.」这一承诺成立，但有一个公告未展开的前提。正式版为此引入了一套官方术语：以每请求元数据工作的版本称 Modern（2026-07-28 及以后），以 initialize 握手建立会话的版本称 Legacy（2025-11-25 及以前），同时支持两者的实现称 Dual-era。正文给出的兼容性矩阵可归结为一句话：「不破坏任何一方」仅当服务端实现为 Dual-era 时成立。

两个失败格中，Legacy 客户端对 Modern 服务端的失败尤其值得留意：旧客户端没有任何前向兼容机制，因此正文要求纯 Modern 服务端应当（SHOULD）在拒绝 initialize 的错误响应中列出自身支持的版本，那条错误信息可能是旧客户端用户唯一能看到的诊断。纪元的探测与缓存也有成文规则：stdio 以 server/discover 探测，HTTP 以首个 Modern 请求探测并检查 400 响应体是否含可识别的 Modern 错误；纪元判定是服务端属性而非单请求属性，客户端应当按进程或源缓存判定结果。

对部署决策的直接含义：面向存量客户端的服务端，迁移的现实路径是 Dual-era 而非直接切换为纯 Modern；纯 Modern 部署适合封闭环境或全新生态。迁移节奏仍由实现者自主决定。在此前提下，迁移的实质约束来自三处。

一，SDK 大版本升级。四个官方 SDK 的升级幅度不均：Python 与 TypeScript 为重写级；TypeScript v2 将核心拆为 client、server、node、core 等包，正式版同时提供 ESM 与 CommonJS 构建；Go 保持模块路径；C# 的旧版 API 仍可沿 v1 线维护，但 v2 默认转向无状态 HTTP 与 discovery-first 协商。迁移测试仍应精确锁定版本。

截至 2026 年 7 月 29 日，各官方仓库已经给出与新规范对齐的稳定版：TypeScript 2.0.0、Python 2.0.0、Go 1.7.0、C# 2.0.0；Rust 的 rmcp 3.0.0 也已转为稳定版。TypeScript v1.x 至少六个月内继续接收缺陷与安全修复，Python v1.x 进入维护模式并继续接收关键与安全补丁。

二，直接破坏点。会话依赖逻辑、-32002 错误码依赖、对 initialize 握手时序的假设、以 ping 实现的保活与健康检查、依赖 Last-Event-ID 的断流续传、resources/subscribe 系列方法，六者在新版协议语义下失效，须主动排查（后三者见 4.4 节）。

三，弃用特性退出。Roots、Sampling、Logging 的既有使用在宽限期内不受影响，但新增使用应停止，存量使用应纳入一年期的退出规划。需要单独提出的是 HTTP+SSE 传输：其弃用早于本轮，最早移除时点也早于上述三项（见 9.1 节），仍在使用该传输的实现应将迁移至 Streamable HTTP 的优先级置于本轮其他迁移项之上。使用 includeContext 的 thisServer 或 allServers 取值的实现，应改为省略该字段或取 none。

逐项迁移检查清单按服务端、客户端两个角色整理于附录一。

十一、边界澄清：与本轮修订相邻但不属于它的工作

规范发布的传播周期内，三类相邻工作易被误归入本轮修订，此处逐一澄清。

第一，Skills over MCP。该官方工作组确实存在：2026 年 2 月成立兴趣组，4 月 16 日升格为工作组，由 Anthropic 与 Nordstrom 的维护者共同牵头，参与方包括 Google、GitHub、AWS、Databricks、Bloomberg 等；正式发布后的规范首页也确实将其与 Tasks、MCP Apps 并列为值得关注的扩展方向。但两处事实同样清楚：首页链接指向的是工作组页面而非扩展文档，扩展总览页的官方扩展清单中并无 Skills；其产出方向 SEP-2640（Skills Extension）截至发稿仍处于评审中（In Review）状态，走扩展轨道、基于既有 Resources 原语构建。准确的表述是：Skills 是官方明示的扩展方向，但不属于 2026-07-28 版规范，也尚未成为官方扩展。

第二，Enterprise-Managed Authorization 为授权扩展（见第八章），非核心协议组成部分。

第三，插件式打包（技能、服务端、子代理与配置的单件分发）被 Skills 工作组章程明确列为范围外事项，归属尚未立项的打包议题。

十二、行业意义与生态影响

本章从规范文本转向行业判断，依据是第二章的治理事实、公开的厂商采用记录与前文三个命题。

12.1 中立化之后的第一次破坏性修订

MCP 的行业地位在二十个月内经历三个节点：2024 年 11 月 Anthropic 开源发布；2025 年 3 月，OpenAI 公开支持 MCP，同年 4 月 Google 发布的 Agent Development Kit 已把 MCP 工具列入工具生态，微软也在其产品线中集成，相互竞争的头部厂商在模型工具接口层形成事实上的共同依赖；2025 年 12 月协议移交 AAIF。在此背景下评估本轮修订，其行业意义首先不在任何具体特性，而在事件本身：一个已被竞争厂商共同采用的协议，在中立治理结构下完成了一次破坏性修订。跨厂商标准的破坏性演进在协议史上通常以年计且伴随长期分裂，Python 2 到 3 的迁移是常被引用的先例；MCP 则以十周验证窗口和四个 SDK 同步发布来推进，正式版也在计划日的 16:47 UTC 落地。

发布日的官方口径首次提供了规模量化：官方发布公告称第一梯队 SDK 合计月下载量接近五亿次；Anthropic 同日的宿主侧公告称 SDK 月下载量已超四亿、年内增长四倍，其 Claude 目录收录服务器逾 950 个；AWS、Cloudflare、Google Cloud、微软等在发布当日公开确认支持，Anthropic 宣布支持将陆续上线其产品线。两处下载量口径不同，但都指向同一个结论：MCP 已形成相当规模的生态。

12.2 企业采纳门槛的移动

由命题 P2 可推出一个方向性判断：本轮修订把 MCP 从「开发者协议」推向「企业基础设施协议」。标准请求头、缓存元数据、追踪上下文与无状态部署使协议流量进入企业既有的网关、可观测性与容量管理体系；授权侧的受众绑定、颁发者校验与 403 语义使安全评审可以在 RFC 的语言体系内完成。若该判断成立，企业采纳的瓶颈将从协议能力本身移向组织自身的工具治理能力：哪些工具可以暴露、谁有权授权、如何审计调用。这一移动同时划出了中间层产品的空间，托管、路由、审计与授权代理由此第一次有了稳定的协议层立足点。企业向的外部解读提供了与此互补的两个观察角：有分析指出，组织此前为旧版 MCP 自建的补偿性设施（会话亲和层、自制鉴权与追踪）自本轮起有了「过期日期」；并认为把智能体身份锚定于标准 OAuth 而非厂商私有控制，是规范在企业智能体平台竞争中的一次立场选择（Trilogy AI, 2026-07-23）。此为第四层材料，本文引用为观点而非事实。

12.3 竞争界面的移动

由命题 P3 可推出第二个方向性判断：核心协议收敛后，「是否支持 MCP」将逐渐失去产品区分度，竞争界面移向扩展支持矩阵：宿主是否支持 Apps 的界面渲染、Tasks 的异步调度、企业授权扩展，以及仍在评审中的 Skills 扩展。官方维护的客户端支持矩阵由此从兼容性文档变为竞争格局的观察窗口。伴随的风险是碎片化，扩展支持的不均匀分布可能重演浏览器时代特性碎片化的旧况。协议方目前的对冲手段有四项：扩展默认关闭、要求优雅降级、公开客户端支持矩阵，以及 2.3 节所述的 SDK 分级与一致性测试制度。前三项作用于扩展层，第四项作用于核心层，即以 Tier 1 的百分之百一致性测试通过率与四周降级机制，保证核心协议在主流实现间不发生偏移。这一组合能否在扩展数量增长后继续奏效，须待观察。

十三、面向产品与应用设计的指引

本章面向产品经理与 AI 应用设计者，每条采用「规范事实 → 设计含义」结构，规范事实均可回溯至前文章节。

#规范事实（出处）设计含义与建议
1Tasks 扩展提供五状态生命周期，input_required 为协议级挂起点（8.2 节）长操作可设计为「可离开、可返回」的任务流；人工确认环节应映射到 input_required 状态，而非以阻塞对话的方式实现
2Apps 扩展支持会话内沙箱界面，协议要求优雅降级（8.1、8.2 节）会话内的数据探索、表单与审批流成为标准能力；同一功能必须设计文本回退路径，覆盖不支持该扩展的宿主
3步进授权与 403 insufficient_scope 语义（7.3 节）授权交互可从「一次性大授权」改为「最小初始权限、按操作增量请求」；授权请求的时机与文案成为产品设计对象
4CIMD 以公开元数据自证客户端身份（7.2 节）第三方客户端接入不再依赖逐家注册，集成的运营成本下降；客户端的公开元数据文档本身成为对外资产
5状态移置：跨调用上下文以显式句柄承载（P1，第四章）用户可见的「会话连续性」不再由协议隐式提供；句柄的生命周期、命名与可分享性（深链、协作等场景）成为产品决策，句柄对模型推理负担的代价亦需权衡（4.3 节）
6工具列表确定性排序与缓存元数据（第四、五章）工具清单应作为稳定的 API 面管理：工具的增删与描述变更有真实的推理成本与缓存失效成本，宜纳入变更管理
7工具 schema 支持完整 JSON Schema 2020-12（第六章）参数约束从提示词文案迁入 schema；工具误调用率由此成为可度量、可工程化的质量指标
8核心收敛、能力经扩展轨道孵化（P3，第八章）能力路线图的观察对象从核心版本移向扩展轨道（如评审中的 Skills）；对未定稿扩展的投入应设置触发条件，方法见第十四章

表中八条有一个共同点：本轮修订把若干原属工程内部的决定（状态的存续、权限的粒度、工具面的稳定性）推到了产品可见的层面。协议托管这些事项时，它们是技术副作用；显式化之后，它们成为需要产品立场的设计题。就此而言，命题 P1 所述的状态管理责任移置不止于工程，同样落在产品设计上。

十四、案例经验：中国财税知识库 MCP 的定稿前对齐

笔者主导推进建设的「中国财税知识库 MCP」（chinataxmcp.caixiaoyun.com.cn，目前公测中）将经核验的中国财税政策库封装为 MCP 服务，供 AI 助手检索政策、定位条款和核验引用。这里聚焦它的协议路径：项目在 RC 锁定后、Final 发布前的窗口期内完成了对 2026-07-28 草案的架构对齐。跟进一个未定稿的协议存在双向风险：过早对齐，承担 RC 与 Final 之间正文变动的返工；不对齐，承担 Final 发布后的集中迁移成本。我们用四条做法管理这段窗口期，每条都在发布日前后得到了一轮检验。

做法一，冻结与哈希核对。将官方仓库的机器可读 schema 冻结入项目仓库，记录 SHA-256 摘要与对应提交号，此后每次核验以重新计算摘要比对完成，把「上游是否变动」从主观印象转换为可判定命题。这条做法在 Final 发布当日兑现了价值：哈希比对精确定位出 RC 至 Final 的全部实质差异，变更日志仅有文档链接切换（不改协议语义），schema 唯一的语义变化是订阅相关类型的重命名与响应对象补充；该项目未启用订阅能力，判定为不适用。「Final 与 RC 实质一致」由此从期望变成经比对确认的事实。

做法二，清单化对齐，不凭整体直觉。将变化点分解为逐项可勾选的清单逐项核对实现状态。Final 发布次日的复核清单显示各承重面对齐：生产源码锁定官方稳定 SDK 2.0.0（四包同号，lockfile 固定完整性摘要）；modern 路径按 2026-07-28 工作，无握手、逐请求版本元数据、server/discover 可发现全部工具；对未知版本返回带 requested 与 supported 数据的 -32022，并纳入生产回归。整体直觉式的「架构挺现代、应该没问题」在逐项清单面前的通过率，在笔者经验中显著低于其自信程度。

做法三，分级冻结，挂触发条件而不挂日期。影响面大的改造显式挂接于触发条件（Final 发布、正式变更日志、一致性测试材料可用），条件满足前保持冻结。值得单独指出的是，一致性测试一项在 Final 发布后依然冻结：官方新一代 Conformance 套件截至核验仍为 alpha（0.2.0-alpha.10），稳定线停在面向旧版的 0.1.16。项目据此将公开表述限定为「与 2026-07-28 Final 对齐，并通过官方稳定 SDK 与项目协议回归」，不表述「通过官方一致性认证」。这里有一条可推广的判断：协议正式发布不等于生态组件全部稳定，对外表述必须逐项对应到证据。

做法四，区分官方口径与官方正文。博客公告与规范正文的重心差异在第三章已有实例；该项目的对齐依据一律取正文与 SEP 原文，公告仅用于确定阅读入口与优先级。第十章的兼容性辨析（公告承诺以 Dual-era 为前提）是同一纪律的又一次应用。

部署选择上，该项目为第十章的矩阵分析提供了一个实例：同一个 Streamable HTTP 端点以官方 SDK 的 legacy: "stateless" 模式同时服务 Final 与 2025 时代客户端，实测覆盖 2025-11-25 与 2025-06-18 两个旧版的完整 initialize 旅程；协议升级不要求客户端同日升级，认证、套餐与数据权限在协议协商之外执行，兼容旧握手不降低权限边界。

最后报告一例核验失败，其教训价值不低于上述成功经验。写作本文期间，该项目的一个信息收集 Agent 曾报告「TypeScript SDK v2.0.0 稳定版已发布」，笔者向官方发布页复核，当时最新条目仍是 alpha，官方博客口径亦是 beta，该信息遂被降级为待核实项。稳定版 2.0.0 后来确实随 Final 发布，但结论应验不能追认时点错误：在证据尚不存在时写下的结论，即使事后成真，仍是核验纪律的失败。此例的一般化表述不变：二手信息，包括自有自动化系统生成的汇总，进入结论前必须回溯至一手来源。

十五、结论

本文对 MCP 2026-07-28 修订的评述可压缩为三个命题。状态移置（P1）：协议不再持有跨请求状态，状态管理显式化为实现层的设计对象。基础设施化（P2）：协议流量成为标准 HTTP 基础设施可治理的对象。核心收敛、变化外置（P3）：扩展机制的正式化确立了核心最小化的演进结构。授权收紧与特性弃用分别从安全边界与功能边界两侧配合了这一收敛方向。

从协议史的视角看，本轮修订处理的问题有充分先例：无状态约束是 REST 确立的经典取舍，核心-扩展分层是成熟协议生态的常见演进形态，弃用政策是标准组织的例行工具。MCP 的特殊性在于时间密度——从首发到完成这轮基础假设的重写，间隔不足两年，且重写发生在协议移交中立基金会治理后的第一年。一个处于采用高峰期的协议选择在此时承担破坏性变更的成本，其隐含判断是：修正基础假设的窗口正在关闭，当前生态规模下的迁移成本尚可承受，此后只会更高。这一判断是否正确，是本轮修订留给未来十二个月的开放问题。
