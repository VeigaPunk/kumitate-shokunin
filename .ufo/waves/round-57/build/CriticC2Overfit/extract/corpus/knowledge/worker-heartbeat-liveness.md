# Worker heartbeat and liveness — detecting a dead worker while its work is outstanding

Admitted round 57. Seventh entry of the durable-execution and multi-agent failure
research line (PROVINCE.md frontier band): after identity/dedupe (r54),
redelivery budgets (r55) and the lease slot (r56), this covers the *liveness
signal* side — how the coordinator learns the consumer died rather than merely
not acking. Three mechanisms admitted (S117 Temporal Activity Heartbeats,
S118 Kafka consumer session liveness, S119 Kubernetes liveness probes), one
rejected (S120 RabbitMQ heartbeats — transport keepalive, not worker liveness).

## Mechanisms (what the sources say)

- **A heartbeat is a progress-and-survival ping, not a lease.** Temporal: "An Activity Heartbeat is a ping from the Worker that is executing the Activity to the Temporal Service" and it "informs the Temporal Service that the Activity Execution is making progress and the Worker has not crashed" (S117). `receipt:.ufo/waves/round-57/build/ScoutTemporalHb/heartbeat-def.txt@sha256:ae275a1442b960ba637a0674aad4004ab9b891a4ffac8f0c52e4e6f8ee1e62ca`
- **Heartbeats pair with a separate Heartbeat Timeout.** The ping and its bound are distinct knobs: "Activity Heartbeats work in conjunction with a Heartbeat Timeout"; Temporal's failure surface splits into four timeout slots — Schedule-To-Start, Start-To-Close, Schedule-To-Close, Heartbeat Timeout — each bounding a different leg (S117). `receipt:.ufo/waves/round-57/build/ScoutTemporalHb/heartbeat-timeout.txt@sha256:daca758361fe7321357acd1c562836b9fb66b0f2262e0040760ae586c7252b86`
- **Short timeout + frequent ping is the recommended trade.** "We recommend using a relatively short Heartbeat Timeout and a frequent Heartbeat. That way if a Worker fails it can be handled in a timely manner" — liveness latency is priced directly (S117); the ping can carry an application payload (progress detail). `receipt:.ufo/waves/round-57/build/ScoutTemporalHb/short-timeout.txt@sha256:b0341d12b45325c8709eceb9d50a37e5a9dab77ef70c43707ca645fa9a92c605`
- **Kafka's session timeout is broker-side liveness detection.** "`session.timeout.ms` — The timeout used to detect client failures when using Kafka's group management facility. The client sends periodic heartbeats to indicate its liveness to the broker" (S118). `receipt:.ufo/waves/round-57/build/ScoutKafka/session-timeout.txt@sha256:c8e38adb341d907deaea8d3f7f4c4863612bea7f7db5ba7a87f59befa98cf55d`
- **Cadence is explicitly bounded by the session window.** "`heartbeat.interval.ms` — The expected time between heartbeats to the consumer coordinator"; default 3000 ms, "typically should be set no higher than 1/3" of the session timeout (group.consumer.session.timeout.ms default 45000 ms) — the same short-timeout/ frequent-ping trade as Temporal (S118). `receipt:.ufo/waves/round-57/build/ScoutKafka/heartbeat-interval.txt@sha256:2257eb0db5f167c240f03cad24b69ef9cb6cbded6e9d5ed20264ce1c49e25fa1`
- **Reclaim is group-level, not per-message.** On session expiry "the broker will remove this client from the group and initiate a rebalance" — the dead consumer's partitions re-assign to survivors; liveness drives *membership* eviction, distinct from the visibility-lease redelivery path (S118). `receipt:.ufo/waves/round-57/build/ScoutKafka/rebalance-reclaim.txt@sha256:3fda05bfb106308042662eda74c08c3efd3817843479894185c46152558041b3`
- **Kubernetes probes are platform-polled, not worker-pushed.** "Kubernetes provides liveness probes to detect and remedy" workers that "cannot recover except by being restarted" — the kubelet probes (exec/HTTP/TCP/gRPC); the remedy is a container restart, a different actor than broker reclaim (S119). `receipt:.ufo/waves/round-57/build/ScoutK8s/liveness-remedy.txt@sha256:c0e53b5e0f567662a70a64ed11e82e258aea3ac79300331833d721ddac5682dd`
- **Probe timing is explicit and periodic.** "`periodSeconds` … the kubelet should perform a liveness probe every 5 seconds" with `initialDelaySeconds` for startup grace — liveness as an interval, plus a startup slot for slow initializers (S119). `receipt:.ufo/waves/round-57/build/ScoutK8s/probe-timing.txt@sha256:aa70f64077485ec630c98552267dc88c7af716f5cc721feb24b8dae9d4bb4d3a`

## Lane mapping (the dispatcher's surfaces, origin tree read-only, pin `31c465f1`)

- **The lane's liveness signal is pull-based, not worker-pushed.** Temporal and Kafka workers *push* heartbeats; `fleet-dispatcher.mjs`'s reconcile instead *pulls* — repend fires only on `registered_mission_missing` with a nonzero launcher exit, and `MAX_LAUNCH_MISSES` bounds false-positive reclaims: the same question ("is the worker still there?") answered by inspection, not by the worker's own pings (origin tree). `receipt:.ufo/waves/round-57/build/ScoutQueue/repend-signals.txt@sha256:a9374aa1ef3d2b158ef494b028179e83379df37b1443dcc4db0dfd7c0e3ca85d`
- **[INFERENCE] Push-vs-pull is the entry's real axis.** S117/S118 liveness is pushed (the worker asserts survival); S119 and the dispatcher are pulled (the platform/broker inspects). Pushed heartbeats prove progress AND survival (Temporal's payload can carry progress detail); pulled checks prove only presence — a hung worker that still answers a TCP/exec probe survives its lease forever, which is exactly why the r56 lease slot and this liveness slot are different mechanisms. For the lane, the 120 s `LAUNCHING_GRACE_MS` window plus repend misses is the pull-based analog of Kafka's session expiry — membership reclaim without a heartbeat channel. Design inference from the three sources against lane surfaces, not a claim the sources state. `receipt:.ufo/waves/round-57/build/ScoutQueue/grace-window.txt@sha256:df6754ba6d9a4d1ef8036eb8f43cbd079e06a73c9a3750e765c14d660c00038b`

## Rejected row

- **RabbitMQ heartbeats are transport keepalive, not worker liveness.** AMQP heartbeats "ensure that the application layer promptly finds out about disrupted connections (and peers)"; on detection "the client … needs to re-connect" — the scope is connection↔peer, one verdict per TCP connection, with no notion of outstanding units of work; the name collides with this entry's scope but the mechanism is the r55/r56 transport layer, not the worker-liveness layer (S120, rejected). `receipt:.ufo/waves/round-57/build/ScoutRabbitmqHb/tcp-liveness.txt@sha256:11d8112d78e17f12a8a977172267b5b51d001ba1ece261dd15223cdae8316216`
