# Visibility lease and ack deadlines

Redelivery under at-least-once needs a *lease*: while a consumer works, the message must be outstanding-but-not-deliverable to anyone else, and it must come back if the consumer never acks. That slot — invisible-but-retained — is what brokers call a visibility timeout or ack deadline. This entry is about that mechanism: how three brokers implement the lease, what each one does at expiry, and where the lane's own dispatcher has the same shape. It is the sixth entry of the durable-execution frontier (after `at-least-once-dedupe.md` on identity and `bounded-redelivery-budgets.md` on the counted bound).

## What the sources ground

- **SQS keeps the message and hides it.** On receive, a message "remains in the queue but becomes temporarily invisible to other consumers" — the visibility timeout is a lease on the queue entry itself, not a delete (S114). `receipt:.ufo/waves/round-56/build/ScoutSqs/invisible.txt@sha256:a8833b60287d2d4fbe025b2b99cb5f908a1bb82de66fd9c0f97737aea3f5d8df`
- **Lease expiry re-arms the delivery.** When the SQS visibility timeout expires "the message becomes visible again in the queue and can be retrieved by another consumer"; the default window is 30 seconds (S114). `receipt:.ufo/waves/round-56/build/ScoutSqs/default-30s.txt@sha256:01dbe7420af79408f494c0c33970a4b05bbeae700009cd80baf6887f435029e6`
- **A too-long lease delays redelivery.** SQS's own guidance: setting the visibility timeout too high "can delay the reappearance of unprocessed messages, potentially slowing down retries" — the lease window is the redelivery latency floor, not just a dedupe fence (S114). `receipt:.ufo/waves/round-56/build/ScoutSqs/reappear.txt@sha256:77d84cdaf0f048b42c6222b7339cdeb67f6490ee2f75a6d2db16bc30061c7458`
- **Pub/Sub names it lease management and lets the consumer extend it.** "The subscriber can dynamically modify the acknowledgment deadline, allowing message processing to take an arbitrarily long time" — a renewable lease, whereas SQS's is a fixed window unless changed per-message (S113). `receipt:.ufo/waves/round-56/build/ScoutPubsub/modify-deadline.txt@sha256:5c35a99ee67ba552cf56c30702c0728fef0faeb98dfd5dc413fc504e619b1468`
- **Lease management is a first-class subscription surface.** Pub/Sub's subscriber topic list puts "Lease management" beside dead-letter topics, retry policy and exactly-once delivery — the broker treats the lease as a distinct tunable, not an internal detail (S113). `receipt:.ufo/waves/round-56/build/ScoutPubsub/lease-mgmt.txt@sha256:b563ed628bd6a75eddb424f8df89789c12d710d31bdf66dc5c65768f4f135255`
- **JetStream redelivers on ack-wait expiry.** "If a message isn't acknowledged in time, the server redelivers it, which is what gives you at-least-once delivery" — the ack deadline is the only redelivery trigger; the message itself was never deleted (S115). `receipt:.ufo/waves/round-56/build/ScoutNats/redeliver.txt@sha256:91201948ff8c8589e05d36d148f5b70d9e5a921397dfcbefef4ee8f64d99f93b`
- **The lease is what upgrades core delivery to at-least-once.** JetStream's doc states it directly: core NATS delivers at-most-once "never replayed", while the persistence layer plus the ack/redelivery machinery "gives you at-least-once delivery" — the lease is the mechanism, not a property of the write path (S115). `receipt:.ufo/waves/round-56/build/ScoutNats/at-least-once.txt@sha256:cee616da54f114cfd28fdd958da484c7cd6f8e5a827544a1a08dd81cd3010aa9`

## Mapping to the lane's own lease

- **The dispatcher's lease is a grace window.** `LAUNCHING_GRACE_MS = 120_000` in `fleet-dispatcher.mjs:123` — a `launching` claim younger than the window is left alone; older, reconcile reclaims it. Same slot as the SQS visibility timeout: outstanding, not yet failed (origin tree, read-only, pin `31c465f1`). `receipt:.ufo/waves/round-56/build/ScoutQueue/launching-grace.txt@sha256:9915087d3f38bd824cdf29f0de213959a4cc6cd6121df9747a625e34c29de90d`
- **Claim expiry is bounded too.** `MAX_PAUSED_RESUME_ATTEMPTS = 8` / `MAX_LAUNCH_MISSES = 8` bound how many reclaim cycles a claim may survive — the lease interacts with the counted budget from `bounded-redelivery-budgets.md` rather than standing alone (origin tree, read-only). `receipt:.ufo/waves/round-56/build/ScoutQueue/resume-budgets.txt@sha256:f80043b2c2ce2fa55f94d62332996b5f0f7e07671431bc04c489be638b90a8da`
- **A re-armed delivery is an auditable event.** Only a `registered_mission_missing` block with a nonzero launcher exit is rependable, and repend stamps `blocker.code = "repend_requested"` — lease-expiry redelivery happens through a named path, not an implicit retry (origin tree, read-only). `receipt:.ufo/waves/round-56/build/ScoutQueue/repend-mark.txt@sha256:67a9e354ef7d7d4073a840654b210d541e1e02fcfdfb77c7edf096056b6a0ec9`
- **The receipt ledger is the ack side.** `receipt-attest verify --ledger` answers REPLAY for a nonce already seen: once an invocation is "acked" (recorded), a re-delivery of the same identity is detected — the dedupe half that the lease window alone cannot give (this repo). `receipt:.ufo/waves/round-56/build/ScoutQueue/nonce-ledger.txt@sha256:61d90a93451c3bde645ee1a20b1c253bff2c488cf209384530180141ff48d8ec`
- **[INFERENCE] A lease makes redelivery cheap and bounded, not free.** Combining S113/S114/S115: the lease converts "did the consumer die?" into a timer, so the broker never needs consensus on consumer liveness — but it pays that in redelivery latency (S114's own caution). For the lane, the 120 s grace window is the same trade: reclaim speed vs. false-positive re-pends on slow launches. This is a design inference drawn from the three sources against the lane's surfaces, not a claim the sources state. `receipt:.ufo/waves/round-56/build/ScoutQueue/inference-lease-window.txt@sha256:216d39fe1d85140cf09892fc2d17fb6c2e3c51c6f70b9d904e3862f8e89576d7`
