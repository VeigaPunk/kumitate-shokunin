1) PROBE KINDS (S119 task page)
=====================================================================
The page teaches FOUR liveness-probe mechanisms, each a section:
- exec  (page.txt L25-58): "Define a liveness command" — kubelet runs a command
  inside the container (cat /tmp/healthy); exit 0 = alive, non-zero = "the kubelet
  kills the container and restarts it" (L51-54).
- httpGet (L91-150): HTTP GET to pod IP+port+path; "Any code greater than or equal
  to 200 and less than 400 indicates success. Any other code indicates failure."
  (L124-125). Alpha note: HTTP/2 cleartext (h2c) via protocol:HTTP2 behind
  H2CContainerProbe feature gate (L151-188).
- tcpSocket (L189-236): "the kubelet will attempt to open a socket to your
  container on the specified port. If it can establish a connection, the
  container is considered healthy, if it can't it is considered a failure."
- grpc (L237-271): gRPC Health Checking Protocol; "Stable since Kubernetes
  v1.27"; "There are no error codes for built-in probes. All errors are
  considered as probe failures." TLS mode is Alpha (v1.37,
  GRPCContainerProbeTLS). gRPC probes do NOT support named ports (L299-300).

Named ports: usable for HTTP and TCP probes; "gRPC probes do not support named
ports" (concept page corroborates implicitly).

Concept page "Check mechanisms" (concept.txt ~L110-128): "There are four
different ways to check a container using a probe. Each probe must define
exactly one of these four mechanisms: exec ... grpc ... httpGet ... tcpSocket".
Success criteria verbatim:
- exec: "considered successful if the command exits with a status code of 0."
- grpc: "considered successful if the status of the response is SERVING."
- httpGet: "successful if the response has a status code greater than or equal
  to 200 and less than 400."
- tcpSocket: "successful if the port is open. If the remote system (the
  container) closes the connection immediately after it opens, this counts as
  healthy."
- exec overhead caution: exec forks processes each run; at high pod density /
  low intervals it adds node CPU overhead (concept.txt ~L126-128).

THREE PROBE TYPES vs four mechanisms: the page covers liveness, readiness, and
startup probes (three purposes); each of the three may use any of the four
mechanisms (concept.txt L15-20: "The kubelet can optionally perform and react to
three kinds of probes on running containers" — Startup / Liveness / Readiness).

2) failureThreshold SEMANTICS
=====================================================================
S119 task page (L321-345, "Protect slow starting containers with startup probes"):
- "set up a startup probe with the same command, HTTP or TCP check, with a
  failureThreshold * periodSeconds long enough to cover the worst case startup
  time."
- Worked example: livenessProbe failureThreshold:1 periodSeconds:10;
  startupProbe failureThreshold:30 periodSeconds:10.
- "the application will have a maximum of 5 minutes (30 * 10 = 300s) to finish
  its startup."
- "If the startup probe never succeeds, the container is killed after 300s and
  subject to the pod's restartPolicy."
==> failureThreshold is a COUNT of consecutive failures; the kill window =
failureThreshold x periodSeconds.

Concept page (L173, field definitions; one long line):
- "failureThreshold After a probe fails failureThreshold times in a row,
  Kubernetes considers that the overall check has failed: the container is not
  ready/healthy/live. Defaults to 3. Minimum value is 1."
- "For the case of a startup or liveness probe, if at least failureThreshold
  probes have failed, Kubernetes treats the container as unhealthy and triggers
  a restart for that specific container. The kubelet honors the setting of
  terminationGracePeriodSeconds for that container."
- "For a failed readiness probe, the kubelet continues running the container
  that failed checks, and also continues to run more probes; because the check
  failed, the kubelet sets the Ready condition on the Pod to false."
- Sibling fields: timeoutSeconds "Number of seconds after which the probe times
  out. Defaults to 1 second. Minimum value is 1."; successThreshold "Minimum
  consecutive successes for the probe to be considered successful after having
  failed. Defaults to 1. Must be 1 for liveness and startup Probes."; periodSeconds
  default 10s min 1; initialDelaySeconds default 0.

3) restartPolicy INTERACTION
=====================================================================
S119 page L344-345: startup probe never succeeding => "the container is killed
after 300s and subject to the pod's restartPolicy." — the probe only kills; the
restart itself is governed by the pod's restartPolicy.

Concept page:
- L27-28 (startup probe failure): "If the startup probe fails, the kubelet kills
  the container, and the container is subjected to its restart policy."
- L31-33 (liveness): "If a container fails its liveness probe more times than
  the configured tolerance, the kubelet restarts that container."
- L82-83: "If the process in your container is able to crash on its own whenever
  it encounters an issue or becomes unhealthy, you do not necessarily need a
  liveness probe; the kubelet will automatically perform the correct action in
  accordance with the Pod's restartPolicy."
- L85-86: "If you'd like your container to be killed and restarted if a probe
  fails, then specify a liveness probe, and specify a restartPolicy of Always or
  OnFailure." — i.e. probe-triggered restart REQUIRES restartPolicy
  Always/OnFailure; under Never the kill still happens but no restart follows.
- L131-135 (probe results): each probe result is Success / Failure / Unknown;
  for liveness+startup "the kubelet kills the container, and the container is
  subjected to its restart policy"; for readiness "the kubelet marks the
  container as not ready, and the Pod stops receiving traffic"; Unknown = "no
  action should be taken". Absent probe = always Success.
- Restart is CONTAINER-scoped ("triggers a restart for that specific
  container"), not pod-scoped; RESTARTS counter in kubectl output increments
  (page L88-90).
- terminationGracePeriodSeconds (probe-level): kubelet waits the grace period
  between shutdown trigger and forced runtime stop; inherits pod-level 30s
  default.
- Caution (concept.txt ~L40-45): "Liveness probes must be configured carefully
  to ensure that they truly indicate unrecoverable application failure ...
  Incorrect implementation of liveness probes can lead to cascading failures."

4) STARTUP-PROBE ROLE vs LIVENESS
=====================================================================
S119 page L317-345 ("Protect slow starting containers with startup probes"):
- Problem: slow first-initialization apps make it "tricky to set up liveness
  probe parameters without compromising the fast response to deadlocks that
  motivated such a probe."
- Mechanism: startup probe with same check, failureThreshold*periodSeconds
  covering worst-case startup.
- Hand-off verbatim (L342-343): "Once the startup probe has succeeded once, the
  liveness probe takes over to provide a fast response to container deadlocks."
- Failure verbatim (L344-345): "If the startup probe never succeeds, the
  container is killed after 300s and subject to the pod's restartPolicy."

Concept page:
- L21-23: "If a startup probe is configured, Kubernetes does not execute
  liveness or readiness probes until the startup probe succeeds, allowing the
  application time to finish its initialization."
- L25-26: "This type of probe is only executed at startup, unlike liveness and
  readiness probes, which are run periodically."
- L36-38 (independence): "Liveness probes do not wait for readiness probes to
  succeed. If you want to wait before executing a liveness probe, you can either
  define initialDelaySeconds or use a startup probe."
- L73-77 (sizing rule): "If your container usually starts in more than
  initialDelaySeconds + failureThreshold x periodSeconds, you should specify a
  startup probe that checks the same endpoint as the liveness probe ... set its
  failureThreshold high enough to allow the container to start, without changing
  the default values of the liveness probe."
- L173 (initialDelaySeconds field): "If a startup probe is defined, liveness and
  readiness probe delays do not begin until the startup probe has succeeded."
- Readiness distinction (S119 page L347-376): readiness runs "during [the
  container's] whole lifecycle"; "The readiness and liveness probes do not
  depend on each other to succeed"; readiness failure => unready/no traffic, NOT
  kill.

==> Division of labor: startup probe = a one-shot startup lease that DISARMS
liveness+readiness until first success (long deadline, kills on exhaustion);
liveness probe = periodic deadlock detector armed after startup, tuned for fast
response (small failureThreshold, e.g. 1-3). Both share the kill remedy;
readiness never kills — it only gates Service traffic.

WORKER-LIVENESS READ (axis relevance, marked inference)
=====================================================================
[INFERENCE] For the durable-execution worker-liveness line: the kubelet PULLS
liveness (platform-poll of exec/HTTP/TCP/gRPC), the remedy is container restart
(a different actor than the task's own lease reclaim), and failureThreshold x
periodSeconds is the failure-detection deadline — the pull-analog of a heartbeat
timeout. Startup probe is a separate initial lease so a slow boot does not trip
the steady-state detector — the same separation the lane draws between launch
grace and heartbeat miss accounting.
